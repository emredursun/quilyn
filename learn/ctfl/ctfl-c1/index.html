Chapter keywords: explain, distinguish and exemplify

These are original plain-language explanations, not quotations from the official glossary. For each term, give a new example and explain its difference from a neighboring term. Use the official glossary with the CTFL syllabus context for authoritative wording.

Chapter plan

FL-1.1.1 · Test objectives · K1

Test objectives

Testing supplies evidence for decisions, finds defects, evaluates work products and reduces uncertainty about quality. Verification concerns specified requirements; validation concerns stakeholder needs.

Worked example: A checkout meets its written rules but excludes the customers who need it. Verification evidence alone does not establish fitness for use.

Close the notes: Give one verification and one validation objective for a checkout.

  • CTFL syllabus v4.0.1, section 1.1 (FL-1.1.1)

FL-1.1.2 · Testing and debugging · K2

Testing and debugging

Testing reveals failures or finds defects directly; debugging investigates causes and implements fixes. Confirmation testing checks a fix; regression testing checks for adverse effects.

Worked example: A tester reproduces a rounding failure. A developer locates the incorrect conversion and changes it. These are different activities.

Close the notes: Who identifies a failure, who diagnoses it, and what follows the fix?

  • CTFL syllabus v4.0.1, section 1.1 (FL-1.1.2)

FL-1.2.1 · Why testing matters · K2

Why testing matters

Testing supports delivery decisions by providing evidence about quality and risk. Early defect detection can prevent expensive downstream rework; testing cannot promise zero operational failures.

Worked example: A review exposes an ambiguous dosage rule before code is written, avoiding implementation and retesting of the wrong behavior.

Close the notes: How can testing add value before executable code exists?

  • CTFL syllabus v4.0.1, section 1.2 (FL-1.2.1)

FL-1.2.2 · Testing and quality assurance · K1

Testing and quality assurance

Testing is product-oriented quality control. Quality assurance improves the processes used to develop and test products; both contribute to quality management.

Worked example: Reviewing a requirement is testing. Changing the requirements workflow using recurring review findings is process improvement.

Close the notes: Distinguish evaluating a product from improving the process that makes it.

  • CTFL syllabus v4.0.1, section 1.2 (FL-1.2.2)

FL-1.2.3 · Root cause, error, defect and failure · K2

Root cause, error, defect and failure

A root cause contributes to an error. A person's mistaken action can introduce a defect in a work product. Execution under triggering conditions can expose a failure; a defect need not cause failure on every execution.

Worked example: Poor training contributes to a misunderstood tax rule; an incorrect expression enters the code; an invoice displays the wrong tax.

Close the notes: Identify each link in the causal chain without calling all of them bugs.

  • CTFL syllabus v4.0.1, section 1.2 (FL-1.2.3)

FL-1.3.1 · Seven testing principles · K2

Seven testing principles

Tests can reveal defects but cannot establish their absence. Exhaustive testing is usually infeasible. Start testing early, investigate defect clusters, vary aging tests, adapt to context and validate usefulness even when few defects remain.

Worked example: A perfectly implemented reporting specification can still be useless to analysts. This illustrates the absence-of-defects fallacy.

Close the notes: Explain all seven principles using a concrete counterexample to each misconception.

  • CTFL syllabus v4.0.1, section 1.3 (FL-1.3.1)

FL-1.4.1 · Test activities · K2

Test activities

Planning establishes objectives and approach; monitoring compares progress with plans; control changes actions. Analysis identifies what to test; design defines how; implementation prepares executable testware; execution compares results; completion consolidates outcomes.

Worked example: Deriving conditions from a requirement is analysis; choosing representative inputs is design; assembling scripts and data is implementation.

Close the notes: Classify identifying conditions, selecting values, preparing a suite and comparing results.

  • CTFL syllabus v4.0.1, section 1.4 (FL-1.4.1)

FL-1.4.2 · Context and the test process · K2

Context and the test process

Stakeholders, risks, domain, architecture, resources, skills and delivery lifecycle shape the process. Adapt the work and documentation to the context while preserving the required evidence.

Worked example: A regulated medical release needs stronger evidence and independence than a disposable internal prototype.

Close the notes: Which contextual facts would change your test approach?

  • CTFL syllabus v4.0.1, section 1.4 (FL-1.4.2)

FL-1.4.3 · Testware · K2

Testware

Testware includes plans, conditions, cases, data, procedures, scripts, logs and reports. Associate each artifact with the activity that primarily produces it; artifacts may evolve across activities.

Worked example: A test log records actual execution; a test case describes inputs, preconditions and expected results before execution.

Close the notes: Match a test condition, case, script, log and completion report to their purpose.

  • CTFL syllabus v4.0.1, section 1.4 (FL-1.4.3)

FL-1.4.4 · Traceability · K2

Traceability

Links from the test basis through conditions, cases, results and defects support coverage evaluation, impact analysis, reporting and audits. A large test count without those links does not demonstrate requirement coverage.

Worked example: A changed discount requirement can be traced to affected cases and unresolved defects before a regression suite is selected.

Close the notes: How would you identify tests affected by a requirement change?

  • CTFL syllabus v4.0.1, section 1.4 (FL-1.4.4)

FL-1.4.5 · Test roles · K2

Test roles

The test management role coordinates planning, monitoring, control and completion. The testing role performs analysis, design, implementation and execution. One person can carry both roles; allocation depends on context.

Worked example: An Agile tester designs cases and also helps coordinate iteration testing; role responsibilities need not imply separate job titles.

Close the notes: Separate a responsibility from the job title of the person doing it.

  • CTFL syllabus v4.0.1, section 1.4 (FL-1.4.5)

FL-1.5.1 · Testing skills · K2

Testing skills

Analytical thinking, curiosity, care, communication, teamwork, technical knowledge and domain knowledge help testers. Communicate evidence constructively, separating observations from blame.

Worked example: A report states reproducible steps and business impact rather than accusing an author of carelessness.

Close the notes: Rewrite a blame-focused defect message as a factual observation.

  • CTFL syllabus v4.0.1, section 1.5 (FL-1.5.1)

FL-1.5.2 · Whole team approach · K1

Whole team approach

Quality is a shared team responsibility. Testers, developers and business representatives collaborate and share knowledge; dedicated skills and context-dependent independence still matter.

Worked example: A tester helps a business representative refine an example while a developer explains implementation constraints.

Close the notes: What does shared responsibility change about day-to-day collaboration?

  • CTFL syllabus v4.0.1, section 1.5 (FL-1.5.2)

FL-1.5.3 · Testing independence · K2

Testing independence

Different perspectives can challenge author assumptions and reveal different defects. Excessive separation can create communication barriers or reduce developer ownership; independence is not a substitute for collaboration.

Worked example: A separate test group catches an assumption missed by the author but joins refinement to avoid becoming isolated.

Close the notes: Name one benefit and one drawback of increasing independence.

  • CTFL syllabus v4.0.1, section 1.5 (FL-1.5.3)

Keyword self-check: chapter 1

Attempt these after studying the chapter, without looking at the keyword table. Explain each answer in your own words, then open the solution.

Try first: Error, defect, failure and root cause

An analyst writes an ambiguous requirement. A developer misreads it and codes “points < 50” instead of “points ≤ 50”. In production, a customer with exactly 50 points is refused a discount. Classify the misreading, the faulty line of code and the refusal. Then explain the two roles of the ambiguous requirement.

Show solution

The misreading is an error (a human mistake). “points < 50” is a defect in the code. The refused discount is a failure observed while the system runs. The ambiguous requirement is itself a defect in the requirements, produced by the analyst’s error. It is also the root cause of the developer’s error: a fundamental reason that led to it. Removing such causes helps prevent similar defects.

Try first: Test object, test basis and testware

A team tests release 2.3 of a mobile app against its user stories. During testing it produces test cases, automated scripts and a test completion report. Identify the test object, the test basis and the testware.

Show solution

Test object: release 2.3 of the app, the work product being tested. Test basis: the user stories, from which the tests are derived. Testware: the test cases, scripts and report, the work products produced by the test process.

Try first: Testing versus debugging

A tester runs a test and observes a failure. A developer reproduces it, locates the defect and fixes the code. The tester then reruns the original test. Which of these activities are testing and which are debugging?

Show solution

Running the test and rerunning it are testing; the rerun is confirmation testing. Reproducing, diagnosing (locating the defect) and fixing are debugging. Testing can trigger failures or find defects directly, but it does not fix them.

Try first: Verification, validation and quality assurance

Classify each activity: (1) checking that a release meets its specified requirements; (2) checking with users that the release meets their needs in its operational environment; (3) improving the team’s review process to prevent defects.

Show solution

(1) Verification. (2) Validation. (3) Quality assurance: it is process-oriented and preventive. Testing itself is a product-oriented quality control activity.

Try first: Test condition, test case, test procedure and test data

For a login story: (a) “account lockout after repeated failed attempts”; (b) “user u1 enters a wrong password three times; expect the account to be locked”; (c) “create u1, run (b), then run the unlock test, in that order”; (d) the u1 credentials. Classify each item and name the activity that produces it.

Show solution

(a) Test condition, from test analysis. (b) Test case, from test design. (c) Test procedure, from test implementation. (d) Test data, also prepared in test implementation. Traceability links each one back to the story.
