FL-2.1.1 · Lifecycle impact · K2

Lifecycle impact

The lifecycle influences timing, scope, documentation, automation and roles. Sequential models often align levels with stages; iterative delivery repeats test activities within increments and needs growing regression coverage.

Worked example: A team shipping weekly maintains regression automation while testing the new increment each week.

Close the notes: How would testing differ between a staged release and weekly increments?

FL-2.1.2 · Lifecycle-independent practices · K1

Lifecycle-independent practices

For each development activity use a corresponding test activity, define objectives for each test level, start analysis and design early, and involve testers in reviewing work products when drafts exist.

Worked example: Draft requirements can be reviewed before development finishes even in a sequential lifecycle.

Close the notes: Recall good testing practices that apply across lifecycle models.

  • CTFL syllabus v4.0.1, section 2.1 (FL-2.1.2)

FL-2.1.3 · Test-first development · K1

Test-first development

TDD starts from component tests; ATDD starts from collaboratively agreed acceptance examples; BDD expresses desired behavior in a stakeholder-readable form, often Given/When/Then.

Worked example: An acceptance example is agreed before implementing a user story. A unit assertion written first is a different test-first practice.

Close the notes: Distinguish TDD, ATDD and BDD by the test basis and participants.

  • CTFL syllabus v4.0.1, section 2.1 (FL-2.1.3)

FL-2.1.4 · DevOps and testing · K2

DevOps and testing

CI/CD and collaboration shorten feedback through automated builds and tests. Reliable environments and maintainable automation need investment; manual and non-functional testing remain useful.

Worked example: A pipeline quickly catches a regression, while a tester still explores a newly designed workflow.

Close the notes: Which testing benefits and costs can a delivery pipeline introduce?

  • CTFL syllabus v4.0.1, section 2.1 (FL-2.1.4)

FL-2.1.5 · Shift left · K2

Shift left

Perform useful testing earlier: review drafts, analyze code and design tests before implementation. Shift left complements later system and operational testing rather than removing it.

Worked example: Discussing an invalid input rule during refinement prevents a defect before the feature is coded.

Close the notes: Give an early test activity and a later activity that remains necessary.

  • CTFL syllabus v4.0.1, section 2.1 (FL-2.1.5)

FL-2.1.6 · Retrospectives · K2

Retrospectives

Inspect the process using evidence, agree actionable improvements, assign owners and follow up. Include successes as well as problems; evaluate actions in later iterations.

Worked example: After repeated environment delays, a team assigns an owner to an automated environment check and reviews its effect next iteration.

Close the notes: Turn a complaint into a measurable improvement action.

  • CTFL syllabus v4.0.1, section 2.1 (FL-2.1.6)

FL-2.2.1 · Test levels · K2

Test levels

Component testing isolates units; component integration tests interactions between components; system tests evaluate the whole product; system integration tests interactions with other systems; acceptance evaluates readiness and stakeholder needs.

Worked example: Testing a service against a stub is different from testing the deployed product against an external bank.

Close the notes: Classify five tests by their object, objective and basis, not their execution tool.

  • CTFL syllabus v4.0.1, section 2.2 (FL-2.2.1)

FL-2.2.2 · Test types · K2

Test types

Functional testing addresses what a system does; non-functional testing addresses how well it behaves. The syllabus lists performance efficiency, compatibility, usability (interaction capability), reliability, security, maintainability, portability (flexibility) and safety as non-functional characteristics. Black-box tests derive from behavior; white-box tests derive from structure. Levels and types are different dimensions.

Worked example: A component performance check is non-functional testing at component level; a system price calculation check is functional.

Non-functional characteristic in the CTFL syllabusExample evidence
Performance efficiencyA search finishes within its specified response-time limit under the stated load.
CompatibilityTwo supported applications coexist and exchange information as required.
Usability / interaction capabilityRepresentative users can complete the task and understand error feedback.
ReliabilityThe service recovers after an interruption and preserves the required behavior.
SecurityAn unauthorized user cannot read another account’s records.
MaintainabilityA localized change can be analyzed, implemented and tested without unintended coupling.
Portability / flexibilityThe supported deployment can move to another specified environment.
SafetyA hazardous condition is handled without exposing people or assets to the specified unacceptable harm.

Use the characteristics listed in this syllabus edition. A correct exported total is functional evidence; the time required to export it is non-functional evidence. Either type may be checked at more than one test level.

Close the notes: Can non-functional testing occur below system level? Explain.

FL-2.2.3 · Confirmation and regression · K2

Confirmation and regression

Confirmation verifies that a reported defect has been corrected. Regression looks for harmful consequences of change, including in connected or unchanged areas. Both can occur at every level.

Worked example: Rerun the failing invoice test to confirm the fix; test unaffected discount paths for regression.

Close the notes: Given two post-fix checks, identify their different objectives.

  • CTFL syllabus v4.0.1, section 2.2 (FL-2.2.3)

FL-2.3.1 · Maintenance testing · K2

Maintenance testing

Changes, migrations, environment upgrades and retirement can trigger maintenance tests. Impact analysis guides scope based on change risk, system size and change size; archived data may need retrieval tests.

Worked example: Retiring an application still requires checking that legally retained records can be restored.

Close the notes: Why can retirement require testing even when no new feature is delivered?

  • CTFL syllabus v4.0.1, section 2.3 (FL-2.3.1)

Keyword self-check: chapter 2

Attempt these after studying the chapter, without looking at the keyword table. Explain each answer in your own words, then open the solution.

Try first: Confirmation versus regression testing

A defect in the discount calculation is fixed. Test A reruns the failing discount test. Test B reruns the tests for the checkout and invoice areas, whose code was not changed. Which is confirmation testing and which is regression testing?

Show solution

Test A is confirmation testing: it checks that the original defect is fixed. Test B is regression testing: it checks that the change has not caused unwanted effects elsewhere. Regression tests are often good candidates for automation because they are run repeatedly.

Try first: Test level versus test type

A team runs performance tests during system testing and functional tests during component testing. Which terms are test levels, which are test types, and can every test type be used at every level?

Show solution

System testing and component testing are test levels. Performance (non-functional) and functional testing are test types. Any of the four CTFL test types (functional, non-functional, black-box and white-box) can be performed at any test level, with a different focus at each level.

Try first: Component integration versus system integration

Test X checks the interface between the cart module and the pricing module of one application. Test Y checks the exchange between the application and an external payment service. Classify both.

Show solution

X is component integration testing: interactions between components of one system. Y is system integration testing: interactions with other systems and external services.

Try first: Maintenance testing triggers

Which of these trigger maintenance testing: (1) a hotfix to production code; (2) moving the system to a new cloud platform; (3) retiring an application whose data must be archived; (4) testing the first release of a new system that is not yet in operation?

Show solution

(1), (2) and (3). Modifications, upgrades or migrations of the operational environment, and retirement are maintenance triggers. (4) concerns a system that is not yet operational, so it is not maintenance testing.
