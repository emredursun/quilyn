FL-3.1.1 · Static test objects · K1

Static test objects

Reviews can examine requirements, designs, code, tests, contracts and other readable work products. Static analysis needs an analyzable structure or syntax. Neither requires execution of the test object.

Worked example: Reviewing an acceptance criterion is possible before software exists; measuring running response time is dynamic.

Close the notes: Name three non-code work products suitable for static testing.

  • CTFL syllabus v4.0.1, section 3.1 (FL-3.1.1)

FL-3.1.2 · Value of static testing · K2

Value of static testing

Static testing exposes defects directly and can find ambiguity, inconsistency, omissions and unreachable code early. It can reduce downstream cost and improve shared understanding.

Worked example: A requirements review finds contradictory currencies before developers implement either interpretation.

Close the notes: Explain an early defect that dynamic execution might struggle to identify directly.

  • CTFL syllabus v4.0.1, section 3.1 (FL-3.1.2)

FL-3.1.3 · Static and dynamic testing · K2

Static and dynamic testing

Static testing examines a work product without executing it; dynamic testing executes software and observes behavior. They find overlapping but different defect types and complement one another.

Worked example: A review spots a missing rule; an execution test exposes a timeout under load.

Close the notes: Choose the technique based on the evidence needed, not on whether a tool is used.

  • CTFL syllabus v4.0.1, section 3.1 (FL-3.1.3)

FL-3.2.1 · Early stakeholder feedback · K1

Early stakeholder feedback

Frequent feedback helps correct misunderstandings early, clarifies requirements and reduces the cost of building the wrong product.

Worked example: A customer reviews a small draft workflow and corrects a mistaken assumption before implementation.

Close the notes: Recall how smaller, earlier feedback cycles reduce wasted work.

  • CTFL syllabus v4.0.1, section 3.2 (FL-3.2.1)

FL-3.2.2 · Review process · K2

Review process

Plan the review; initiate it with access and instructions; review individually; communicate and analyze anomalies; fix and report. An anomaly is investigated before it is classified as a defect.

Worked example: Reviewers first record observations independently, then discuss which require changes, before the author fixes them.

Close the notes: Distinguish individual review from communication and analysis.

  • CTFL syllabus v4.0.1, section 3.2 (FL-3.2.2)

FL-3.2.3 · Review roles · K1

Review roles

The manager allocates support and resources; the author creates and fixes the work product; the moderator facilitates; the scribe records; reviewers examine; the review leader organizes and takes overall responsibility.

Worked example: A moderator keeps a review constructive while the scribe records decisions and anomalies.

Close the notes: Match facilitation, recording and overall organization to roles.

  • CTFL syllabus v4.0.1, section 3.2 (FL-3.2.3)

FL-3.2.4 · Review types · K2

Review types

Informal reviews need no defined formal process; walkthroughs are author-led; technical reviews use qualified reviewers and a moderator; inspections use the most formal process and collect metrics. In inspections the author cannot be review leader or scribe.

Worked example: A formal inspection checks entry and exit conditions and records metrics; an author-led teaching session is a walkthrough.

Close the notes: Choose a review type from its defining process characteristics.

  • CTFL syllabus v4.0.1, section 3.2 (FL-3.2.4)

FL-3.2.5 · Review success · K1

Review success

Use clear objectives, small work products, preparation time, trained participants, management support and a constructive culture. Review work products rather than using defects to appraise people.

Worked example: A short prepared review with an explicit objective encourages useful findings; a blame meeting suppresses them.

Close the notes: Recall three conditions that make reviews more effective.

  • CTFL syllabus v4.0.1, section 3.2 (FL-3.2.5)

Keyword self-check: chapter 3

Attempt these after studying the chapter, without looking at the keyword table. Explain each answer in your own words, then open the solution.

Try first: Static versus dynamic testing

Test 1: reviewers read a user story and find a contradictory acceptance criterion. Test 2: a test run of the built feature shows a wrong total. Which is static testing, and what does each find?

Show solution

Test 1 is static testing: nothing is executed, and the review finds the defect directly. Test 2 is dynamic testing: execution causes a failure, which must then be analysed to locate the defect.

Try first: Choose the review type

(1) The author leads a session to explain a design to new team members and gather ideas. (2) Technically qualified reviewers, led by a moderator, must decide between two architecture options. (3) A review with defined roles, collected metrics and an author who cannot act as review leader or scribe aims to find as many anomalies as possible. Name each review type.

Show solution

(1) Walkthrough. (2) Technical review. (3) Inspection, the most formal type. An informal review follows no defined process and requires no formal documented output.

Try first: Static analysis versus review

A tool reports unreachable code and a variable used before it is assigned. Later, three colleagues read the design document and discuss its gaps. Which activity is static analysis, which is a review, and what do they have in common?

Show solution

The tool-based check is static analysis; the colleagues reading the document perform a review. Both are static testing: neither executes the software.

Try first: Anomaly versus defect

Reviewers log 12 anomalies. After analysis, 9 are confirmed as defects, 2 are misunderstandings by the reviewers and 1 is a change request. Why are the logged items called anomalies?

Show solution

An anomaly is a condition that deviates from expectation. In the review process, each logged anomaly is then evaluated and given a status and action: a defect, not a defect, or a different action such as a change request.
