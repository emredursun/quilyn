FL-4.1.1 · Technique families · K2

Technique families

Black-box techniques model specified behavior; white-box techniques analyze internal structure; experience-based techniques exploit tester knowledge. They complement each other rather than competing for a universal best choice.

Worked example: A decision table comes from business rules; branch tests come from control flow; error guessing comes from prior failures.

Close the notes: Classify a proposed technique by the basis used to derive tests.

FL-4.2.1 · Equivalence partitioning · K3

Equivalence partitioning

Identify non-empty, non-overlapping groups expected to be treated alike. Cover valid and invalid partitions. Each Choice for multiple inputs covers every partition of each input, not every combination.

Worked example: An integer quota accepts 10 through 50 inclusive: below 10, 10–50 and above 50 are three partitions. Values 9, 30 and 51 cover all three.

Try first: Delivery quantity and service

Delivery quantity is an integer: 1–20 is accepted; smaller and larger quantities are rejected. Service is standard or express; every other service value is rejected. Derive all partitions. Calculate Each Choice coverage for tests (5, standard) and (12, express). Then add the fewest tests that reach 100%, with at most one invalid value per test.

Show solution

Quantity has three partitions (≤0, 1–20, ≥21); service has three (standard, express, other): six in total. The two tests cover 1–20, standard and express: 3/6 = 50%. Add (0, standard), (21, express) and (5, other). Each new test contains one invalid value, so a rejection can be traced to its cause, and coverage becomes 6/6 = 100%. Each Choice coverage does not test every combination.

Close the notes: Derive partitions before choosing representatives and calculate covered / total partitions.

FL-4.2.2 · Boundary value analysis · K3

Boundary value analysis

Start with the feasible input domain and every ordered partition, including invalid partitions. List each finite minimum and maximum. The union of these boundary values is the 2-value coverage set. For 3-value coverage add both immediate neighbors of every boundary value, keep only feasible inputs and deduplicate. An unbounded integer domain with accepted L through U has finite boundaries L-1,L,U,U+1; full 3-value coverage normally also needs L-2,L+1,U-1,U+2. A bounded domain can add outer endpoints and their feasible neighbors; close boundaries can overlap.

Worked example: For the domain of all integers with accepted 10–50, partitions are x<10, 10–50 and x>50. Finite boundary values are 9,10,50,51. Their 3-value neighborhoods unite to 8,9,10,11,49,50,51,52. If the feasible domain instead starts at zero, add outer boundary 0 to the 2-value set and 0,1 to the 3-value set. Negative values are then infeasible, not extra invalid test inputs.

Domain and partitions2-value set3-value set
Non-negative integers; 0≤x<10, 10≤x≤50, x>500,9,10,50,510,1,8,9,10,11,49,50,51,52
All integers; x<2, x=2, x>21,2,30,1,2,3,4

Compared with the worked example above, a non-negative domain adds the finite minimum 0, and −1 is infeasible. A singleton partition has the same minimum and maximum, so neighborhoods overlap. No fixed six-value or eight-value shortcut is safe: the domain, partitions and requested scope determine the set.

Try first: Price field with two decimals

A price field accepts 0.01 to 99.99 in steps of 0.01. Negative values cannot be entered. 0.00 and every value from 100.00 upward can be entered but are rejected; there is no upper input limit. Identify the partitions, then list the 2-value and 3-value BVA sets.

Show solution

Partitions: {0.00} invalid, 0.01–99.99 valid, ≥100.00 invalid. The upper invalid partition has no finite maximum. 2-value set: 0.00, 0.01, 99.99, 100.00 (4 values). 3-value set: 0.00, 0.01, 0.02, 99.98, 99.99, 100.00, 100.01 (7 values). −0.01 is infeasible, and overlapping neighbors are counted once.

Close the notes: Declare the feasible domain, derive every partition and its extrema, then form both coverage unions. Explain why valid endpoints alone omit invalid-partition boundaries.

FL-4.2.3 · Decision tables · K3

Decision tables

Represent condition combinations as rules and associate actions. Remove infeasible rules; merge rules with identical outcomes when a condition is irrelevant. Coverage counts exercised feasible rules, not individual conditions.

Worked example: A discount needs membership AND a qualifying basket. With two independent booleans, four feasible combinations exist; only true/true earns the discount.

Condition / actionR1R2R3R4
MemberTTFF
Qualifying basketTFTF
Give discountX

For the rule Member AND Qualifying basket, the two conditions give 2×2 = 4 combinations, so the full table has four columns. A test for member=false, qualifying=false exercises R4 and expects no discount. Testing R1 twice still covers only one distinct rule.

Condition / actionReduced R1Reduced R2Reduced R3
MemberTTF
Qualifying basketTF-
Give discountX
SymbolMeaning
T / FThe condition is satisfied / not satisfied.
-The condition is irrelevant to the outcome of this rule.
N/AThe condition is infeasible for this rule. It is not the same as irrelevant.
X / blankPerform the action / do not perform it.

When membership is false, the basket condition is irrelevant, so the two full-table columns merge into Reduced R3. Coverage counts the feasible rule columns of the table actually under test; infeasible columns are excluded. Full minimization algorithms are outside CTFL scope.

Try first: Account creation rules

An account is created if the applicant is registered AND (is 18 or older OR has parental consent). Conditions in order: registered, adult, consent. Build the full table, then a reduced table. Which reduced rules do tests (T,T,F) and (F,F,F) cover, and what coverage do they achieve?

Show solution

Full table: 2³ = 8 rules. An account is created only for (T,T,T), (T,T,F) and (T,F,T). Reduced table, four rules: not registered (others -) → no account; registered and adult (consent -) → create; registered, not adult, consent → create; registered, not adult, no consent → no account. (T,T,F) exercises the registered-and-adult rule and (F,F,F) the not-registered rule: 2/4 = 50%. Add (T,F,T) and (T,F,F) to reach 100% of the reduced table.

Close the notes: Construct the full table before minimizing it and keep impossible combinations separate.

FL-4.2.4 · State transitions · K3

State transitions

Model states and event-triggered transitions, including guards and actions. State coverage can miss transitions. All valid transition coverage exercises each modeled valid transition. All transitions coverage adds attempted invalid transitions from the state table; isolate one invalid transition per test to avoid defect masking. All transitions coverage subsumes valid transitions coverage, which subsumes all states coverage.

Worked example: Draft → Submitted → Approved → Draft visits three states but a separate Submitted → Draft rejection transition remains untested.

Original guarded example: states Locked and Unlocked. Label syntax is event [guard] / action. From Locked, badge [valid] / release goes to Unlocked; badge [not valid] / recordFailure is a valid self-loop back to Locked. From Unlocked, timeout / engage returns to Locked.

Current statebadge [valid]badge [not valid]timeout
LockedUnlocked / releaseLocked / recordFailureInvalid
UnlockedInvalidInvalidLocked / engage

The syllabus convention leaves invalid transitions as empty cells; Invalid is written here for readability.

Start Locked: badge(valid), timeout, badge(not valid) covers all three valid transitions, including the self-loop. The rejected badge in Locked is a modeled valid transition, not an invalid transition. The three Invalid cells need separate attempted-event tests if all-transitions coverage is requested; isolate one invalid attempt per test to limit defect masking.

Try first: Coverage of a short test

Using the table above, one test starts Locked and runs badge(valid), then timeout. Calculate all-states, valid-transitions and all-transitions coverage.

Show solution

States: Locked and Unlocked are both visited, 2/2 = 100%. Valid transitions: release and engage are exercised, but the recordFailure self-loop is not: 2/3 ≈ 67%. All transitions (3 valid + 3 invalid table cells): 2/6 ≈ 33%. Full state coverage does not imply full transition coverage.

Try first: Invalid transitions

Using the table above, design one test for each Invalid cell. Start each test Locked, name its setup sequence and make exactly one invalid attempt. Do not chain invalid events.

Show solution

(1) No setup; attempt timeout in Locked. (2) badge(valid) to reach Unlocked; attempt badge(valid). (3) badge(valid) to reach Unlocked; attempt badge(not valid). These cover the three invalid cells separately. With the valid-transition sequence above they exercise all six table cells. The state model does not specify error messages: take the expected rejection behavior from the requirements, and do not assume an invalid attempt changes state.

Close the notes: Trace the events from the specified initial state and distinguish states from transitions.

FL-4.3.1 · Statement testing · K2

Statement testing

Statement coverage is executed executable statements divided by total executable statements. Full statement coverage says nothing certain about untested decision outcomes or missing requirements.

Trace model: S1 sets fee=0; decision D tests premium; its true outcome executes S2, which sets fee=5; both paths reach S3, which returns fee. The executable statements are S1, D, S2 and S3 (the decision itself counts as a statement). The control-flow graph has four branches: S1→D, D→S2 (true), D→S3 (false) and S2→S3.

Try first: One test, two coverage measures

The only test uses premium=true. Calculate statement coverage and branch coverage for the model above. Which branch is not exercised?

Show solution

Statements: S1, D, S2 and S3 all execute, 4/4 = 100%. Branches: S1→D, D→S2 and S2→S3 execute, 3/4 = 75%. D→S3 (premium=false) is not exercised. 100% statement coverage does not imply 100% branch coverage. CTFL branch coverage counts every branch in the graph, conditional and unconditional, not only the decision outcomes.

Recap example: An if-without-else can execute every statement when true while never testing its false branch.

Close the notes: Compute statement coverage and explain what 100% does not establish.

  • CTFL syllabus v4.0.1, section 4.3 (FL-4.3.1)

FL-4.3.2 · Branch testing · K2

Branch testing

Branch coverage counts exercised control-flow branches. Full branch coverage subsumes full statement coverage, but not the reverse; neither implies all paths or correct requirements.

Try first: Branches versus paths

Decision X tests x>0: true executes A, false executes B. Both continue to decision Y, which tests y>0: true executes C, false executes D. Both end at End. The control-flow graph has eight branches: X→A, X→B, A→Y, B→Y, Y→C, Y→D, C→End, D→End. What branch coverage do tests (1,1) and (−1,−1) achieve? Which routes through the code are never executed?

Show solution

(1,1) exercises X→A, A→Y, Y→C, C→End; (−1,−1) exercises X→B, B→Y, Y→D, D→End: 8/8 = 100% branch coverage, so every statement also executes. The routes A-then-D and B-then-C are never executed. Full branch coverage does not mean every path has run; path testing is outside CTFL scope. Neither result proves the specified behavior is correct.

Recap example: Running both outcomes of each if covers branches, but not necessarily every combination of outcomes through the program.

Close the notes: Explain why all branches does not mean all paths.

  • CTFL syllabus v4.0.1, section 4.3 (FL-4.3.2)

FL-4.3.3 · Value of white-box testing · K2

Value of white-box testing

Structural coverage supplies objective evidence and can reveal gaps in behavior-based testing. It cannot identify an omitted requirement simply because all implemented code is exercised.

Worked example: A coverage tool reports 100% for a calculator that lacks a required tax rule. The missing rule still needs specification-based tests.

Close the notes: What defect can remain when the implemented structure has full coverage?

FL-4.4.1 · Error guessing · K2

Error guessing

Use experience of errors, defects, failures and the application domain to target likely mistakes. Fault attacks organize likely defect types and corresponding tests.

Worked example: Past timezone failures motivate trying a date across a daylight-saving transition.

Close the notes: Distinguish a hypothesis about likely mistakes from a formal structural coverage target.

FL-4.4.2 · Exploratory testing · K2

Exploratory testing

Learning, test design and execution influence each other during exploration. A timeboxed session can use a charter, notes, coverage observations and a debrief; exploration is not unrecorded random clicking.

Worked example: A tester investigates interrupted checkout, follows a surprising result and records observations within a session charter.

Close the notes: Write a focused charter and name the evidence you would record.

FL-4.4.3 · Checklist-based testing · K2

Checklist-based testing

Use a list of conditions derived from experience and needs to guide checks. Keep it relevant and update it with findings. Broad items permit varied execution, but vague or stale lists can miss defects.

Worked example: An accessibility checklist prompts keyboard navigation checks across screens without prescribing every click.

Close the notes: How would a checklist guide testing without becoming a detailed script?

FL-4.5.1 · Collaborative user stories · K2

Collaborative user stories

Business, development and testing perspectives refine a story together. The card starts a conversation and confirmation examples clarify intent. INVEST asks for independent, negotiable, valuable, estimable, small and testable stories.

Worked example: A tester asks what happens when a booking fails, helping turn a vague story into testable behavior.

Close the notes: Use the three perspectives to resolve one ambiguity in a story.

  • CTFL syllabus v4.0.1, section 4.5 (FL-4.5.1)

FL-4.5.2 · Acceptance criteria · K2

Acceptance criteria

Acceptance criteria set shared, unambiguous conditions for accepting a story and include positive and negative behavior. They may be scenario-oriented or rule-oriented.

Worked example: Given a locked account, when correct credentials are entered, then access remains denied is scenario-oriented; a list of locking rules is rule-oriented.

Close the notes: Express the same acceptance condition in both formats.

  • CTFL syllabus v4.0.1, section 4.5 (FL-4.5.2)

FL-4.5.3 · Acceptance test-driven development · K3

Acceptance test-driven development

Discuss the story and criteria before implementation; derive stakeholder-readable tests for its characteristics. Include positive, negative and relevant non-functional cases without inventing unrelated scope. Agree concrete examples before implementation, then use their expected results to guide the work.

Worked example: For free delivery on baskets of at least EUR 60, EUR 60 gets free delivery and EUR 59 does not. Agree these examples before coding.

Try first: Order cancellation story

A signed-in customer may cancel their own Pending order; cancellation sets it to Cancelled and restores its reserved stock once. Shipped orders reject cancellation without changing stock. Write two acceptance cases. What does a second cancellation request require you to clarify?

Show solution

Given a Pending order with 2 reserved units and available stock 8, when its customer cancels, then the status is Cancelled and stock is 10. Given a Shipped order and stock 8, when its customer attempts cancellation, then cancellation is rejected, the status stays Shipped and stock stays 8. The story does not define the response to a repeated request for a Cancelled order: clarify it collaboratively while keeping the once-only stock rule. Do not invent a response code or latency requirement.

Close the notes: Derive tests that follow exactly the story's acceptance rules.

Keyword self-check: chapter 4

Attempt these after studying the chapter, without looking at the keyword table. Explain each answer in your own words, then open the solution.

Try first: Coverage item versus coverage

For an age field you identify 3 equivalence partitions and your tests exercise 2 of them. What are the coverage items, and what is the coverage?

Show solution

The 3 partitions are the coverage items, derived from the test conditions. Coverage is 2/3 ≈ 67%. Always state the items and the denominator with a coverage figure.

Try first: Classify the techniques

Classify: equivalence partitioning, branch testing, error guessing, decision table testing, checklist-based testing, statement testing, exploratory testing, state transition testing.

Show solution

Black-box: equivalence partitioning, decision table testing, state transition testing. White-box: statement testing, branch testing. Experience-based: error guessing, exploratory testing, checklist-based testing.

Try first: Which experience-based technique?

Name the technique in each case. (1) A tester designs, executes and evaluates tests at the same time within a time-boxed charter. (2) A tester anticipates likely mistakes from past failures, such as empty input or division by zero. (3) A tester follows a list of questions derived from experience and standards.

Show solution

(1) Exploratory testing, here session-based. (2) Error guessing. (3) Checklist-based testing.

Try first: Acceptance criteria versus ATDD

A story states: “Orders of at least EUR 60 ship free.” The team agrees examples (EUR 60 free, EUR 59.99 charged) and writes tests from them before coding. Which part is the acceptance criterion and which is ATDD?

Show solution

“Orders of at least EUR 60 ship free” is an acceptance criterion: a condition the story must meet. Agreeing examples and deriving tests before implementation is acceptance test-driven development, a collaboration-based test approach.
