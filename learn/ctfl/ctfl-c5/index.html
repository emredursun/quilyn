FL-5.1.1 · Test plans · K2

Test plans

A plan communicates objectives, scope, basis, approach, roles, assumptions, risks, resources, schedule and reporting. Update it as context changes; it does not remove uncertainty.

Worked example: A shared plan records what an external payment outage means for testing and who decides on mitigation.

Close the notes: What should stakeholders learn from the test plan?

FL-5.1.2 · Planning contributions · K1

Planning contributions

Testers help refine testable stories and criteria, analyze risks, estimate effort and plan activities at release and iteration scales.

Worked example: During refinement a tester identifies missing test data and estimates the testing tasks.

Close the notes: Recall how a tester contributes before implementation begins.

FL-5.1.3 · Entry and exit criteria · K2

Entry and exit criteria

Entry criteria express prerequisites to begin an activity; exit criteria express completion expectations. If time ends before quality targets are met, communicate residual risk and obtain stakeholder acceptance.

Worked example: A ready environment is an entry condition; required coverage and acceptable open-defect risk are exit conditions.

Close the notes: Classify a criterion by the activity boundary it controls.

FL-5.1.4 · Effort estimation · K3

Effort estimation

Use relevant historical ratios, extrapolation from current observations, Wideband Delphi or three-point estimation. In Wideband Delphi experts estimate independently, discuss differences, then re-estimate until consensus; Planning Poker is a card-based Agile variant. For three-point use E=(a+4m+b)/6 and SD=(b-a)/6; effort and calendar duration differ.

Worked example: With a=4, m=7 and b=16 person-days, E=8 and SD=2. Parallel staffing does not automatically divide calendar time exactly.

TechniqueBasisWhat to do
RatiosRelevant completed projectsApply the historical test/development effort ratio to comparable work.
ExtrapolationObservations from the current projectUse an explicitly stated model, such as recent comparable iteration means.
Wideband DelphiIndependent expert estimatesCollect isolated estimates; discuss when they fall outside the agreed range, re-estimate in isolation and repeat to consensus. Planning Poker is a card-based variant.
Three-pointOptimistic, most likely and pessimistic expert estimatesUse the stated weighted mean and spread model; retain assumptions and effort units.

Technique-selection check: experts first estimate in isolation, discuss estimates outside the agreed range and privately estimate again. This is Wideband Delphi; using numbered effort cards is its Planning Poker variant. Taking a numerical mean of recorded iteration effort is extrapolation, not expert consensus.

Try first: Ratio and three-point estimates

Historical development:test effort is 4:1, and comparable development work is 240 person-hours. A different task has three-point estimates a=3, m=6, b=15 person-days. Calculate the ratio estimate, then E = (a + 4m + b)/6 and SD = (b − a)/6. Keep the units.

Show solution

Ratio estimate = 240 × 1/4 = 60 person-hours. E = (3 + 24 + 15)/6 = 7 person-days; SD = (15 − 3)/6 = 2 person-days, written as 7 ± 2 person-days (5 to 9). The spread alone is not a guaranteed completion interval. Neither result gives calendar duration without availability, dependencies and other scheduling assumptions.

Try first: Extrapolation

The last three iterations needed 18, 22 and 20 test hours for comparable scope. Using their mean as the model, estimate the next iteration and state one assumption.

Show solution

(18 + 22 + 20)/3 = 20 test hours. Assumption: the next iteration has comparable scope, team and conditions. If that changes, the extrapolation model no longer applies without adjustment.

Close the notes: Calculate an estimate, state its unit and identify its assumptions.

FL-5.1.5 · Test prioritization · K3

Test prioritization

Order tests by risk, coverage contribution or stakeholder priority as requested. Respect dependencies and resources. Additional coverage prioritization recalculates new coverage after every selection.

Worked example: T1 covers A,B; T2 covers B,C; T3 covers D. After T1, both T2 and T3 add one new item, so an explicit tie-breaker is needed.

TestCovered itemsPrerequisite
T1A, B, CNone
T2A, BNone
T3D, ET1
T4FNone

Try first: Additional coverage with a dependency

A test is eligible only after its prerequisite has run. Order the tests in the table above by additional coverage among eligible tests. Break equal contributions by the lower test number.

Show solution

T1 first (3 new items). T3 becomes eligible and adds 2. T4 adds 1. T2 adds 0. Order: T1, T3, T4, T2. Ordering by total coverage would put T2 ahead of T4; additional coverage must be recalculated after every selection.

Try first: Risk-based order with a dependency

T1 is Low risk. T2 is High risk but needs T3 to run first. T3 is Medium risk. T4 is High risk. At each step, run the highest-risk test whose prerequisite has already run; break equal risk by the lower test number. Derive the order.

Show solution

T4 first (High and eligible). T2 is High but not yet eligible, so its prerequisite T3 runs next (Medium beats Low). Then T2, then T1. Order: T4, T3, T2, T1. A high-risk test cannot run before a mandatory prerequisite.

Close the notes: Derive an order from the stated strategy and document ties rather than guessing.

FL-5.1.6 · Test pyramid · K1

Test pyramid

The pyramid typically has many fast, small, isolated tests and fewer slow, broad end-to-end tests. Layer labels vary; use the model to balance feedback speed and breadth.

Worked example: A team moves repeated business-rule checks from slow UI flows into fast component tests while preserving essential user journeys.

Close the notes: Recall what changes from the bottom to the top of the pyramid.

  • CTFL syllabus v4.0.1, section 5.1 (FL-5.1.6)

FL-5.1.7 · Testing quadrants · K2

Testing quadrants

The quadrants combine business/technology focus with support-team/critique-product purpose. Q1 technology supports the team; Q2 business supports the team; Q3 business critiques the product; Q4 technology critiques the product. They are not lifecycle stages.

Worked example: Business acceptance examples support implementation in Q2; a load test critiques technical behavior in Q4.

Close the notes: Classify a test on both axes and avoid treating quadrants as execution order.

  • CTFL syllabus v4.0.1, section 5.1 (FL-5.1.7)

FL-5.2.1 · Risk attributes · K1

Risk attributes

Risk combines likelihood and impact. Numeric risk levels may use likelihood multiplied by impact when scales permit; qualitative labels need a defined comparison model.

Worked example: A likelihood of 0.2 and a EUR 50,000 loss imply EUR 10,000 expected exposure under that model.

Close the notes: Recall the two attributes and distinguish a scoring model from a probability guarantee.

  • CTFL syllabus v4.0.1, section 5.2 (FL-5.2.1)

FL-5.2.2 · Product and project risks · K2

Product and project risks

Product risks concern quality of the delivered product. Project risks concern execution of the project, such as staffing, supplier delays or environment availability; one can influence the other.

Worked example: An incorrect interest calculation is a product risk; losing the test specialist before release is a project risk.

Close the notes: Classify risks by what is at risk, not who reports them.

  • CTFL syllabus v4.0.1, section 5.2 (FL-5.2.2)

FL-5.2.3 · Risk analysis and test scope · K2

Risk analysis and test scope

Risk analysis combines identification and assessment. Identification produces a list using workshops, interviews, brainstorming or cause-effect diagrams. Assessment categorizes already identified risks, estimates likelihood, impact and level, prioritizes them and proposes responses. Use the results to choose scope, priority, techniques, coverage and effort; revise the analysis as evidence changes.

Worked example: A high-impact refund risk receives deeper negative and boundary testing than a low-impact cosmetic preference.

Close the notes: Explain how a risk assessment changes test depth rather than merely test order.

  • CTFL syllabus v4.0.1, section 5.2 (FL-5.2.3)

FL-5.2.4 · Product risk responses · K2

Product risk responses

Risk control combines risk mitigation and risk monitoring. Respond through mitigation, acceptance, transfer or contingency planning as appropriate. Testing reduces uncertainty and can support mitigation; it does not itself fix defects or eliminate all risk.

Worked example: A critical defect triggers a fix and targeted regression while stakeholders assess residual release risk.

Close the notes: Separate a test action, a corrective action and a risk acceptance decision.

  • CTFL syllabus v4.0.1, section 5.2 (FL-5.2.4)

FL-5.3.1 · Test metrics · K1

Test metrics

Metrics can describe progress, execution outcomes, coverage, defects, risk and effort. State denominators and context; a pass rate is not a direct measure of overall product quality.

Worked example: 80 passed of 100 executed gives an 80% execution pass rate, even when 200 tests were planned.

Close the notes: Recall useful metrics and state the denominator of each percentage.

  • CTFL syllabus v4.0.1, section 5.3 (FL-5.3.1)

FL-5.3.2 · Test reports · K2

Test reports

Progress reports support ongoing control with current status, impediments and next actions. Completion reports summarize outcomes, deviations, residual risk and lessons for the completed activity; tailor detail to the audience.

Worked example: A daily report explains blocked tests; a completion report summarizes remaining risk at the end of the release test cycle.

Close the notes: Choose report content for its timing, purpose and decision maker.

  • CTFL syllabus v4.0.1, section 5.3 (FL-5.3.2)

FL-5.3.3 · Communicating test status · K2

Communicating test status

Use audience-appropriate reports, dashboards, meetings or informal discussion. Communicate urgent blockers and risk changes promptly, with evidence and proposed actions.

Worked example: An executive needs business impact and a decision request; a developer needs reproduction data and environment details.

Close the notes: Translate the same issue for a business sponsor and a technical colleague.

  • CTFL syllabus v4.0.1, section 5.3 (FL-5.3.3)

FL-5.4.1 · Configuration management · K2

Configuration management

Identify and version test objects and testware, control changes and preserve baselines and traceability. Reproducing a result needs the matching build, configuration, data and tests.

Worked example: A failure on build 12 cannot be reproduced confidently using an unknown build and newer test data.

Close the notes: List the configuration items needed to reproduce a test run.

  • CTFL syllabus v4.0.1, section 5.4 (FL-5.4.1)

FL-5.5.1 · Defect reporting · K3

Defect reporting

Write a concise title, reproducible steps, build and environment, data, expected and actual results, supporting evidence, severity, priority and references. Severity describes impact; priority expresses urgency to fix.

Worked example: A payment defect report specifies currency, amount, build, steps and observed discrepancy rather than saying payments are broken.

Try first: Report a stock defect

Acceptance criterion AC-3: cancelling a Pending order sets it to Cancelled and restores its reserved stock once. Build 4.2, Chrome 130. You are signed in as the owner of Pending order O17 (2 reserved units; available stock 8). You cancel once. The status becomes Cancelled, but available stock becomes 12. Draft a defect report that another tester can reproduce without asking you questions.

Show solution

Title: “Cancellation restores reserved stock twice”. Environment: build 4.2, Chrome 130. Preconditions: signed in as owner; O17 Pending, reserved 2, available 8. Steps: open O17 and cancel once. Expected: Cancelled and available stock 10 (AC-3). Actual: Cancelled and available stock 12. Attach timestamped before/after evidence and reference AC-3 and the test identifier. Assess severity from the inventory impact; agree priority with the responsible stakeholders. The tracking tool normally records the ID, reporter, date and initial status: check they are present. The observation does not prove which component caused it.

Close the notes: Select or prepare a report that lets a different person reproduce and assess the anomaly.

Keyword self-check: chapter 5

Attempt these after studying the chapter, without looking at the keyword table. Explain each answer in your own words, then open the solution.

Try first: Product risk versus project risk

Classify: (1) a key tester is unavailable for two weeks; (2) search may respond too slowly under peak load; (3) a supplier delivers a component late; (4) a payment calculation may be wrong.

Show solution

Project risks: (1) and (3). They affect the management and control of the project. Product risks: (2) and (4). They concern product quality characteristics.

Try first: Parts of risk management

Place each activity in risk analysis (identification or assessment) or risk control (mitigation or monitoring): identifying risks in a workshop; rating each risk by likelihood and impact; adding tests for a high risk; checking whether a mitigation is working.

Show solution

Identifying risks in a workshop: risk identification. Rating likelihood and impact: risk assessment, which determines the risk level. Both are part of risk analysis. Adding tests: risk mitigation. Checking that the mitigation works: risk monitoring. Mitigation and monitoring are part of risk control.

Try first: Entry versus exit criteria

“The test environment is available and the story is ready for testing” and “All high-risk tests have passed and the defined coverage is achieved”. Which is an entry criterion and which an exit criterion?

Show solution

The first is an entry criterion: a precondition for starting an activity. The second is an exit criterion: what must be achieved to declare the activity complete. In Agile, entry criteria are often called the Definition of Ready and exit criteria the Definition of Done.

Try first: Monitoring, control and reports

A test manager (1) collects pass/fail and coverage data daily; (2) reassigns testers to a blocked area; (3) sends a weekly status summary; (4) summarizes the results when testing ends. Classify each.

Show solution

(1) Test monitoring. (2) Test control: guiding actions based on monitoring information. (3) Test progress report. (4) Test completion report.

Try first: Test pyramid versus testing quadrants

Classify these tests into testing quadrants: a component test, tests derived from user-story examples, a usability test and a performance test. Then state what the test pyramid says about the number of tests at its lower layers.

Show solution

Component test: Q1 (technology-facing, supports the team). Tests from user-story examples: Q2 (business-facing, supports the team). Usability test: Q3 (business-facing, critiques the product). Performance test: Q4 (technology-facing, critiques the product). In the test pyramid, lower layers have many small, fast, isolated tests, and higher layers have fewer, more complex tests.
