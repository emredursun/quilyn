Rules and Rule Types

Rule

The basic building block of a Pega application. Each Rule is an instance of a Rule Type (e.g., a Flow Rule models a Process). Rules define application behavior without custom coding.

Rule Type

A template for creating a Rule that models a specific behavior — for example, a Flow Rule models a Process, while other Rule Types model UI, automated Decisions, and more.

Automated Rule creation in App Studio

App Studio auto-creates Rules as you design:

  • Adding a Process creates its underlying Flow Rule.
  • Case design and UI configuration generate/manage underlying task and presentation Rules; the exact record types depend on the UI architecture.
  • The cited rule-creation topic shows a Section example; do not apply Section/Harness assumptions universally to Constellation.

Rules are the rules of chess: agreed instructions that govern how each piece behaves (a pawn moves one or two spaces on its first move). A Rule Type is the rulebook chapter; a Rule is one specific instruction in it.

Application Modularity with Rules

Versioning

Creating a new version of a Rule whenever Case behavior must change. Pega keeps a full change history, enabling rollback of a specific Rule without affecting others.

Delegation

Exposing a specific Rule to business users so they can update Case behavior as conditions change, without filing an IT change request or touching other rules.

Reuse

Developers reuse Rules whenever an application needs existing behavior, instead of reconfiguring it every time (e.g., reuse one policyholder-info UI form across auto, property, and marine claims).

Parametrization

To increase reusability, use parameters to drive a Rule's logic based on a passed value instead of hard-coded data — reducing code duplication and the time to implement Rule specializations.

Modular Rules are like LEGO bricks: Versioning is swapping one brick for an improved one without rebuilding the model; Delegation hands a labeled brick to a business user to adjust; Reuse clicks the same brick into many models.

Rulesets and Versioning

Ruleset

A group that identifies, stores, and manages the Rules defining an application or a significant portion of it. Rulesets enable versioning, access control, and portability.

Ruleset version

An instance of a Ruleset collecting individual Rules. To update contents you create a NEW version (unlocked), add/change Rules, then lock it when complete.

Ruleset stack

The ordered Ruleset sequence used when selecting applicable Rules. Stack order is one input to resolution alongside class context and other eligibility criteria; it is not a guarantee that the first same-named record always wins.

Independent analogy: an ordered collection helps prioritize eligible variants, but real selection must also respect class context, versions and eligibility.

Rule Creation

Two paths to a Rule

In App Studio, Rules are created FOR you as you build the Case Life Cycle, Views, and data. In Dev Studio, you can directly create and manage how a Rule is created and reused to maintain Rule integrity and reusability.

Specialization by copy (Save As)

Save As can create a context-specific variant while preserving the original. Change at least one of identifier, class or Ruleset; leaving all three unchanged is rejected. Inspect the target context before creating the copy.

App Studio is autopilot (Rules generated as you build); Dev Studio is manual flight (you decide exactly which class/Ruleset a Rule lives in and how it is reused).

Classes and Class Hierarchy

Class

A grouping of Rules according to their capacity for reuse:

  • Work class (process Cases)
  • Integration class (connect to systems)
  • Data class (describe data types)

Parent and child classes

A class can contain other classes. A parent class contains another class; a child class is contained by another. A child class can reuse/inherit any Rules defined for its parent class.

Class hierarchy

The introductory inheritance search starts in the specific class and expands toward general classes. This describes class reuse, not the entire Rule resolution algorithm or a guarantee that every ancestor Rule is eligible.

The class hierarchy is a family tree read upward: a child inherits traits from parents and grandparents. Pega first asks the child for a Rule, then walks up the tree to ever-more-general ancestors.

Rule Reuse Through Inheritance

Pattern inheritance

Pattern inheritance uses class-name prefixes to search the naming hierarchy. The Academy topic describes this as automatic; inspect the class configuration rather than assuming all Rule selection is determined solely by its name.

Directed inheritance

Inheritance where the parent class is EXPLICITLY specified on the class form. It lets an application class inherit from standard Pega classes outside the naming hierarchy.

Resolution order & @baseclass

Pega alternates pattern and directed searches up the class hierarchy. If no Rule is found by @baseclass, Pega returns a Rule-not-found error.

Pattern inheritance is following your own family surname up the tree (automatic); directed inheritance is a formal adoption document on the class form that points to a different parent so you can inherit standard Pega rules too.
