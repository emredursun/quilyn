Basics of a Data Model

Data Model

The visual representation of all data elements and their relationships. It serves as a common language between Business and IT, existing at three levels: Conceptual, Logical, and Physical.

Conceptual Data Model

A living document built WITH BUSINESS STAKEHOLDERS using Entities, Attributes, and Relationships (cardinality). It describes WHAT data exists, not how it is stored.

Logical Data Model

The Conceptual model translated and refined for Pega Platform: entities become DATA OBJECTS and attributes become FIELDS. The BA configures the primary elements (data objects, fields, relationships) in App Studio, while System Architects configure advanced requirements in Dev Studio.

Physical Data Model

Reflects how data is actually stored and accessed — integration settings, local Pega database storage, and external System of Record connectivity. Derived from the Logical model.

Crayon → Lego → Plumbing: The Conceptual model is the crayon sketch you show stakeholders; the Logical model is the Lego build (objects and fields snapped together in App Studio); the Physical model is the plumbing (how data is really stored and piped in via integrations).

Understanding Data Objects

Data object

A reusable definition grouping fields for a business entity, such as Customer. A local table can store its records, but the definition is not itself a database table and may obtain records through an external service.

Data object vs. data type (Dev Studio)

The same constructs have different names by studio:

  • APP STUDIO terms: 'Data object' (the entity) and 'field' (an attribute)
  • DEV STUDIO terms: 'data type' (entity) and 'property' (attribute) — used interchangeably on projects

Draft data object

A placeholder created when you add a data object from the Case Life Cycle Designer without configuring fields or integration. Must be fully configured before use in production.

A data object is a labeled folder; the fields are the forms inside it. A Draft data object is an empty, labeled folder you drop into the workflow now and fill with forms (fields) and a filing system (integration) later.

Fields and Field Types

Field

A reusable UI component consisting of a NAME and a FIELD TYPE; each field stores one value associated with a Case. The Field Type determines the format/validation of the data and the input control presented to the user.

Choosing the right Field Type

Selecting the correct type (rather than Text for everything) enforces a common, valid format across all Case Types, reducing errors and streamlining the workflow.

The Field Type is the data's dress code: it dictates what a value may look like (a date, a currency amount, a yes/no) and how it is entered — so every Case Type collects it consistently.

Application Data Records

Data Record

A unique set of field values for one instance of a data object (e.g., one specific customer). Records are stored locally in Pega or retrieved from external systems.

Value change vs. structure change

Two types of data model changes with different implications:

  • VALUE change, such as updating an existing phone number, is generally routine data maintenance; assess any business-specific effects.
  • STRUCTURE change, such as adding a status field, changes the definition and may require process/schema updates; assess the actual impact.

pyGUID

Each locally-stored Data Record gets a pyGUID — an automatically-assigned unique identifier. The pyGUID is stored along with the Case so the record can be retrieved later.

If a data object is a spreadsheet's column headers, a Data Record is a single row of values. Editing a cell (value) is routine; adding a new column (field) reshapes the whole process.

Creating Data Relationships

Data relationship

A container that associates a set of related fields but does NOT store data itself. It relates data between a data object and a Case Type, between data objects, and between Case Types.

Embedded Data

Field type used when data is sourced from user input/action made DIRECTLY inside the Case instance (e.g., credit-card payment info entered each order). The data is stored WITH that specific Case instance and is only retrievable via that Case.

Data reference

Field type used when data is sourced from Data Records stored locally in the Pega database OR retrieved from an external system of record (e.g., a Customer maintained in an external SOR, or a product catalog).

Case reference

Field type used when data is sourced from a selected Case Type (e.g., choosing from a list of Service Cases).

Two dials, set independently: Dial 1 = SOURCE (Embedded = typed into the case; Data reference = from a SOR; Case reference = from another Case Type). Dial 2 = CARDINALITY (Single record vs. List of records). Every relationship sets both dials.

Accessing Data with Data Pages

Data Page

The bridge that retrieves data from a source and caches it for use. It decouples the Case from the underlying data source, supporting simulated data and refresh strategies.

Pega Live Data

The virtualization layer separating the application's business logic and data utilization from the technical details of how/when data is accessed. Data Pages are a key component of Pega Live Data.

Three default Data Pages per data object

The sourced App Studio data-object model describes three generated defaults: single read-only, list read-only and single read-and-write. This default set is not a limit on all custom Data Pages that an application may define.

Savable Data Page

Saves a page or page list back to its system of record (local or external), enabling real-time updates; governed by a data save plan configured by System Architects in Dev Studio (the BA helps choose the plan).

A Data Page retrieves and caches the configured records. A save plan can write changes back; the cache is not automatically fresh without an appropriate refresh strategy.
