Performing Calculated Values

Calculated value field

A calculated field derives its value from configured inputs using a function, expression or Decision table. Configure dependent inputs correctly; read-only presentation protects the derived value but is not a guarantee that the formula or source data is correct.

When the calculation runs

The calculation network can update dependent fields when an input changes. Functions support Sum/Average/Maximum/Minimum over numeric relationship items. Expressions support field references; the documented Simple Field Type exceptions are Email, Phone and Picklist.

A calculated field is a spreadsheet cell with a formula: you don't type the total, you type the inputs and the cell recomputes itself the moment any input changes.

Calculations with Decision Tables

Decision Table

In the sourced single-result calculation mode, evaluate rows in order and return the first match, or Otherwise. Dev Studio can also enable Evaluate all rows for multiple results; first-match is not every table’s universal contract.

When to use one for calculations

Use a Decision Table to compute a value that depends on combinations of conditions — for example a shipping cost by region and weight, or a discount tier by order total — instead of writing complex nested logic.

A Decision Table is a pricing chart on the wall: the clerk scans rows from the top and charges the rate from the first row your order matches — no hand calculation needed.

Setting Default Property Values

Default value

A starting value pre-populated into a field when a Case is created, so users don't have to enter commonly-used values (e.g., default Country = 'USA', default Date = today). This reduces Case processing time and improves consistency.

Business value

Defaults speed data entry, reduce errors, and standardize commonly-used values across Cases — improving efficiency and the user experience.

Default values are the pre-filled fields on a web form (country already set to your locale): you only change them when needed, saving time on the common case.

Manipulating Application Data with Data Transforms

Data Transform

A Data Transform assigns, copies, converts or calculates values when invoked. Configure the Run Data Transform step or pre/post-processing trigger; a one-time copy does not subscribe to later parent/source changes.

Common uses

Common Data Transform use cases:

  • Initialize/seed values on Case creation
  • Copy data from one Case or page to another (e.g., copy billing address to shipping address)
  • Apply explicit mapping at chosen triggers between related Case contexts; copying alone does not continuously synchronize them.

A Data Transform is a mail-merge macro: it takes values from one place and writes them consistently into others, so you never retype the same data twice.

Validation of Data (Business Logic Validation)

Business logic validation

Form business validation evaluates configured invalid-value conditions on submission: true raises an error. Stage validation blocks entry into the selected Stage when its invalid condition is true. Neither is a promise of continuous checking at every later use.

When validation helps

Use controls for format/required-value constraints and business validation for requirements the control cannot express. Define the invalid predicate, give actionable error text and provide a way to correct blocked Stage-entry data.

For a required value above 100, configure invalid as value <= 100. A validation error reports what must be corrected; its trigger/context must match the business requirement.
