UI Configuration in App Studio

Separation of Concerns

The software design principle the Pega UI layer applies:

  • Divide the application into distinct parts
  • Each with a single responsibility
  • So front-end components are decoupled from back-end APIs

UI elements: Views, templates, widgets

You author applications with Views, templates, and widgets. For new apps, Pega auto-generates a set of Views (built from Templates) so you can start configuring UI immediately.

Templates

Handle layout and responsiveness of a View — including breakpoints, white-space management, and wrapping — to ensure out-of-the-box accessibility. Each View type uses a different template; available templates vary by the type and location of the View.

Full Page View

Automatically added when a new Case Type or data object is created. Provides the three-pane framework — navigation, summary panel, and detail area — representing the overall workspace for a Case.

Summary panel

Displays the most critical Case information in the upper-left pane. Its content is configured by the architect and typically includes the Case's Primary Fields for quick-glance status.

Promoted Action

Gives quick access to a frequently used Action (e.g., Change Stage) as a button on the Case header — a default pattern requiring no button component. Each Case Type supports ONE promoted Action, and it is the first Case-wide Action.

Separation of Concerns is a well-run restaurant: the dining room (UI), the waitstaff (logic), and the kitchen (back-end APIs) each do one job and stay decoupled, so you can redecorate the dining room without touching the kitchen.

Data Capture in Views

View

A UI component that gathers data from a user OR displays data to the user, showing the fields and instructions for the current Task/Assignment. Views are reusable across applications with multiple Case Types.

Prescribed design system

A systemized collection of design rules, patterns, and UI component standards (Cosmos React) that ensures consistent look, feel, and accessibility across all Pega applications.

The four View types & editability

Full Page View (read-only), Partial (read-only), List (read-only by default; can enable editing), and Form (editable). View type determines whether users can enter data.

Views are like form letters in a template library: write one 'Customer details' View and reuse it across every Case Type that needs customer info — change it once, and every letter updates.

Forms in Pega Platform

View vs. Form

Related but distinct UI concepts:

  • VIEW — a reusable configuration of UI elements attached to a data source
  • FORM — an interface specifically for collecting data, with navigation controls (a type of View)

Where Form Views are configured

Two entry points: the Workflow tab (clicking Configure View on a Step auto-creates a Form View using the Default template), or the UX tab (manual creation, not auto-generated).

Layout

1–3 columns; two-column is best practice. Narrow inputs (Text single line, Currency) take one column; wider/any-height inputs (Rich Text Editor, Text area, Radio group, Checkbox, Booleans, Attachments) span two columns. This keeps tabbing left-to-right.

Field groups

A cluster of related fields under a single header (collapsible); fields can come from the Case Type Data Model or various data objects. Field groups are specific to that View only — NOT reusable in other Views.

Multi-step vs. Hierarchical Forms

Two Form types for complex data collection:

  • MULTI-STEP FORM — one Assignment across MULTIPLE Views (linear; default for Create Stage)
  • HIERARCHICAL FORM — a single View with expandable sub-Views (nested structure for complex data)

Adding Data Through a UI View

Add fields from a View

You can create portions of the Data Model while creating a View — adding new fields to the Case Type Data Model from the Configure/Edit View screen (e.g., adding an Account number field while configuring the Collect customer information View).

Adding a field from a View is like jotting a new line on a form mid-meeting: convenient, but the master template (Data Model) should really be designed first so the addition fits the bigger picture.

Designate Primary Fields

Primary Fields

Fields marked as Primary on the Data Model tab that appear automatically on the Create, Edit, and Details Views without additional configuration. Label and Description are Primary by default.

Default Primary Fields on Case Types

The Case Type Data Model automatically designates the Label and Description fields as Primary by default; removing the Primary designation removes them from the Details, Create, and Edit Views.

Primary Fields & Reference Fields (inheritance)

Adding a reference field to a Case Type inherits the referenced object's Primary Fields into the Case Type's Views automatically, without manual field-by-field mapping.

Primary Fields are the 'pinned' columns of a spreadsheet — the few you always want visible. Mark them once on the data object, and any Case that references it inherits those pinned columns automatically.
