Microjourney, Case Types, and Cases

Microjourney

The units of work that deliver a meaningful result to customers and users — a part of the overall customer journey. Each Microjourney is captured in App Studio as a Case Type.

The three pillars of an application

Every Microjourney in App Studio is built on three pillars:

  • (1) Case Types and Strategies
  • (2) Data and Interfaces
  • (3) Personas and Channels

Case Type vs. Case

Fundamental Pega terminology:

  • CASE TYPE — an ABSTRACT model of a repeatable business transaction (the template)
  • CASE — a SPECIFIC transaction instance; each submission creates a new Case with a unique ID and its own data and history

A Case Type is the cookie cutter; a Case is the individual cookie. The Microjourney is the recipe card describing how that batch of cookies gets baked from mix to plate.

Building Blocks: Stages, Processes, Steps

Stage

The top-level organization of work — a distinct phase or milestone in the Case Life Cycle. Stages organize the process into a sequential, logical collection of activities that drive toward resolution (e.g., an online order's Submission, Processing, Delivery).

Process

A series of Tasks/Steps within a Stage. Each Stage can contain one or more Processes; a Case can only move to the next Process after completing the Steps in the current one (e.g., Place Order, Process Order, Ship Items).

Step

Either a user action or an automated action within a Process. A Step requiring user action is a Task or Assignment; a Step performed by the system is an Automation Step (e.g., 'Enter customer details').

Stages are chapters, Processes are scenes within a chapter, and Steps are the individual lines of action — together they tell the story of the Case from start to resolution.

Stage Types and Components (Designing)

Create Stage

The FIRST Stage, denoted by a GREEN bar; it holds Processes/Steps to enter initial data on creation. It CANNOT be deleted or repositioned but CAN be renamed. Cases that include the Create Stage are assigned a Case ID upon creation.

Create Process

The default Process in the Create Stage. Non-Channel-specific Create Processes can only include Collect information Steps; Channel-specific ones may include Collect information and Automation Steps.

Primary Stages & primary path

Primary Stages lead to an expected outcome (most Cases go through them; they are part of usual processing and required for positive resolution). The path through the Case Life Cycle without deviating from Primary Stages is the PRIMARY PATH.

Alternate Stage

Handles DEVIATIONS from the primary path. Alternate Stages are OPTIONAL and either represent a negative Resolution Stage or are used for exception handling to allow the Case to re-enter the primary path.

Resolution Stage

Denoted by a RED bar; defines Case behavior at the END of the Life Cycle. Every Case Type should have AT LEAST ONE Resolution Stage, and can have more than one if you define alternate paths.

Color code for the exam: GREEN = Create Stage (start), RED = Resolution Stage (end). The primary path is the main highway; Alternate Stages are the detour ramps for exceptions.

Stage and Step Transitions

Stage transitions

Configured in the Stage contextual properties pane to control how a Case moves between Stages. You CANNOT configure Stage transitions on the Create Stage.

Change Stage Automation

A Change Stage Automation Step transitions the Case to a specific Stage automatically — most useful for automated transitions to and from Alternate Stages (e.g., return to Verification once rejected IT setup selections are modified).

Step transitions & Previous button

By default at run time, clicking Submit advances the Case to the next Step. Enabling the 'Allow users to go back to the previous Step' option in a Process displays the Previous button at run time.

Submit is the gas pedal (move forward); 'Allow go back to previous Step' adds a reverse gear (the Previous button). The Create Stage, though, has no transition controls — it's the fixed on-ramp.

Users, Personas, and Channels

Persona

Represents a category of people involved in your processes — the role a user plays and the access they need (e.g., Customer, CSR, Manager). Personas are one of the three pillars and are captured in App Studio.

Channel

The way users interact with a Case — for example a Web portal, mobile, or digital messaging. Personas and Channels together describe who participates and how.

A Persona is the role on the cast list; a Channel is the stage door they enter through (web, mobile, messaging). The same play (Case Type) can be reached through different doors.

User Guidance, Communication, and Benefits

User guidance

Instructions and help that keep users oriented while completing work — Step/Stage instructions, optional actions, and contextual guidance — so users know what to do at each Assignment to drive the Case to resolution.

Communicating with stakeholders

Pega keeps Case participants informed throughout the Life Cycle using features such as Pulse (post/view/reply to messages in Case context) and automated notifications (e.g., email) tied to Case events and status.

Case status & benefits

Case status communicates where a Case stands in its Life Cycle and supports automated notifications. Case Management with Pega delivers automation, consistency, visibility, and faster, more reliable resolution by modeling work the way users think about it.

Status + notifications are the flight tracker for a Case: participants always see the current 'gate' (status) and get alerts (notifications) when something changes.
