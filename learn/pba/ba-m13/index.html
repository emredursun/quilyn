Creating Case Relationships (Parent and Child Cases)

Parent and child Cases

Case relationships let you decompose complex business processes into focused, modular Case Types that work together. A parent Case orchestrates child Cases and waits on their completion.

Business value of child Cases

Child Cases break a large, complex workflow into smaller, manageable, reusable units that can run in PARALLEL, be owned by different teams, carry their own data/SLAs, and be reused across applications — reducing complexity and improving operational efficiency.

A parent Case is the general contractor; child Cases are the specialized subcontractors (plumbing, electrical) working in parallel. The contractor coordinates them and finishes once their work is done.

Managing Case Workflow Dependency (Wait Steps)

Wait Step

A Wait Step PAUSES a Case until a defined condition is met, which is how you manage dependencies between Cases (e.g., a parent waiting on its child Cases) or time-based pauses.

Two Wait types

(1) Case-dependency Wait — pauses until one or more specified Cases reach a particular status. (2) Timer Wait — pauses until a specific date and time is reached, then continues automatically.

A Wait Step is a relay handoff: the parent runner pauses at the line until the child runners finish their legs (case dependency) or until the official's clock hits a set time (timer), then continues.

Duplicate Case Search

Why detect duplicates

A user might create a Case with the same data values as an existing Case (e.g., same customer, request date, items). Identifying and resolving duplicates saves time and money, so it is important to know how Pega detects them.

Search duplicate Cases Step

Pega provides the Search duplicate Cases Process, implemented as a Search duplicate Cases Step. When a Case enters the Step, the system uses BASIC conditions and WEIGHTED conditions to compare specific property values against Cases already in the system.

Basic vs. weighted conditions & threshold

Two ways to configure duplicate Case search conditions:

  • BASIC — conditions MUST match (mandatory; all must be true)
  • WEIGHTED — each condition carries a numeric score; the SUM must reach a configured threshold (more flexible)

Resolving a duplicate

When a user decides the current Case is a duplicate, they resolve it with a Resolved-Duplicate status and processing ends; the flow can be customized to let the user open the original Case to make updates.

Duplicate detection is airport security: basic conditions are the mandatory ID check (must pass), and weighted conditions are points on a watchlist — once your points cross the threshold, you're pulled aside as a likely match.
