Where Module properties sit

Fix it once, not in every TestCase

A reusable Module stores control identification and supported steering configuration. Changes can affect tests that reference it, so validate the affected usages. Not every wait, focus, keyboard or transition behavior is a configurable Module property; some require TCPs, Modules or scenario-specific TestStepValues.

Independent maintainability guidance: put a stable reusable control rule in supported shared configuration, and keep scenario-specific actions and assertions explicit. Confirm the actual parameter’s supported level and platform before moving it.

Identification properties

Choosing what identifies the control

XScan identifies controls by properties by default. Make Unique can choose additional properties; you can also choose them manually or use another method. Validate that the selected values uniquely identify the target in expected languages, states and layouts.

A reproduction condition is evidence for investigation, not a guaranteed property diagnosis. Compare the current control tree and selected properties with the failing TestStep and logs.

Steering properties and realistic interaction

Why realistic matters on mobile

Use the supported interaction path and verify the required business outcome. If a scenario explicitly depends on focus, confirmation or another action, establish that it occurred; a final stored value alone may not demonstrate the required path. This is a local testing principle, not a claim that every native value-setting operation bypasses user behavior.

Native mobile automation does not support Tosca user simulations; the steering guide refers to SendKeys keyboard commands for native interactions. Do not imply that desktop simulation properties automatically apply to native mobile controls.
