Where Module properties sit

Fix it once, not in every TestCase

A Module describes a control: how to find it and how to interact with it. Every TestCase that steers that control inherits the description. So a property adjusted on the Module applies everywhere the control is used, while the same adjustment made inside a TestCase applies to that TestCase alone. When the same control misbehaves across several TestCases, the Module is the correct place to fix it, and fixing it in each TestCase instead is how a workaround gets copied twenty times.

A useful test for where a fix belongs: if the answer to 'why is this step configured this way' is a fact about the control, it belongs on the Module. If it is a fact about this particular scenario, it belongs in the TestCase.

Identification properties

Choosing what identifies the control

A scan captures several properties per control and selects some of them to identify it. That automatic selection is a starting point rather than a verdict. Properties that look stable in one scan can turn out to be dynamic in practice, such as text that is localised, an index that shifts when a list reorders, or a coordinate that moves with screen size. Editing which properties participate in identification is how a Module is made resilient without touching a single TestCase.

Each of those failures reproduces reliably under one specific condition and passes everywhere else, which is exactly why they are usually blamed on the environment rather than on identification. The condition under which a step fails is normally the clearest available evidence of which property is doing the identifying.

Steering properties and realistic interaction

Why realistic matters on mobile

A framework can often set a value directly on a control, which is fast and reliable and completely unlike what a user does. Mobile UIs frequently attach behaviour to the interaction itself rather than to the resulting value: validation that runs on blur, a picker that only commits on confirm, a list that lazy-loads as it scrolls, an animation that has to finish before the next control accepts input. Automation that sets values directly can bypass all of that, which produces a TestCase that passes while the user-facing flow is broken.

The general point: a test that passes by taking a shortcut the user cannot take has quietly stopped testing the thing you meant to test. Configuring interaction to resemble real use is not only about stability, it is about the result still meaning something.
