The Mobile Scan wizard

One wizard, three app types

The Mobile Scan handles native, hybrid, and web applications on mobile through the same wizard. The high-level sequence is always: prepare the test environment, start the Mobile Scan and connect to your device, then add the mobile device, emulator, or simulator you want to scan against. From there, scanning produces Modules the same way it does for any other Engine.

The Add connection dialog in this wizard is more forgiving about the TMAServer value than execution is — it will connect even without the trailing slash the TCP itself requires. Don't take a successful scan connection as proof the TCP value is correctly formatted for execution.

Configuring Capabilities

The wizard's three panes

The Mobile Scan dialog is organised into three panes that get filled in top to bottom: Select connection (Add connection, or a saved Local/Remote connection), Select device (filterable by Platform and OS Version, showing tiles for each device/simulator TMA currently sees), and Select application (Add app, or pick an app already scanned before, like a Tricentis-provided sample app).

Desired Capabilities

Below device/app selection, Set capabilities opens a Capabilities dialog where individual Appium Desired Capabilities can be added — each is an appium:-prefixed key and a value, the same capability mechanism any Appium-based automation session configures, just exposed through Tosca's UI instead of code.

Capability Sets — reusable, named bundles

Rather than re-entering the same capabilities on every scan, Add capability set saves a named group of Desired Capabilities (e.g. 'Close Permissions/Alerts') that can later be reapplied in one click via Select Capability Set — while Add capability still adds one-off, ungrouped entries to the current session.

A typical example: a Capability Set named 'Close Permissions/Alerts' bundling appium:autoGrantPermissions = true (auto-grants Android runtime permission prompts, e.g. camera/contacts/location access) and appium:autoAcceptAlerts = true (auto-accepts native alert/popup dialogs). Applying it before Connect means the scan or TestCase run isn't interrupted by an OS-level permission or alert dialog the automation never expected to see.

Scanning a native app

What gets captured

For a native app, each captured control is identified by native accessibility properties — resource-id (Android) or accessibility identifier (iOS), class/type, text/label, and position — the same properties a native Appium-based tool would report. Screens are typically organised into separate Modules mirroring the app's own screen structure.

Control identification quality depends heavily on how well the app under test exposes accessibility metadata. A poorly-labelled app (generic resource-ids, no accessibility labels) produces weaker, less stable identification — the mobile equivalent of a web page with no useful CSS selectors or test-ids.

Scanning a hybrid app

Native shell, embedded webview

A hybrid app wraps one or more web views inside a native shell. From the outside it looks and behaves like a native app, but part or all of its content is actually rendered as HTML/CSS/JS inside an embedded browser engine.

Context switching during scan

The Mobile Scan needs to know whether it's currently looking at native chrome (the shell's own tab bar, native buttons) or webview content (the embedded HTML). Switching context during scanning is what lets the same scan capture both native controls surrounding the webview and the DOM-based controls inside it, using the appropriate identification strategy for each.

Forgetting to switch context is the most common hybrid-scanning mistake: controls inside the webview simply don't appear to be scanned (because the scan is still in native context), which looks like a broken scan rather than a context problem.

Scanning mobile web

The device's own browser, scanned in its device context

For mobile web, the Mobile Scan opens the target site inside the device's own mobile browser rather than a desktop XBrowser session. This captures the page with the actual mobile viewport, mobile-specific rendering, and touch-driven interaction model — closer to how a real user on that device experiences the site than a desktop browser scan resized to a phone width would be.

Scanning mobile web through the Mobile Scan, instead of a resized desktop XBrowser scan, is the recommended approach specifically because it reflects genuine mobile browser behaviour rather than an approximation of it.
