Troubleshooting as its own skill

Why this deserves a dedicated part

Mobile automation setup spans several independent layers — the device/emulator, TMA, the network path between TMA and Tosca, and Tosca's own TCP configuration. A failure at any one layer can produce a symptom that looks like it belongs to a different layer entirely (the recurring theme across this whole course). Troubleshooting effectively means having a fixed order to check those layers in, rather than guessing based on where the error message points.

A layer-by-layer method

This order matters because each layer is cheap to verify in isolation and rules out an entire category of causes at once — checking TCP formatting before confirming the device itself is healthy wastes time second-guessing a config value that was never the problem.

Reading TMA's own logs

Why go past the console

The TMA console's device list gives a status summary; TMA's underlying logs give the actual detail behind a session that failed to start, including the raw driver-level (Appium/UiAutomator2/XCUITest) error that the Tosca-side error message often paraphrases or, as with the trailing-slash case, mischaracterizes entirely.

When a Tosca-side error message and a device-console Ready status disagree with each other, the raw TMA log is usually where the real story is — it sits closer to the actual failure than either the summarized console status or Tosca's own error text.

Session ID as the log's lookup key

Each session TMA creates carries a Session ID, and every log line produced by that session is tagged with it. A log file typically holds several runs one after another, so the Session ID is what lets you jump straight to the one execution under investigation instead of reading the whole file — it identifies a session in the log, nothing more; it isn't used to steer controls or edit TestCase data.
