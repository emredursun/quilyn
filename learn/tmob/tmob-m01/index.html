Why mobile automation traditionally hurts

The classic mobile toolchain

Automating a mobile app with raw Appium normally means: installing Appium and its Node.js dependencies, installing Java, wiring up platform-specific drivers (UiAutomator2 for Android, XCUITest for iOS), managing environment variables and PATH entries, and writing test scripts in a supported language. None of that is Tosca-specific — it is the general cost of mobile test automation before you write a single test.

TMA removes the toolchain, not the underlying engine

The Tricentis Mobile Agent (TMA) provides simplified setup and configuration of iOS and Android devices. You do not install Appium, Java components, or configure environment variables yourself — TMA bundles and manages that layer. Underneath, Mobile Engine 3.0 still drives sessions the same way Appium-based tools do (UiAutomator2 on Android, XCUITest on iOS); TMA is what hides that machinery behind a device list and a Start/Stop toggle.

Knowing that Appium sits underneath is useful for troubleshooting — error messages from a failed session sometimes surface raw Appium/driver text — but day-to-day authoring never requires touching Appium directly.

Two components, two jobs

Tricentis Mobile Agent (TMA)

A standalone application, installed separately from Tosca Commander, that manages device connectivity: it lists connected/available devices, emulators, and simulators, reports their status (Ready, Busy, Offline), starts and stops automation sessions, and exposes a REST API that both the TMA console and Tosca itself talk to.

Mobile Engine 3.0

The Engine inside Tosca that steers mobile applications through a TMA session. Once Modules exist, the TestCase-building workflow is the familiar Tosca one — Modules, TestSteps, TestStepValues, ActionModes — identical in shape to XBrowser or any other Engine. The mobile-specific work lives in the connection and scanning setup, not in how TestCases are structured.

Platform and app-type coverage

All three app types (native, hybrid, mobile web) are reached through the same Mobile Scan and the same Mobile Modules — the difference is in what gets captured during scanning, covered in the Mobile Scan lesson.

Local vs Remote — a first look

Local (TMA)

TMA runs on the same machine as Tosca Commander, connected to a device via USB or to a simulator/emulator on that same machine. This is the simplest topology and the one most learners start with.

Remote (TMA)

TMA runs on a different machine than Tosca Commander — for example a Mac running TMA for iOS work, connected to over the network from a Windows machine running Tosca Commander. Remote is also how shared device farms and CI environments are typically wired.

This is only an introduction — the full connection mechanics (TCPs, the TMAServer trailing-slash requirement, the --rest-address startup flag) are covered in depth in the Connecting Tosca to TMA lesson.
