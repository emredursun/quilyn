Test configuration parameters (TCPs)

The same TCP mechanism used elsewhere in Tosca

The connection to a device, emulator, or simulator is established through test configuration parameters — the identical mechanism used for the TestDataService endpoint, for SelfHealing, and elsewhere in Tosca. The same scoping rules (Project → Configuration → environment overrides) apply here too.

Static vs Dynamic device allocation

Static allocation

The DeviceName TCP is pinned to one specific device's identifier (a udid, or a specific emulator id). Every run always targets that exact device — the right choice whenever a test needs to run consistently on a specific device, e.g. verifying a bug that only reproduces on one particular phone model or OS version.

Dynamic allocation

DeviceName carries a wildcard rather than one fixed identifier, matching against criteria (e.g. any Android device meeting a Platform/OS filter) instead of a specific udid. TMA hands out whichever matching device is currently free. This favours throughput and parallelization across a device pool over consistency on one exact device.

Static vs Dynamic is a choice, not a fixed rule — pick Static when the test's whole point is a specific device, and Dynamic when the point is coverage/parallel execution across whichever devices are available.

The trailing-slash trap

The TMAServer TCP value MUST end with a trailing slash — http://<ip>:8585/ works, http://<ip>:8585 fails. Without the slash, execution fails with the misleading message 'Could not create TMA session: Ensure that the requested device is connected.' The cause: TMA's REST base path is /api, and Tosca concatenates that onto the TMAServer value — a missing slash produces a broken URL, and the request never even leaves Tosca.

What makes this trap so confusing: the Mobile Scan wizard's Add connection dialog tolerates the missing slash, so scanning works perfectly while TestCase execution fails on the exact same value. Seeing Scan succeed naturally leads you to rule out the connection string — and go looking everywhere except the one value that's actually wrong.

Local vs Remote, set up for real

Local (TMA)

Device/emulator/simulator on the same machine as TMA, and TMA on the same machine as Tosca Commander. TMAServer typically points at http://localhost:8585/ or http://127.0.0.1:8585/.

Remote (TMA)

TMA runs on a different machine than Tosca Commander — commonly used when Tosca Commander runs in a VM or on Windows but the device/emulator needs to be on a different physical machine (a Mac, for iOS; a native host, for an emulator a VM can't run).

Remote TMA must be started with the --rest-address flag: tricentis-mobile-agent start --rest-address <hostIP>:<port>. The tray/GUI launch does NOT enable it, even on a machine that's otherwise network-reachable.

Diagnosing device-side vs Tosca-side

Query TMA's REST API directly

A GET request to http://<TMA-host>:<port>/api/devices returns JSON describing every device TMA currently sees — udid, name, connected, busy, and statusReady fields. If that call shows connected:true and busy:false, the device side is proven healthy and the fault must be on Tosca's side — saving time that would otherwise go into chasing proxy, firewall, or network theories that don't apply.
