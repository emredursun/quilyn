Open Mobile App comes first, always

The mandatory first TestStep

Drag and drop the Open Mobile App Module onto the TestCase — and note the hard constraint: it must be the first TestStep of the TestCase. Nothing can be steered on the device until the application has been opened through this Module.

This mirrors a recurring pattern across Tosca's Engine 3.0 family: engines that attach to an external resource require an explicit open step before anything else in the TestCase — the same shape as TBox Open Excel Workbook for the Excel Engine.

What Open Mobile App actually does

It's more than a click-through step: Open Mobile App creates the mobile device session (via TMA) for the TestCase, and it can install the app on the device at the start of that session if an install source (a local .apk path, or the equivalent iOS install path) is configured — or, for an app already on the device, open it directly by its identifier: BundleID for iOS, or AppPackage/AppActivity for Android.

Switch Mobile App

For TestCases that move between apps mid-flow (e.g. testing a deep link handoff, or a share-sheet interaction that opens a different app), Switch Mobile App changes the active app context without needing a second Open Mobile App step.

Gestures: when there's no control to click

Coordinate-based gestures are a fallback, not a first choice — they're brittle across different screen sizes and resolutions. Prefer steering a scanned control whenever one exists; reach for On Screen Modules only when no addressable control is available.

Text entry and the keyboard

Send Text Input To Focused Control

Enters text into whichever control currently has focus — typically used right after tapping a text field, mirroring how a real user would tap then type.

Set Autohide Keyboard

Controls whether the on-screen keyboard automatically dismisses after a text-entry step. Leaving the keyboard open when the next TestStep expects to interact with an element it's now covering is a common source of flaky steps — this setting exists specifically to manage that.

Running with LiveView

Watching execution happen

With the LiveView TCP set to True, executing a mobile TestCase shows the device's screen updating in near-real-time inside Tosca — genuinely useful while a TestCase is still being built and debugged, since a failed TestStep can be visually correlated with exactly what the device was showing at that moment.

LiveView adds overhead to execution. It's worth leaving on while authoring and debugging, and worth considering turning off for large batch/CI runs where nobody is watching.
