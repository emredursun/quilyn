What a capability actually is

Session-level configuration, not TestCase logic

Desired Capabilities are passed when the automation session is created, so they configure the session rather than any individual step. Two consequences follow. A capability applies to everything in that session, and changing one means the session has to be recreated. This is why capabilities belong in configuration rather than being toggled mid-flow, and why a Capability Set is a sensible unit to name and reuse.

Tosca exposes these through the Capabilities dialog rather than in code, but they are the standard Appium capabilities underneath, which is why the appium: prefix appears and why Appium's own documentation is the reference when a capability behaves unexpectedly.

Grouping them by what they control

Why grouping helps

Capability lists are long and mostly irrelevant to any given project, so memorising them is wasted effort. Knowing which group a problem falls into is what makes the list navigable: a run interrupted by a popup, a TestCase polluted by leftover state, a session dying during a long wait, and text landing in the wrong place are four different categories, and each has its own small set of candidates.

The cost nobody mentions

Every capability that suppresses something also removes it from view. Auto-accepting alerts stabilises a run and simultaneously means the run can no longer report whether an alert appeared, what it said, or whether a new one showed up after a build. Auto-granting permissions has the same shape: the permission flow stops being exercised at all, so a regression in it cannot be caught by any test using that capability.

Suppress broadly, verify deliberately

The workable position is not to avoid these capabilities, because runs that stall on OS dialogs are worse. It is to accept that suppression is the default for the bulk of the suite while keeping at least one TestCase that deliberately does not suppress, so the dialog behaviour itself stays under test somewhere.

This is the same reasoning as the earlier point about realistic interaction. A configuration that makes tests pass more often is only an improvement if the passes still mean what you think they mean.

Capability Sets versus one-off entries

Naming a bundle you will reuse

A Capability Set groups several capabilities under a name, such as a Close Permissions/Alerts set holding autoGrantPermissions and autoAcceptAlerts, and applies them in one action. A single Add capability entry configures one value for the session at hand. The distinction is reuse: anything the whole suite needs belongs in a named set, while something genuinely specific to one scenario does not.

Watch for one-off capability entries that quietly become load-bearing. A value added to make a single TestCase work, then copied into the next one and the one after, is a Capability Set that never got named. The copies then drift, and the resulting differences are invisible because nothing displays them side by side.
