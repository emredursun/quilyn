One workflow, three targets

What stays the same across all three

Regardless of app type, every mobile TestCase starts with Open Mobile App, steers scanned Modules with the same TestStepValue/ActionMode mechanics as any other Tosca TestCase, and verifies outcomes with the same Buffer/Verify actions. The Getting Started course covered this shape once (Lesson 7); this part is about applying it three times, deliberately, against each app type's specific quirks.

What actually changes

Native: control identification relies purely on platform accessibility properties. Hybrid: the TestCase must explicitly manage native/webview context switches mid-flow. Web: steering happens inside the device browser's DOM, closer to an XBrowser TestCase in spirit but running through the Mobile Engine.

Building a native TestCase

Native is the most predictable of the three to author against, precisely because control identification and steering match what was covered in the Getting Started course's Mobile Scan and TestCase lessons directly — this part is mostly about applying that discipline consistently across a longer, realistic flow rather than a single toy TestStep.

Building a hybrid TestCase

Context switches belong in the TestCase, not just the scan

A hybrid TestCase needs the same native/webview context switching used during scanning to also happen during execution, at the right points in the TestStep sequence — steer the native shell's tab bar, switch to webview context to steer the embedded content, switch back to native context to steer whatever surrounds it next.

A hybrid TestCase authored entirely in whatever context the scan happened to be in when each control was captured will silently fail on controls captured in the 'wrong' context relative to where the TestCase actually needs to be at that point in the flow. Explicit context-switch TestSteps at each transition avoid this.

Timing matters more in hybrid than native: the embedded webview can take noticeably longer to finish loading than the native shell around it. A control steered before the webview has finished rendering behaves like a control that doesn't exist yet — build in a wait or a Verify-for-presence step before steering into freshly-loaded webview content.

Building a mobile web TestCase

DOM steering through the Mobile Engine

Once scanned through the device's own browser, a mobile web TestCase steers controls the way a DOM-based Module normally would — but every interaction still runs through the same device session and Mobile Engine plumbing as a native or hybrid TestCase, not a separate execution path.
