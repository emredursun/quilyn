One workflow, three targets

What stays the same across all three

Native, hybrid and mobile web tests share Tosca’s Module/TestStepValue and supported ActionMode concepts. Opening differs: native/hybrid apps use Open Mobile App after any required capability setup; websites use OpenUrl. Buffer stores data; Verify performs assertions.

What actually changes

Native controls use exposed platform properties. Hybrid flows combine native and web content with the appropriate context. Mobile web scanning/execution defaults to Mobile Web Engine 3.0, with version-specific legacy alternatives; it is not one identical engine path for every app type.

Building a native TestCase

Treat this sequence as independent local authoring guidance. Reliability depends on the application, identifiers, synchronization and assertions rather than an assumed reliability ranking between application types.

Building a hybrid TestCase

Context switches belong in the TestCase, not just the scan

Use Get Appium Context and Set Appium Context when the execution flow needs native/web context changes. Confirm the actual current and target contexts rather than assuming each scanned control automatically switches execution context.

A context mismatch can prevent correct steering. Inspect the active context and errors before diagnosing the failure; neither a captured context nor an explicit switch guarantees every control operation succeeds.

Synchronize against observable readiness such as an enabled target before interacting with newly loaded content. WaitOn can wait for a property condition; a one-time Verify or buffering operation alone is not a substitute for waiting.

Building a mobile web TestCase

DOM steering through the Mobile Engine

Use OpenUrl and the relevant Browser TCP for a mobile website. Tosca 2026.1 defaults mobile web scanning/execution to Mobile Web Engine 3.0; native and embedded web content have their respective engine/context behavior.
