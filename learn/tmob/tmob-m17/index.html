Beyond the local machine

Where this part picks up

Everything up to this point runs one TestCase, from one Tosca Commander, against one TMA and one device. The advanced use cases are about what changes when that stops being true: many executions across many agents (Tosca Distributed Execution), or execution owned by a hosted platform instead of a workstation (Tosca Cloud).

Tosca Distributed Execution (DEX)

TestEvents and ExecutionList configurations

Distributed Execution does not work by hand-picking which TestCase goes to which machine. Executions are managed through TestEvents together with ExecutionList configurations — the TestEvent defines what should run, and the ExecutionList configuration defines how, while agents pick the work up from there. Assignment is configuration-driven, not manual.

The mental shift is from 'I press Run here' to 'I declare what should run, and the infrastructure resolves who runs it' — the same shift dynamic device allocation makes at the device level.

Tosca Cloud

Uploading an ExecutionList

Tosca Commander can upload TestCases in bulk, and entire ExecutionLists, to Tosca Cloud. An uploaded ExecutionList becomes a Tosca Cloud playlist — playlists are Cloud's own execution unit, managed under Run → Playlists. The ExecutionList is not deleted, not restricted to local machines, and does not block other executions; it is converted into the equivalent Cloud object.

Upload mode settings let Tosca upload only objects changed since the previous upload, which matters once uploads are routine rather than one-off migrations.

What this means for mobile specifically

Distribution raises the stakes on device configuration

Once executions are distributed or cloud-triggered, nobody is watching a LiveView window when something goes wrong. A TestCase pinned to one static device blocks every other run needing that device, and a TestCase carrying device-specific assumptions fails unpredictably across a pool. Dynamic device allocation and disciplined capability filters stop being conveniences and become prerequisites.

Diagnostics get harder in exactly the same proportion: the local console you would have read is gone, so TMA's own logs and the Session ID become the primary way to reconstruct what a distributed run actually did.
