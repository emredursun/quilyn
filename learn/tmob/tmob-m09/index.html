From virtual-device creation to automation validation

From 'an emulator exists' to 'TMA can drive it'

A virtual device has separate configuration, boot, discovery and automation checks. Seeing its screen does not prove that the Agent can create a session or launch the test application.

This is an independent local setup guide based on accessible product documentation. The original Academy recording and its exact exercise sequence were not available for comparison.

Creating the AVD deliberately

Picking the system image on purpose

Choose an image that supports the application’s minimum SDK and required libraries, the intended coverage target and the Agent’s supported OS range. An emulator image is not evidence of identical physical-device behavior.

Google documents matching image/host architecture for VM acceleration: x86/x86_64 on x86_64 hosts and arm64-v8a on ARM64 hosts. Do not assume an incompatible image will launch successfully through translation or infer rendering glitches from architecture alone.

Integrating the AVD with TMA

If the Agent does not detect the emulator, inspect adb detection, supported versions and Agent logs. A required universal AVD-before-Agent startup order is not established by these guides.

Wiring DeviceName to the AVD

Tosca’s device table specifies the displayed full emulator name for an Android emulator; other connection cases use reported device IDs. Use the value required by the actual connection and verify it with a minimal test. Do not interchange the AVD profile name and adb serial blindly.
