Why this course goes deeper on AVD setup

From 'an emulator exists' to 'TMA can drive it'

The Getting Started course covers creating an AVD as one step among many. This course treats AVD creation and TMA integration as their own dedicated part — because in practice, a surprising share of 'automation isn't working' reports trace back to an AVD that boots and looks fine but was never actually wired up correctly for TMA to use.

Official course description: this interactive course equips you to automate mobile testing using Tricentis Tosca. It starts with setting up an Android Virtual Device (AVD) in Android Studio to establish a solid mobile testing environment, then covers creating and running tests for native, hybrid, and web applications, and troubleshooting common mobile automation issues.

Creating the AVD deliberately

Picking the system image on purpose

The API level chosen here determines which Android behaviours the AVD exhibits — permission dialog styles, Developer Mode specifics, security defaults. Matching the system image to whatever real-world Android version the app under test actually targets (or needs to be verified against) avoids automating against a device that behaves differently from production.

ABI mismatches are a common source of a slow or crashing emulator: an x86_64 image on Apple Silicon (or vice versa) runs, technically, through translation — but noticeably slower, and occasionally with subtle rendering glitches. Match the system image's ABI to the host CPU architecture.

Integrating the AVD with TMA

An AVD that's visibly running in the Android Studio emulator window does not guarantee TMA sees it. If it's missing from the TMA console's device list, the emulator process may have started after TMA, or TMA may need a restart to re-scan — check the device list again after both are confirmed running, in that order (AVD first, TMA started or refreshed after).

Wiring DeviceName to the AVD

Once the AVD shows Ready with its emulator-#### identifier, that exact string is what goes into the DeviceName TCP for a static, pinned connection to this specific AVD instance. The identifier is tied to the running emulator process — if the AVD is closed and relaunched, it is not guaranteed to receive the same port/identifier.
