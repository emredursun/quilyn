From the concept to the configuration

Where this picks up

The Getting Started course introduced Static vs Dynamic device allocation as a concept — pin one device, or let TMA hand out any matching one. This part is about actually configuring the dynamic side: the wildcard syntax, the criteria that matter, and what changes operationally once a TestCase no longer targets one specific device.

Configuring the wildcard

DeviceName as a criterion, not an identifier

Instead of a specific udid or emulator-#### value, the DeviceName TCP is set to the literal wildcard TOSCA_DYNAMIC_DEVICE_SELECTION. TMA resolves that wildcard against its currently-known device pool at connection time — handing out whichever Ready, non-Busy device satisfies the remaining criteria (Platform, OS Version, device type).

A wildcard that's too broad (matching every device in a mixed Android/iOS pool, for instance) risks a TestCase landing on a platform it was never actually written for. Scope the criteria as tightly as the TestCase's real requirements — broad only where the TestCase is genuinely platform/version-agnostic.

How TMA resolves a dynamic match

Resolution at connection time

When a TestCase with a dynamic DeviceName connects, TMA evaluates the pool of devices it currently sees, filters to those matching the criteria, and hands out one that's Ready and not Busy. Which specific device gets picked is not something a TestCase controls or should assume — the same TestCase run twice in a row can legitimately land on two different physical devices.

Because the specific device is not guaranteed, any assumption baked into a TestCase about a particular device's exact screen resolution, installed apps, or prior state will not hold reliably under dynamic allocation. Dynamic allocation trades device-specific certainty for pool availability — TestCases relying on device-specific quirks belong on static allocation instead.

Failure modes specific to dynamic allocation

Ensuring 'successful test execution' with dynamic allocation is less about any single TCP value and more about pool sizing and criteria discipline: enough matching devices in the pool for expected parallel load, and criteria narrow enough that a resolved device genuinely satisfies what the TestCase needs.
