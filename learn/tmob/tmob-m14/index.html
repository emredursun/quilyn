Two jobs, one mechanism

Connection TCPs versus tuning TCPs

The earlier courses used TCPs to answer a single question: which agent and which device. TMAServer, DeviceName, Type. Those are connection parameters, and a wrong value there means nothing runs at all. This course adds a second category: parameters that assume the connection already works and instead shape how the run behaves. A wrong value there does not stop the run. It makes it slower, less stable, or less informative, which is considerably harder to notice.

That difference in failure mode is worth holding onto. Connection TCPs fail loudly and immediately. Tuning TCPs fail quietly and gradually, usually showing up as flakiness that gets blamed on the application.

Parameters that shape a run

Reset application and test independence

Skipping the reset is tempting because it makes a run start faster, and it works fine while you are executing one TestCase at a time by hand. It stops working the moment TestCases run in sequence or in parallel, because each one inherits state from whatever ran before it. The symptom is a TestCase that passes alone and fails in a suite, which is one of the most time-consuming failure patterns to diagnose.

Scoping, and why it starts mattering here

The same TestCase, several environments

TCPs follow Tosca's normal scoping rules, so a value set at Project level can be overridden by a Configuration and again per environment. While everything runs on one local emulator, this is invisible. It becomes the central mechanism the moment the same TestCases have to run against a local emulator during development and a shared device pool in CI, because only the configuration should differ between those two, never the TestCases.

The anti-pattern to avoid: duplicating a TestCase so one copy points at the local emulator and another at the shared pool. Two copies drift. Keep one TestCase and let the configuration carry the difference, which is exactly what the TCP scoping hierarchy exists for.
