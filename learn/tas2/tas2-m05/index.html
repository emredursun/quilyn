Why Conditions Are Needed

Conditional instantiation controls which model elements are generated for each data combination. It is different from evaluating an IF or WHILE against the live SUT at execution. Supported conditional targets include the Template, TemplateInstance, TestStep folders, TestSteps/XTestSteps and XTestStepValues. Use the narrowest intended scope. Later condition edits require regeneration of existing cases.

Setting a Condition

Add Condition through Column Chooser or edit the property. Link the Template to its data source first. Dragging an ordinary Instance into a Condition creates an equality comparison; inspect the generated expression. Attribute conditions default to a non-null check, with special handling for NULL and EMPTY Instances. Use == for equality and != for inequality; && combines required clauses and || accepts either clause. Do not rely on an assumed default OR. Quoted strings and valid source paths matter. A != exclusion also accepts other unexpected values, so use it only when the intended domain makes that safe. Numeric comparison should use the documented numeric syntax or conversion. Dotted icon outlines indicate condition-based instantiation.

After Setting Conditions

Run Check Template, inspect the selected instance source and manual changes, then regenerate. Inspect which cases and steps were actually generated and trial-run meaningful valid/negative paths. Generation and schema checking alone do not certify a complete working test set.

Independent Practice: Conditional Payment Paths

Independent practice: synthetic payment data includes a controlled non-null domain of Visa, MasterCard and No Credit Card used. Compare a deliberate exclusion with an explicit allowed-value condition, inspect generated subsets and their assertions. Original Academy payment exercise material was inaccessible and remains unverified.
