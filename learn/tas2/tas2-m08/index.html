Where API TestCases Come From

Scenario: test that countries and country IDs are combined correctly by the system. You're given a subset directly from the developer and a TestSheet from the Test Design Specialist, and need to build the TestCases for this new DemoWebShop functionality.

API Scan

Tosca can scan an application's API to collect relevant Request/Response pairs and export them as a raw TestCase. In this course, developers already performed the scan for you. The exported raw TestCase needs adjusting: TestSteps must be renamed and polished, following a clear, consistent structure and naming convention so anyone can follow the flow. The final structure should resemble a UI TestCase — easier to understand and to automate.

Want to go deeper into API Scanning itself? See the dedicated "Automation Specialist for API" course.

The One Key Difference from UI TestCases

Like ordering at a restaurant — you can't receive food without placing an order first, and an order is pointless without a response (your food) coming back.

In API TestCases, every Message that performs a function must be expressed as a Request + Response TestStep PAIR. A Request without a Response (or vice versa) is incomplete and must be fixed before proceeding.

Building the API Template (Same Flow as UI)

Besides the Request/Response pairing requirement, the entire Template workflow (linking, Conditions, Check Template, Instantiate) is IDENTICAL to UI test automation — nothing new to learn mechanically, just a different kind of TestStep.

Exercise 8a: Build the API TestCase

Scenario: some DemoWebShop products recently had their SKU changed. Since the SKU isn't visible on the UI, you need an API TestCase — "Verify Product by SKU" — to check that BlueJeans still has the expected SKU/ID, using the API Scan subset the developers provided.

{CP[...]} — Common/Configuration Parameter

{CP[Email]} and {CP[Password]} reference reusable, project-wide Configuration Parameters (e.g. login credentials) — not a TestSheet. They can be dropped into any TestStepValue directly, independent of Attribute/Instance linking, which is why they show up here before any TestSheet is even linked in 8a.

Use the correct ActionMode for each direction: request values (sku, usernameOrEmail, userPassword) use Insert; Response values you're checking (Id, Name) use Verify. Mixing these up is the most common mistake in this exercise.

Exercise 8b: Convert to Template, Link Values, Instantiate

Before dragging and dropping Values from the TestSheet onto the Template, delete the existing Values in the TestStepValues first — same rule as everywhere else in this course: Tosca appends the new XL reference instead of replacing an existing value.
