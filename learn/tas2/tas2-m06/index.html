From Templates to Execution

As covered in AS1, we use ExecutionLists and RequirementSets to run tests and get a project-level overview. Here we build an ExecutionList for the Template-generated TestCases from this course, so results and any bugs get reported properly.

ExecutionLists always live inside an ExecutionList Folder. You can't create one directly at the Execution root — first create an ExecutionList Folder under the root Execution folder, then create the ExecutionList inside that folder.

Key Icons: Set vs. Individual

TemplateInstances Folder

The auto-generated folder holding every TestCase a Template produced. Shown as a teal/cyan folder icon with a capital "I". This is the object you drag as a whole — onto a Requirement and onto an ExecutionList — never individual TestCases from inside it.

RequirementSet vs. Requirement

A RequirementSet is a hollow/outline orange triangle — a container that groups related Requirements (e.g. "WebShop Frontend"). An individual Requirement is a solid/filled orange triangle (e.g. "Log in", under Customer tasks). They look similar at a glance, but only the filled triangle is the correct drop target for linking TemplateInstances at requirement level.

ExecutionLists icon

A green arrow/chevron icon, visually distinct from the TemplateInstances and Requirement icons — makes the Execution section easy to spot in the Navigation pane.

Linking TemplateInstances (Best Practice)

Drag and drop the WHOLE TemplateInstance folder onto the ExecutionList — not individual TestCases. If the folder itself is linked, it's much easier to synchronize when the Template later changes: synchronization is manually triggered from the ExecutionList ribbon, and every ExecutionList linked to that folder updates automatically.

Reading the Results

ExecutionState and CoverageSpecified are NOT columns in the Execution section — they appear on the RequirementSet/Requirement once the ExecutionList has been linked to it, i.e. in the Requirements section.

Column (Requirements section)What it shows
ExecutionStateResult of executed TestCases, factoring in risk, leading to a risk-based coverage statement.
CoverageSpecifiedWhat percentage of the overall project risk has been covered.

These two columns feed directly into status reports/dashboards, giving developers exact information about which step failed and what the error message was.
