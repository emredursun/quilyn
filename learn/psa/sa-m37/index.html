Data Transforms and Default Values in Dev Studio

A sorting machine on a factory line — it doesn't just move boxes from A to B. It can flip them, relabel them, or only pass through boxes over a certain weight. Data Transforms in Dev Studio work similarly: they initialize, manipulate, map, and transform data — including iterating over lists and applying conditional logic.

Calling a Data Transform from a flow

Open a Process in Dev Studio → click the Connector between Steps → Connector properties window → Set properties section → select 'Apply Data Transform'. This fires the Data Transform at that specific transition point in the flow.

Iterating over a page list — auto repair example

Data Transforms can iterate a page list with conditional logic. Example: iterate repair items and copy only entries where quantity > 0 to the parent Case for invoicing. Shows that Data Transforms can filter and iterate — not just copy/convert.

Expressions in Data Transforms — @CurrentDateTime()

Use @CurrentDateTime() in pyDefault to set a date field to the moment the Case is created. Example: .DateOfTravel = @CurrentDateTime() → sets travel date to right now.

Expressions in Data Transforms — @addCalendar()

Use @addCalendar() to calculate a date offset. Example: .DateOfReturn = @addCalendar(.DateOfTravel, '0','0','0','7','0','0','0') → sets return date to 7 days after travel date.

pyDefault and pySetFieldDefaults in App Explorer

Both are accessible via the App Explorer in Dev Studio. Best practice: use the Data initialization page (Settings tab) for simple defaults — it updates pyDefault. For complex defaults, edit pyDefault directly. Never modify pySetFieldDefaults — system-managed.

Pages & Classes tab — required for Data Page references

To reference a Data Page (e.g., OperatorID) in a Data Transform, add it to the Pages & Classes tab first. Example: .FirstName set to pyFirstName from OperatorID — OperatorID must be registered in Pages & Classes.

Superclass Feature for Data Transforms

A company org chart inheritance — the CEO sets company-wide policies, the VP adds division rules, the manager adds team rules. Each level adds its own defaults; they don't conflict because they cover different fields. The superclass feature works the same way across the class hierarchy.

Superclass feature — purpose

Makes Data Transforms modular and maintainable by combining same-named Data Transforms at different class hierarchy levels. Each level sets defaults appropriate to its scope. Common defaults live high in the hierarchy; specific ones live low.

Superclass — runtime execution order

At runtime, Pega walks UP the hierarchy to find the highest parent, then invokes Data Transforms TOP-DOWN (highest parent first → current class last). Example: Claim → Home → Rental: Claim SetDefault runs first, then Home, then Rental.

Subclass overrides parent for conflicting properties

If the same property is set in both parent and subclass, the subclass value wins — it runs last and overwrites. Non-conflicting properties from all levels accumulate. So superclass is additive except where both levels set the same field.

Claim → Home → Rental example

Data Transform inheritance in a child Case hierarchy:

  • Claim SetDefault: sets Date of loss + Prefix (Case ID prefix)
  • Home SetDefault: inherits from Claim + adds Address
  • Rental SetDefault: inherits from Home + adds Name on lease

Configuration — how to enable

In Dev Studio: create a Data Transform with the SAME NAME at each class level → check 'Call superclass Data Transform' on each. Auto-enabled when App Studio creates default fields for a Case Type.

Work- pyDefault — what it sets

Pega ships pyDefault in the Work- class. It sets work status, Urgency (default = 10), and operator organization info. All Case Types inherit it. Override in your Case Type class to change defaults.
