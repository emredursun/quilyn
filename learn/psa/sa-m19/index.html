Roles on a Pega project

Delivery roles: PO, Project Manager, Scrum Master

Three delivery management roles:

  • PRODUCT OWNER — manages scope and prioritizes sprint requirements
  • PROJECT MANAGER — leads delivery, maintains governance, liaises with client leadership
  • SCRUM MASTER — runs Sprint ceremonies (Planning, Sizing, Backlog Refinement, Retrospectives) and removes impediments

Developing a Pega application as a team is like building a house with specialists working simultaneously: the architect draws plans (SA), the electrician wires rooms while the plumber installs pipes (parallel development), and each team works from a locked blueprint version (Ruleset version). Without the version lock, one team could accidentally overwrite another's work.

Build & quality roles: SA/SSA/LSA, QA, BA

Three build and quality assurance roles:

  • SYSTEM ARCHITECTS (SA/SSA/LSA) — configure the application; LSA imports Blueprint files
  • QUALITY ANALYSTS — verify requirements and write test scripts
  • BUSINESS ARCHITECT — translates business needs into workflows, Data Models, and user experiences

Client & design roles: SME, UX, Solutions Consultant

Three client-side and design roles:

  • SUBJECT MATTER EXPERT — client operational expert who supplies requirements
  • UX DESIGNER — ensures design meets user needs and accessibility standards
  • SOLUTIONS CONSULTANT — engages client in sales, co-designs Blueprint, hands off to delivery team

Roles and studios

Each studio serves a different set of roles:

  • APP STUDIO (no-code) — SAs, BAs, UX designers, solutions consultants, Project Managers, Scrum Masters
  • DEV STUDIO (advanced) — System Architects and Quality Analysts
  • PREDICTION STUDIO — data scientists
  • ADMIN STUDIO — business IT for system administration

Parallel development: Workspaces and Branches

Workspace → Branch → Application

Three parallel development scopes (changes promote outward):

  • WORKSPACE — one developer's PRIVATE changes, isolated until shared
  • BRANCH — the TEAM's active changes in progress
  • APPLICATION — GENERALLY AVAILABLE features (the shared, production-ready Ruleset)

Workspaces

Private development space tied to one operator and one application. Changes stay isolated until shared to a Branch — avoiding rule conflicts. Each operator gets one Workspace by default; multiple are allowed. Enabled via the EnableWorkspace setting.

Branches and Branch Rulesets

A BRANCH is a container of Rulesets under active development. Branch Rulesets are based on (branched from) another Ruleset. Best practice: one Branch per feature so teams work in isolation — a finished feature merges independently.

Merging into the main application

A Branch merges into the main application only after the feature is complete, conflicts are resolved, and approval is granted. Pega automatically checks which Rules are new or updated before completing the merge.

Branch quality metrics

Guardrails

Settings that flag elements not complying with Pega best practices. You must respond to warnings to keep the application efficient. The WEIGHTED SCORE metric reflects the number and severity of guardrail warnings on a Branch.

The four Branch quality metrics

Four metrics tracked per Branch before merging:

  • (1) GUARDRAILS — weighted compliance score
  • (2) MERGE CONFLICTS — total unresolved conflicts
  • (3) TEST COVERAGE & UNIT TESTS — rules covered % and pass rate %
  • (4) UNCOVERED RULES — Branch Rules not covered by any test
