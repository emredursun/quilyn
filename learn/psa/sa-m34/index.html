Data Validation — Overview

Why validate data?

Validation helps reject inappropriate input before dependent processing. A valid input is necessary, but not a guarantee that every later processing step is error-free. Three requirements:

  • (1) correct TYPE (e.g., number in 'Total units')
  • (2) restricted to POSSIBLE VALUES (e.g., valid loan type from a list)
  • (3) meets BUSINESS CONSTRAINTS (e.g., a historical employment start date is in the past)

Field Type/control vs. Business logic validation

Two layers of data validation:

  • FIELD TYPE/CONTROL — handles FORMAT validation (e.g., a calendar ensures a valid date format)
  • BUSINESS LOGIC — handles BUSINESS RULE validation (e.g., 'start date cannot be in the past')

Think of Field Type validation as a passport scanner — it checks that the document is a valid passport format. Business logic validation is the customs officer — they check whether you're actually allowed to enter (right age, valid visa, not on a watchlist). Format ≠ business validity.

Validation on a Form vs. Validation on a Stage

Validation on a FORM

Triggered when the user submits the form. If invalid, an error displays inline and submission is blocked until corrected. Use when the user CAN immediately fix the issue (e.g., entered a future date → correct it and resubmit).

Validation on a STAGE

Evaluated before entry into the specified Stage. An invalid value prevents entry and displays an error. Configure a way to correct the data or take another action, such as returning to earlier work or closing the Case; a corrective path is not supplied automatically.

Configuring business logic validation in App Studio

App Studio supports form-submit validation and Stage-entry validation. The condition describes an invalid value; meeting it displays an error. Stage validation is configured in the Case Type Data Model. A field used on several forms can have different validation conditions at each use; reusing it later does not automatically repeat an earlier check.

Same field, different business contexts

An employment-history form can require a past start date while a new-hire form requires a future date. Configure the relevant condition for each use of the field; one historical validation is not a global invariant for every later use.
