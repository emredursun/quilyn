Decision Tables in Dev Studio

Decision table

A Decision table maps tested conditions to outcomes. Each column uses its property/operator pair across rows; different columns may test different fields. The topic’s App Studio calculated-field procedure creates a Decision Table Rule in Work-, not a universal storage rule for all tables.

Compare a grid of combinations with nested questions. A table can put several input fields in columns and combinations in rows. A tree follows conditional branches, with later questions depending on earlier ones. Either may express similar logic, but choose a readable structure supported by the consuming configuration.

Decision logic maintenance (Delegation)

A suitably authorized Process owner can maintain a delegated table. The Results tab’s Delegation options control which editing capabilities are available, such as adding rows or columns. Those options are not by themselves a grant of user access or the entire delegation setup.

Evaluate all rows

Without Evaluate all rows, processing stops at the first matching row. Enabling it checks every row; only matching rows perform their configured actions and return calculations. Consumers such as an authority matrix can collect multiple successful results; checking rows does not make every row match.

Direct flow processing with Decision tables

Add a Decision shape in a flow pointing to a Decision Table. Each result value maps to a flow connector, directing the Case to a different path — keeping branching logic out of the flow diagram.

Decision Trees

Decision tree

Handles logic that returns a result from test Conditions. Each branch evaluates a property/operator pair against a single value; a true comparison can lead to nested branches. Decision trees can test DIFFERENT properties and operators across branches.

Condition branches and nesting

A branch combines a comparison and an action: return a result, continue or stop evaluation. A matching parent can lead to child comparisons. Otherwise supplies the fallback when evaluation does not return a result.

Where Decision trees can be referenced

Choosing: Decision Tree vs. Decision Table

When to use a Decision table

Prefer a table for many combinations of the same set of properties. A column uses a consistent property/operator pair; other columns can use other inputs. The table is not restricted to one field.

When to use a Decision tree

Prefer a tree when branch-specific questions depend on prior conditions. Different branches may use different inputs or operators. This is a structural preference, not proof that any multi-field decision requires a tree.

Decision Rule Conflicts and Completeness

Conflict tests (Show conflicts)

Show conflicts identifies conditions made unreachable by other rows or branches, such as an earlier broad match shadowing a later narrower one. An unreachable row may still have satisfiable conditions in isolation. Evaluate all rows removes that first-match shadowing check, not every possible logic error.

Completeness tests (Show completeness)

Identifies missing conditions in a Decision table or missing branches in a Decision tree. 'Show completeness' can generate a LARGE number of rows for many-valued combinations; the user determines which suggested conditions are necessary.
