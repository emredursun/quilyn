Decision Tables in Dev Studio

Decision table

Tests property values against conditions to return a result. All rows in a column evaluate the same property. App Studio calculated-field Decision tables are stored as Decision Table Rules in Dev Studio under the Work- class.

A Decision Tree is like a diagnostic flowchart: start at the top, answer YES or NO at each branch, follow the path until you reach a result. A Decision Table is the same logic compressed into a lookup grid — rows are conditions, columns are outputs. The tree is easier to read when conditions are sequential and hierarchical; the table is more concise when many combinations map to the same result.

Decision logic maintenance (Delegation)

Organizations can delegate maintenance of Decision tables to stakeholders who manage a specific product line. Example: a logistics manager updates the expedited shipping threshold. To delegate: configure the Delegation options in the Results tab of the Decision table form.

Evaluate all rows

By default, a Decision table returns the first match (single result). Enable 'Evaluate all rows' to return ALL rows whose conditions are satisfied. Required when multiple matching results are valid (e.g., applying all eligible discounts).

Direct flow processing with Decision tables

Add a Decision shape in a flow pointing to a Decision Table. Each result value maps to a flow connector, directing the Case to a different path — keeping branching logic out of the flow diagram.

Decision Trees

Decision tree

Handles logic that returns a result from test Conditions. Each branch evaluates a property/operator pair against a single value; a true comparison can lead to nested branches. Decision trees can test DIFFERENT properties and operators across branches.

Condition branches and nesting

Each branch has a value, operator, and action (result or sub-branch). Branches nest — a true result triggers deeper comparisons. Example: 'Student?' → Yes → 'Senior?' → Yes → '60+ account'; else → 'Standard account'.

Where Decision trees can be referenced

Decision trees (and Decision tables) can be referenced in:

  • Flow Rules
  • Declare Expressions
  • Activities
  • Routers

Choosing: Decision Tree vs. Decision Table

When to use a Decision table

Use when all conditions evaluate against the SAME property/operator pair. The columnar structure makes it easy to read and maintain when all rows test the same field (e.g., 'Account type =' with different values).

When to use a Decision tree

Use when conditions evaluate against DIFFERENT properties or operators. The branching structure handles logic that cannot fit in a single column (e.g., one branch tests 'Revenue >', another tests 'Customer type =').

Decision Rule Conflicts and Completeness

Conflict tests (Show conflicts)

Identifies rows or branches that can never execute (unreachable conditions). Run via 'Show conflicts' to catch logic gaps before deployment. A conflict means no input could ever satisfy that row's conditions.

Completeness tests (Show completeness)

Identifies missing conditions in a Decision table or missing branches in a Decision tree. 'Show completeness' can generate a LARGE number of rows for many-valued combinations; the user determines which suggested conditions are necessary.
