Localization Fundamentals

Localization in Pega is like preparing a restaurant menu for international guests: you translate the text (language), change the currency symbol and date formats (locale-specific components), and flip the layout for right-to-left readers (RTL). The language pack is a pre-translated menu template — it only works if it fits the same restaurant format (UI architecture) and edition (version).

Localization — 3 aspects

Adapts an application for a specific language or region by:

  • (1) translating text
  • (2) converting locale-specific components (currency symbols, calendar settings)
  • (3) adapting the UI for right-to-left (RTL) text direction if relevant

Locale priority

Pega first checks the browser locale. If the operator profile specifies a different locale, the profile locale takes precedence. If no Ruleset exists for the selected locale, the UI displays English (default).

Language packs

A translated Ruleset with values for fields that typically appear in every application (button labels, prompts). Import via the Localization landing page. The pack must match the same version AND UI architecture (e.g., Constellation v8.8).

Localization process — 3 steps

Create a package, translate it and import it on the App Studio Localization page. Depending on the content, translation uses JSON/Excel and packaged Paragraph HTML. GenAI-assisted text needs review. Test each target locale before relying on automatic Ruleset selection.

Verifying localization

Change the current operator locale in Dev Studio and test the application. A fresh login may be needed. Review messages and correspondence as well as visible labels; correct missing translations and test again.

Localization limitations in Constellation

What can and cannot be localized in Constellation:

  • CAN localize: labels, captions, tooltips, instructions in Views and Portals
  • CANNOT localize: Decision tables and decision trees, Case Statuses, radio buttons and drop-down controls in a table

Studio scope

App Studio and generated user Portals support localization. Dev Studio is not fully localized; untranslated developer content does not alone prove the user Portal translation failed.

Design Considerations for Localization

Picklist properties — omitted from package

When generating a translation package, Pega OMITS local properties with multiple values (e.g., picklist properties). You must add these manually by editing the localization file in Dev Studio.

Dynamic values — must also be localized

Translate the phrase around a dynamic placeholder, preserving its substitution purpose. The topic uses a pyMessages phrase with a user-name placeholder; changing the customer name itself is not phrase translation.

Paragraph instructions — packaged HTML, manual translation

Step-instruction Paragraph text is included in the ZIP as source HTML in paragraph/base. Translate the corresponding paragraph/translated HTML, upload the compressed package and test the target locale. Manual translation does not mean absence from the package.

Data Page controls — not auto-included

For Data Page-backed radio/drop-down entries, add the missing values as separate rows in the Additional text localization record, then rebuild and import the package. If the Data Page is absent from Views, create its localization Rule manually. This is a package omission, not a blanket localization ban.
