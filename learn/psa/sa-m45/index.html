Unit Testing in Pega

Unit testing a Rule is like a quality inspector on a production line testing one specific component (a single bolt, a single circuit) with known inputs before it goes into the final product. The Test Pyramid is the assembly line strategy: test the cheap individual parts (unit tests) most often, and reserve expensive full-car crash tests (end-to-end) for last.

Unit testing — purpose

Tests individual Rules with test data you provide. Reduces risk of configuration errors propagating to other Rules. Supports continuous delivery. Run via: Actions → Run on the Rule form toolbar in Dev Studio.

Binary file Rules — cannot be unit tested

For some Rule types such as binary file Rules, Pega does not provide a unit testing option. The 'Run' option is unavailable on their Rule forms.

Rule resolution applies during unit testing

When you unit test a Rule, Pega applies Rule resolution. If a higher version of the Rule exists, the HIGHER version runs — not necessarily the version you opened.

Test case and assertions

A reusable test checking whether a Rule returns expected results (created from a test run). Each expected result is an ASSERTION. Types: Property (value), Validation summary (harness errors), Run time (≤ N seconds), Page (page in memory).

Test suites

Group multiple test cases to execute in a specified order. Test suites run SEQUENTIALLY — NOT in parallel. Requires a Ruleset configured to store test cases. PegaUnit auto-runs saved unit tests. Run tests on every merge and check-in at minimum.

High-priority vs low-priority test candidates

Test prioritization for Pega Unit Testing:

  • HIGH-PRIORITY — predictable results, executed frequently, complex logic, Rules with wide usage
  • LOW-PRIORITY — frequently changing code, unstable results, or simple/rarely executed Rules

Creating Unit Test Cases

Test cases for Rules

Convert a unit test run into a reusable test case. Define assertions (expected results). When the test case runs, results are compared to assertions — mismatch → test FAILS.

Test cases for Processes and Case Types

Actions → Record test Case (toolbar) → step through the flow entering input → click 'Create test Case' (lower-right) to save the recording. Modify pxCapturePropertyIgnore Data Transform to EXCLUDE unwanted properties from the test.

v8.5+ restriction on Case Type test recording

From Pega v8.5+, recording a test Case for a process that has a Create Stage is NOT possible for NEW Case Types. It only works for Case Types MIGRATED from versions lower than 8.5.

Test Coverage

Test Pyramid

Industry best practice for test strategy. Bottom of pyramid (unit tests): least expensive, easiest to maintain, fastest, should be the MOST tests. Top (end-to-end tests): most expensive, hardest to maintain, slowest, fewest tests. Higher up = higher cost.

Test coverage tool

Determines how many Rules are covered by tests. User-level report: covered/uncovered Rules for the current user. Application-level report: aggregates results from MULTIPLE USERS — visible in the APPLICATION QUALITY DASHBOARD in Dev Studio.

Test coverage configuration

Steps to configure and view test coverage:

  • Configure quality settings: Dev Studio → Configure → Application → Quality → Settings
  • Merge reports: Quality → Test Coverage (only the LATEST application-level report per application appears)
  • Role requirement: SysAdm4 access needed to run test suites
