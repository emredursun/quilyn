Unit Testing in Pega

Unit testing a Rule is like a quality inspector on a production line testing one specific component (a single bolt, a single circuit) with known inputs before it goes into the final product. The Test Pyramid is the assembly line strategy: test the cheap individual parts (unit tests) most often, and reserve expensive full-car crash tests (end-to-end) for last.

Unit testing — purpose

Test individual Rules with defined inputs to isolate configuration errors. The earlier Unit tests v5 topic describes Actions > Run on a supported Rule form in Dev Studio; available interfaces depend on the Rule type.

Binary file Rules — cannot be unit tested

Unit tests v5 identifies binary file Rules as lacking a unit-test Run option. This is a version-scoped source detail, not a universal statement about every testing mechanism.

Rule resolution applies during unit testing

Normal Rule Resolution selects the applicable Rule in the test context. A higher version can run when eligible; version number alone does not override Ruleset availability, class and other resolution criteria.

Test case and assertions

A reusable test compares actual results with assertions. The current v6 examples include Property, Decision result, Expected run time and Page. Assertion availability depends on the Rule type.

Test suites

Unit tests v5 describes sequential bulk suite execution and a Ruleset configured for test storage. This does not imply test dependencies: keep tests portable and independent. Configure execution through PegaUnit and run at least on each merge/check-in.

High-priority vs low-priority test candidates

Test prioritization for Pega Unit Testing:

  • HIGH-PRIORITY — predictable results, executed frequently, complex logic, Rules with wide usage
  • LOW-PRIORITY automation examples: frequent maintenance, easy manual testing, complexity that resists automation, or database persistence. This is prioritization, not a reason to omit risk-based testing.

Creating Unit Test Cases

Test cases for Rules

Convert a unit test run into a reusable test case. Define assertions (expected results). When the test case runs, results are compared to assertions — mismatch → test FAILS.

Test cases for Processes and Case Types

Actions → Record test Case (toolbar) → step through the flow entering input → click 'Create test Case' (lower-right) to save the recording. Modify pxCapturePropertyIgnore Data Transform to EXCLUDE unwanted properties from the test.

v8.5+ restriction on Case Type test recording

Creating unit test Cases v7 retains the 8.5+ restriction for running/recording a process with a Create Stage in a new Case Type. It describes an exception for migrated pre-8.5 Case Types; it does not guarantee all other recording prerequisites.

Test Coverage

Test Pyramid

Industry best practice for test strategy. Bottom of pyramid (unit tests): least expensive, easiest to maintain, fastest, should be the MOST tests. Top (end-to-end tests): most expensive, hardest to maintain, slowest, fewest tests. Higher up = higher cost.

Test coverage tool

Coverage reports identify executable Rules exercised or not exercised in included applications. Application-level reports combine multiple users; user-level results appear in Coverage history. A covered Rule is not proof that every internal path was tested.

Test coverage configuration

Distinguish suite execution, coverage contribution and session initiation:

  • SysAdm4: role required by this topic to run test suites.
  • SysAdm4 or User4: tests can contribute to coverage.
  • pzStartOrStopMasterAppRuleCoverage: privilege required to initiate application-level coverage.
  • Application-level results: Application Quality Dashboard; user-level results: Coverage history. Merge application-level reports for consolidated results.
