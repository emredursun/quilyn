Personas, Access Roles, and Access Groups

Think of an Access Group as a configured set of hotel permissions, with Access Roles contributing the rules for rooms and actions. A Persona describes a user group’s goals; it is not itself a universal permission grant. Evaluate the applicable restrictions as well as grants.

Persona

Defines how users align with an application by BUSINESS OUTCOMES. Example: 'Loan Applicant' and 'Loan Officer' have different goals in the process. Creating a Persona in App Studio auto-creates a corresponding Access Group in Dev Studio.

Role

Defines how users INTERACT with the application. Example: Manager, User. Each Role has a default Channel interface — this determines which screen users see upon login.

Access Role

Categorizes users by job function. For each Access Role, you configure permissions to control Actions on instances of a specific class. Example: 'Manager' and 'User' can be separate Access Roles with different permissions.

Access Group

Represents a group of privileges. Each Access Group references one or more Access Roles. Multiple Access Groups can reference the same application for different access levels and align with roles assignable to users in App Studio.

Access Group — conflicting permissions rule

In the lesson’s ordinary conflicting-role example, the most permissive setting applies. Do not extend this example into a promise that other security checks, Access Deny conditions or authorization models are bypassed.

Access Control Records and Tools

ARO — Access of Role to Object

Access of Role to Object binds an Access Role to permissions for a class. Permissions can allow actions or specify No Access; the record is not limited to unconditional grants.

Access Deny

Access Deny supplies explicit denial over the applicable ARO permission. Evaluate its conditions and production-level settings; do not assume every role’s grant and every denial combine identically in all configurations.

Best practice: use management tools, not direct record edits

Prefer App Studio User management when sufficient. Some permissions, including Case deletion, require Access Manager. Both simplify the underlying role permissions:

  • App Studio: Users → User management (Persona access landing page)
  • Dev Studio: Configure → Org & Security → Access Manager

Production levels (on-premises)

On-premises levels: 5 Production, 4 Staging, 3 Quality assurance, 2 Development, 1 Sandbox. Access value 0 denies; otherwise the permission value must be at least the system production level. A value of 2 can permit Development while denying Production.
