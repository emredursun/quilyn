Personas, Access Roles, and Access Groups

Think of access control like a hotel. The Persona is the guest type (business traveler vs. tourist — different business outcomes). The Role is the floor/wing they're placed on. The Access Group is the room key type (standard vs. premium). The ARO is the list of which specific doors that key can open. Access Deny is a padlock that blocks entry even if the key matches.

Persona

Defines how users align with an application by BUSINESS OUTCOMES. Example: 'Loan Applicant' and 'Loan Officer' have different goals in the process. Creating a Persona in App Studio auto-creates a corresponding Access Group in Dev Studio.

Role

Defines how users INTERACT with the application. Example: Manager, User. Each Role has a default Channel interface — this determines which screen users see upon login.

Access Role

Categorizes users by job function. For each Access Role, you configure permissions to control Actions on instances of a specific class. Example: 'Manager' and 'User' can be separate Access Roles with different permissions.

Access Group

Represents a group of privileges. Each Access Group references one or more Access Roles. Multiple Access Groups can reference the same application for different access levels and align with roles assignable to users in App Studio.

Access Group — conflicting permissions rule

When an Access Group references multiple Access Roles with conflicting permissions, the MOST PERMISSIVE permission applies. Pega favors access in conflict scenarios.

Access Control Records and Tools

ARO — Access of Role to Object

Specifies permissions for instances of a specific CLASS for members of a specific ACCESS ROLE. This is how RBAC permissions are granted in Pega. The name describes its function: Access of Role to Object.

Access Deny

OVERRIDES AROs to explicitly DENY access when regulations or policy require it. An Access Deny record takes precedence over any ARO that would otherwise allow access. Denial can also depend on the production level value (1 to 5).

Best practice: use management tools, not direct record edits

Navigate to access management through the correct studio path:

  • App Studio: Users → User management (Persona access landing page)
  • Dev Studio: Configure → Org & Security → Access Manager

Production levels (on-premises)

Scale 1–5: 1 = Production (most restrictive), 2 = Staging, 3 = Quality Assurance, 4 = Development, 5 = Sandbox (most permissive). Lower number = more production-like. Access Deny denial can depend on the production level.
