Agile Workbench

Application profile & Developer Assistant

Application profile tracks development work; Developer Assistant organizes work and provides AI-assisted aids. The source names Guidance, Knowledge, Work and Checklists tabs without saying every tab is independently AI-powered.

  • Application profile: up-to-date view of all work items, features, and status
  • Developer Assistant pane: AI-powered aids with 4 tabs — Guidance, Knowledge, Work, Checklists

Features and subfeatures

Features = capabilities the application supports. Subfeatures = features nested within a feature. When you create a new Case Type, Pega automatically creates a feature with the same name. Work items are associated with features or subfeatures.

3 work item types

Work items tracked in the Application profile:

  • Stories (User stories): describe business requirements; make up the majority of development work; can be uploaded from Excel in bulk
  • Bugs: document feature defects; major bugs are addressed before minor ones
  • Feedback items: enhancement requests identified during playback sessions

Two ways to change work item status

To do, Doing and Done are the listed statuses. Change status by dragging the card to a column or using the Status list on the work item itself.

Agile Workbench integrations

Integrates with Agile Studio (expanded functionality: release management, progress tracking, team capacity, analytics). Also integrates with external tools: Jira, CA Agile Central — allowing customers to use their existing infrastructure.

Release Management — DevOps & CI/CD

CI/CD is like a car assembly line with quality checkpoints. CI is the early part: workers (developers) frequently add parts (code changes), robots (automated tests) check each part before it moves forward. If a part fails inspection, the line STOPS. CD is the downstream line: the car is tested at speed, compatibility, and safety gates before reaching the customer (production). Deployment Manager is the factory floor supervisor who orchestrates the whole line automatically.

DevOps

A collaborative practice between development, quality, and operations:

  • Goal: deliver high-quality software in an automated, agile way
  • Reduces time to market without compromising quality
  • CI/CD pipeline = the automated process from development through testing to deployment

Continuous Integration (CI)

Developers frequently check in changes. Automated build verifies each change — identifies issues EARLY. 'Ready to share' step: new changes work with existing app. 'Integrate changes' step: critical tests pass → changes published to development repository.

Continuous Delivery (CD)

The deployment pipeline stages after CI:

  • Rigorous automated regression testing
  • Changes deployed to staging for further testing
  • 'Ready to accept': acceptance criteria tests pass
  • 'Ready to deploy': performance and compatibility tests pass
  • Deploy: validates in preproduction → production → post-deployment tests with rollback option

Deployment Manager

Deployment Manager orchestrates Pega CI/CD. The source describes Admin Studio for designing and managing pipelines and a configured App Studio integration for Publishing.

  • Manage pipelines through Admin Studio in the described workflow.
  • After integration, App Studio Settings > Versions exposes the application pipeline for Publishing.
  • Automate Branch merging, packaging and environment promotion.
  • The source lists Jenkins and Microsoft Azure DevOps as third-party examples.

Agile Development Best Practices

3 Pega agile best practices

① Real-time updates: frequent small-scope development iterations. ② Testing: continuous validation to identify and address issues early. ③ Branches: concurrent team development environment to maximize productivity.

CI best practices

Best practices for Continuous Integration in Pega:

  • Test early and often: run Pega unit tests + critical integration tests before packaging
  • If tests fail → STOP the release pipeline until fixed
  • Automate: trigger merges and builds via Deployment Manager
  • Update the referenced product Rule (Rule-Admin-Product).
  • Maintain deployable version history by publishing exported application archives to a repository.

CD best practices

① Create test environments (Docker/UAT). ② Run regression tests — UI and service layer. ③ Use version control: target specific Ruleset versions for production. ④ Define a rollback strategy. ⑤ Annotate passing packages as deployment-ready.
