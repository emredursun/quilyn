Data Modeling

Data object (data type)

A structure that groups related fields to describe a business entity (e.g., Customer with Name, Email, Phone). Reusable across all Case Types. In Dev Studio, a data object is called a data type and a field is a property.

A Pega data model is like a factory's inventory system: Data Classes are the warehouse shelves (organized by type), Data Records are the physical items (actual data instances), and Data Pages are the forklifts — they retrieve items from wherever they are stored (local warehouse or external supplier) and bring them to the production floor, caching the load so the trip only happens once.

Why model data

A well-designed Data Model promotes reuse, accuracy, consistency, and scalability. You model the data an application needs to complete work, then connect it to Case Types so the workflow has the right data at the right time.

Sourcing data objects

Data for a data object can be stored LOCALLY in the Pega database, or sourced from an EXTERNAL system of record (e.g., a client database or web service). Pega ships pre-configured objects (e.g., Address-Postal, Address-Email) to reuse or extend.

Data Records

Data Record

The unique set of fields and values for one instance of a data object (e.g., one Customer = Ian / Mitchell / email / phone). Records live in a system of record — Pega DB or external.

Value change vs. structure change

Two types of data model changes with different implications:

  • VALUE change (add a customer, update a phone number) — normal business operation; no process change needed
  • STRUCTURE change (adding/removing fields) — modifies the data object definition; requires careful planning

pyGUID & local entry

Add records locally on the Records tab (stored in Pega DB tables). Each local record receives an auto-assigned pyGUID (unique ID) stored with the Case for later retrieval. External sources: each database row is one record.

Data Pages and the Visual Data Model

Data Page

The bridge between a data object and its data — retrieves from a source and CACHES it in Clipboard memory. Hides integration details so developers work with sourced data without knowing where it lives.

Pega Live Data & default Data Pages

Pega Live Data is the virtualization layer separating business logic from how/when data is accessed. Every data object includes three default Data Pages: a single read-only, a list read-only, and a single read-and-write. Case Types have two (both read-only).

Visual Data Model

A diagram showing the application's data objects and their relationships. Relationship indicators: one line = one-to-one; multiple lines on one side = one-to-many; multiple lines on both sides = many-to-many.

Integration Designer

Data objects and Integrations landing page

The Integration Designer is the single place in App Studio to see the application's data objects, their Data Pages, the systems of record (SOR) that source them, which Case Types reference each object (Referenced By), and simulated data sources.

Visual Data Model & Integration Map

From the Integration Designer you open the Visual Data Model (objects and relationships) and the Integration Map (a diagram of data objects and the systems of record from which they are sourced).
