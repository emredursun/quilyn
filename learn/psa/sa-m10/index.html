Views in Constellation

View

A reusable configuration of UI elements used to capture or display data for a Case. Constellation applications are built on a View-based UI architecture (the Constellation Ruleset), and Views are reusable across Case Types.

Configuring a Pega Constellation UI is like furnishing a modular apartment: Views are the room layouts, Fields are the furniture pieces, and model-driven controls are the building code that says 'all outlets must be at 18 inches.' Change one layout template and every room using it updates automatically — the model drives the furniture arrangement without repainting each room by hand.

Prescribed design system

Constellation provides a prescribed but configurable design system — a builder kit of UI elements, styles, UX patterns, themes, and guidelines — with out-of-the-box accessibility. BAs, Citizen Developers, and System Architects configure Views in App Studio.

The four View types

Full Page View (read-only; one per Case/data object), Partial (read-only), List (data-source-backed; table/timeline/tile; read-only by default), and Form (gathers data; editable).

UI Configuration in App Studio

Separation of Concerns

The UI layer follows the Separation of Concerns principle — the application is divided into distinct parts, each addressing one concern — so front-end components connect cleanly to back-end APIs.

Templates

Auto-generated Views are built from Templates that handle layout and responsiveness (breakpoints, white-space, wrapping) and ensure out-of-the-box accessibility. Each View type uses a different template.

Full Page View

Auto-added per new Case Type/data object; the three-pane visual framework representing a single Case. Edited on the UX tab. While authoring, the Preview shows only placeholder text — run a Case instance to preview with real data.

Summary panel & Promoted Action

The Summary panel sits upper-left and by default includes the Details View (showing Primary Fields) and Pulse View. A Promoted Action gives header access to a frequent Case-wide Action (e.g., Change Stage) — one per Case Type.

Form Views

Creating a Form View

Two ways: on the Workflow tab (configuring a Step's View auto-creates a Form View) or on the UX tab's Other Views pane. Form Views use the Default template; Step-associated Views can also use the Hierarchical template.

Layout

Set 1–3 columns; two-column is best practice. Narrow inputs (Text single line, Currency) take one column; wider/any-height inputs (Rich Text Editor, Text area, Radio group, Checkbox, Booleans, Attachments) span two columns, keeping tabbing left-to-right.

Field groups & multi-step vs hierarchical

Three UI structuring concepts:

  • FIELD GROUP — clusters related fields under one header; specific to the View (not reusable)
  • MULTI-STEP FORM — one Assignment split across MULTIPLE Views (linear; default for Create Stage)
  • HIERARCHICAL FORM — a single View with expandable sub-Views (nested structure)

Exploring Fields

Field settings

Each field has a name and a Field Type that determines its format/validation and the control shown. You configure field settings (label, required, visibility, etc.) to tailor capture and presentation.

Primary Fields

The critical fields displayed whenever interacting with a Case type; automatically shown on the default Create, Edit, and Details Views. A reference field inherits the referenced data object's Primary Fields into the Case Type's Views.

Model-driven UI Controls

Model-driven UI

In Constellation, the UI is generated from the Data Model: the control type is selected AUTOMATICALLY based on field type. Date → date picker; Boolean → checkbox; Picklist → dropdown. No manual wiring needed.

Patterns and consistency

Because controls derive from the model via reusable patterns, the UI stays consistent and responsive across devices/channels, and adapts automatically when rules change. You can still customize a control's presentation where needed.
