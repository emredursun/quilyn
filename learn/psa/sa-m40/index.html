AIC Triad & Security Checklist

Airport identity checks illustrate authentication; permission to enter particular areas illustrates authorization. A checklist tracks applicable security work before release. It is a process aid rather than proof that every possible attack has been prevented.

AIC Triad

Availability, Integrity, Confidentiality — Pega's shared security goal. Unauthorized individuals cannot access or modify the application or its data. Authorized individuals only access what they need to perform their jobs.

Security Checklist

A guideline Rule instance automatically installed per app version to harden Pega applications. Tasks are organized by timing and key area: monitoring, authentication, authorization, auditing, production testing. Not all tasks are required for every app.

Security Checklist — enforcement

The source describes Deployment Manager blocking production promotion when the Security Checklist is incomplete. Applicable tasks depend on the application and deployment; not every listed task applies to every release.

Guardrail compliance — #1 security requirement

The source emphasizes guardrail compliance because custom code can bypass built-in security enforcement. Use platform security features; do not treat compliance as a replacement for MFA, authorization design or security testing.

Security Policies — Types and Authentication

Two types of security

Pega security operates at two distinct layers:

  • Application-level security: protects from outsiders and unauthorized users (passwords, auth policies, MFA, third-party tools)
  • Feature security: controls what authorized users can and cannot access within the app (RBAC, ABAC, CBAC)

Where to configure Security Policies

The earlier Security policies v5 source documents these navigation routes; v6 focuses on policy behavior. Verify the interface in the target version:

  • App Studio: Authentication landing page → Security Policies tab
  • Dev Studio: Configure → Org & Security → Authentication → Security Policies (applies to the entire Pega Platform server)
  • ⚠ CAUTION: authentication service settings may OVERRIDE Security Policy page settings

Security Policy: Password

Sets rules for password strength:

  • Minimum length
  • Required character types (uppercase, digits, symbols)
  • Restrictions on predictable or reused passwords

Security Policy: CAPTCHA

Presents a challenge on initial login or after failed login attempts. Can use a custom or default CAPTCHA.

Security Policies — Access Control and Monitoring

Security Policy: Lockout

Controls account lockout behavior after failed logins:

  • Enabled penalty: configure a failed-attempt threshold and initial seconds; repeat failures escalate the penalty.
  • Disabled penalty: configure failed-attempt count and lock duration in minutes. Disabling the penalty option does not mean all lockout protection disappears.

Security Policy: Audit

Controls the level of detail recorded in the system log for security-related events.

Security Policy: Multi-factor Authentication (MFA)

The built-in OTP policy delivers a time-limited code by email or SMS. MFA is broader than this delivery mechanism; 2FA uses two factors. The source lists knowledge, possession and an inherent characteristic such as a fingerprint.

Security Policy: Operator disablement

Automatically disables access for users who have been inactive for a specified number of days. An exclusion list can protect users who still require access despite inactivity.

Authentication vs. Authorization

Authentication — WHO can access

Authentication verifies identity for application and service access. An Operator ID is commonly an email address, but not necessarily one. SAML, OpenID Connect and token credentials support SSO; the authentication service configures applicable policies.

Authorization — WHAT users can do

Controls what authenticated users can access and perform within the application. Three models: RBAC, ABAC, and CBAC.

Authorization model: RBAC

RBAC assigns permissions through user Roles. It can complement other authorization models; it is not automatically sufficient for every security requirement.

Authorization model: ABAC

Attribute-Based Access Control. Access is determined by comparing object characteristics (Case, field, document) to user attributes. More granular than RBAC — the same role can have different access depending on contextual attributes.

Authorization model: CBAC

Client-Based Access Control. Tracks and processes requests to view, update, or remove personal customer data. Designed to address GDPR and similar data privacy regulations.
