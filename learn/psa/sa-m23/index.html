Relevant Records — Purpose and Marking

Relevant record

A rule marked to make it accessible to other developers from App Studio prompts. Marking exposes Dev Studio rules so App Studio developers can use them without navigating to Dev Studio.

Think of a curated toolbox: a developer recommends suitable tools for a particular job. The recommendation helps colleagues find an existing Rule; it does not grant security permissions or copy the tool into a new implementation.

Why designate relevant records

Relevant designation makes developer-prepared Rules discoverable in supported App Studio configuration prompts. For an existing SLA selection, mark the Dev Studio Rule relevant for the appropriate class. This designation is not a deployment or authorization control.

Auto-marked vs. manually marked

Relevant designation supports discovery and reuse, rather than mobile/offline packaging.

  • AUTO-MARKED — App Studio-created fields, views and processes in a Case Type or data type are examples of automatically designated records.
  • MANUAL — For an eligible Dev Studio Rule, use Actions → Mark as relevant record. Verify guardrail compliance before recommending it for reuse.

Relevant Records — Scope and Visibility

Where relevant records appear in App Studio

Accessed in App Studio when: (1) adding a step to a process, (2) adding fields to a user view, or (3) applying a service level. The Fields and Views lists in the Case Designer are populated with relevant records.

Viewing relevant records in Dev Studio

Configure → Application → Inventory → Relevant Records, then enter a class name. By default, ACTIVE records are shown. The 'Marked relevant at' column shows which class level set the designation.

Inactive relevant records

Records no longer applicable can be marked INACTIVE to narrow the list without deleting the rule. Enable 'Show inactive relevant records' to view them. Use the Actions icon to toggle active/inactive per class.

Inherited relevant records

An active designation can be inherited by subclasses. In the source example, Insurance-Claims passes its SLA designation to Insurance-Claims-Auto and Insurance-Claims-Home. Show inherited relevant records for the class reveals those entries; active/inactive state is managed for the selected class.

Which rules can be relevant records

Eligible Rule types in the reviewed source

Correspondence, Data transforms, Decision tables, Decision trees, Harness (Pages), Notification, Paragraphs, Process (Flows), Property, Proposition filters, Pulse Feed, Sections, Service Level Agreements, Strategy, User Action (Flow actions), Validate, View, When.

Proposition filter requirement

For Proposition filter rules, ALL properties, strategies, and When rules used as filter conditions must ALSO be marked as relevant records for the primary context class (default: the Customer class).
