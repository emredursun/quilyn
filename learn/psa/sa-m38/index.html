Data Pages — Structure and Edit Modes

A Data Page is like a whiteboard in a meeting room. The first person to need the information fetches it and writes it up. Everyone else reads from the whiteboard (cached). When the whiteboard gets stale, someone erases it and writes fresh data — but only once per meeting (one refresh per interaction).

Data Page — what it is

A Data Page caches data from external systems in Pega's Clipboard memory. It is populated ON-DEMAND — only when first accessed. If it already exists and is not stale, Pega reuses the cached version.

Structure: Page vs List

Two Data Page structure types:

  • PAGE — holds a SINGLE item (e.g., one customer record); accessed directly by property name
  • LIST — holds MULTIPLE items in the pxResults ordered array; accessed by DataPageName[index].property

Edit Mode: Read-Only

Data stays cached — no changes written back to the source. Appears in the 'Data Pages' category of the Clipboard tool. Example: DMV record lookup.

Edit Mode: Editable

Users can modify the cached data within the session. Appears in 'User Pages' category of the Clipboard tool. Example: a shipping address a user updates during checkout.

Edit Mode: Savable

Changes made to the Data Page can be pushed back to the system of record via a save plan. Use when Pega must update the external source after user edits. Example: push-back approval updates the external HR system.

Data Pages — Scope

Scope: Thread

Unique to a single Case — each Case gets its own Data Page instance. Use for Case-specific data. Example: real-time stock price during one buy/sell transaction.

Scope: Requestor

Shared across all Cases created by one user in a single session. Use for user-specific data reused across Cases. Example: a list of the user's privileged shipping addresses.

Scope: Node

Shared by ALL users on the system. Use for common static data. Example: list of vehicle makes and models that never changes per user.

Data Sources and Parameters

9 data source types

Data Transform, Activity, Connector, Report definition, Database lookup, Robotic Automation, Robotic desktop Automation, Aggregate sources, Lookup. Each specifies where Pega fetches data for the Data Page.

When a Data Transform mapping is required

A Data Transform must map source output to the Data Page's Data Model when using: Report definition (page structure), Lookup (list structure), Robotic Automation, or Robotic desktop Automation. The other 5 source types map automatically.

Aggregate sources

Combines data from multiple sources into a single Data Page. Sources are populated in the listed order. Use when data must be merged from two or more systems.

Conditional sourcing

When a Data Page has multiple sources, configure a condition on each to determine which Pega uses. Pega evaluates in order and uses the first matching condition. The last source has no condition — it acts as the 'Otherwise' fallback.

Parameters — purpose and syntax

Parameters filter or limit what a Data Page loads. Example: load only auto insurance policies for one customer. Reference syntax: DataPageName[Param1_Name:Param1_Value, Param2_Name:Param2_Value].

Parameters — Clipboard instances CAUTION

Each unique combination of parameter values creates a separate Clipboard instance. High-cardinality parameters can consume significant memory. Use 'Limit to a single Data Page' on the Load Management tab to force one instance (Pega overwrites it when parameters change).

Refresh Strategies

Refresh strategy — overview

Defines when cached Data Page contents are considered stale and must be reloaded. Optional but strongly recommended. If at least one configured condition is met, Pega reloads the page from the data source.

Reload once per interaction

Reloads the Data Page every time it is accessed — but only once per interaction. Only available for Thread or Requestor scope. Cannot be combined with other refresh options. Example: travel reservation Case reloads seating availability for each interaction.

Do not reload when

Uses a When Condition. If the condition returns TRUE → data is considered current, no reload occurs. Example: stock prices after trading day ends — condition 'marketClosed = true' prevents pointless reloads.

Reload if older than

Reloads after a fixed time interval. After the interval expires, the next access triggers a reload. Example: seating inventory with a 10-min interval — if loaded at 12:00, it becomes stale at 12:10 and reloads on first access after.

Key rule: max ONE reload per interaction

Regardless of the refresh strategy, Pega Platform NEVER refreshes a Data Page more than once per interaction. If accessed 5 times in one interaction, it reloads at most once — subsequent accesses use the already-refreshed version.

Autopopulation, UI Controls, and Simulated Data

Refer to a Data Page

The Case points to the Data Page (no copy). Data reloads per the refresh strategy. When a parameter changes, Pega creates a new instance and the property points to it. Use when you always need the most current data.

Copy data from a Data Page

Data is copied into the Case at a specific point in time. Once copied, the Data Page is NOT accessed again (unless request parameters change). Use for historical snapshots. Example: customer info captured at insurance claim creation.

UI list from a Data Page

Populate a dropdown or list from a Data Page instead of hardcoding values — avoids re-releasing the app when values change. Only the SELECTED value is saved to the Case's Data Model; the full list stays in the Data Page.

Displayed value vs. copied value in UI lists

In UI selection controls, displayed and stored values can differ:

  • DISPLAYED VALUE — what the user sees in the dropdown or list (e.g., country name)
  • COPIED VALUE — what gets saved to the Case (e.g., country code); configure via the Clipboard property mapping

Simulated external data sources

Pega lets you simulate any external data source using sample data. Use when: the external system is unavailable, the API is under development, or the source has no data yet. Allows full dev/test without interruption.

Simulated data sources for unit testing

Simulation lets you dictate the exact response returned by a source. This is valuable for unit testing — you control the response to verify different processing scenarios without depending on a live system.
