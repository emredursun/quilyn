Rules and Rule Types

Rule

The basic building block of a Pega application that defines its behavior. Each Rule is an instance of a Rule Type, which determines the type of behavior it models. Pega uses Rules to generate application code in the background.

A Rule is an individual instruction; a Ruleset groups related instructions for management. Runtime selection depends on the configured application context, not an automatic download of the latest available version.

Rule Type

A template for creating a Rule that models a specific behavior — for example, a Flow Rule models a Process, while other Rule Types model UI, automated Decisions, and more.

Automated Rule creation in App Studio

As you add Processes, define Steps, and configure Views in the Case Life Cycle, Pega creates and manages the underlying Rules (Flows, Tasks, UI) in the background, letting developers focus on business tasks.

Application Modularity with Rules

Versioning

Create a new version whenever Case behavior must change. Pega keeps change history — you can review and undo. Each Rule describes specific behavior, so changes are isolated to that Rule only.

Delegation

Developers delegate a Rule to business users so they can update Case behavior as conditions change while the rest of the application stays unchanged (e.g., Accounting raises an auto-approval threshold from USD 25 to USD 50 without a change request).

Reuse

Developers reuse Rules whenever an application needs existing behavior, instead of reconfiguring it every time (e.g., reuse one policyholder-info UI form across auto, property, and marine claims).

Parametrization

To increase reusability, use parameters to drive a Rule's logic based on a passed value instead of hard-coded data — reducing code duplication and the time to implement Rule specializations.

Rulesets and Versioning

Ruleset

A group that identifies, stores, and manages the set of Rules defining an application, packaged for distribution. Rulesets can be SHARED between applications to reuse the same Rules (like an album shared across playlists).

Ruleset version

An instance of a Ruleset collecting individual Rules. Create a NEW version to update contents (unlocked for edits); best practice is to LOCK older versions. Version format: major-minor-patch (two-digit each), starting at 01-01-01.

Ruleset stack

The application stack orders Rulesets for lookup. A listed entry covers versions down to the lowest minor and patch in the specified major version, not every earlier major version.

Rule Creation

Two paths to a Rule

In App Studio, Rules are created FOR you as you build the Case Life Cycle, Views, and data. In Dev Studio, you can directly create and manage how a Rule is created and reused to maintain Rule integrity and reusability.

New Record form fields (Dev Studio)

Four fields that uniquely identify a rule: (1) Rule Type (function), (2) Ruleset (grouping), (3) Apply to (target class), (4) Label (display name). These four fields together enable Rule Resolution.

Rule creation methods (what auto-fills)

Five paths to the New Record form, each pre-filling context:

  • Create menu: Rule Type, application context and Ruleset
  • App Explorer: adds the class context
  • Rule reference: also provides Label/identifier when the reference has a name
  • Save As: source context, with Identifier, Class or Ruleset changed
  • Records explorer: application context and Ruleset

Specialization by copy (Save As)

Copy an existing Rule into a different class or Ruleset to specialize its behavior, preserving the original while creating a variant. At least one of Identifier, Class, or Ruleset must differ from the source.

Instance key (.pzInsKey)

The source describes a generally four-part instance key: internal Rule Type, applies-to class, identifier and creation timestamp normalized to GMT. Some Rule Types add identifying elements. Do not confuse this key with the entire runtime Rule selection algorithm.

Classes and Class Hierarchy

Class

A grouping of Rules by reuse scope. Three class types per application: Work class (Case processing rules), Data class (data model rules), Integration class (connector rules). Classes form the inheritance hierarchy Pega uses to resolve rules at runtime.

Parent and child classes

A class can contain other classes. A parent class contains another class; a child class is contained by another. A child class can reuse/inherit any Rules defined for its parent class.

Class hierarchy

Classes are layered most-specific to least-specific. At run time, Pega starts with the most-specific class and expands to more general ones. The class name shows position: TGB-IT-Work is a child of TGB-IT, a child of TGB.

Rule Reuse Through Inheritance

Pattern inheritance

AUTOMATIC inheritance using the existing class-name structure (shared prefix) to determine which Rules are available for reuse. Promotes reuse based on BUSINESS suitability — aggregating Rules at higher levels for departments within that division.

Directed inheritance

Inheritance where the parent class is EXPLICITLY specified on the class Rule form (not automatic). Lets an application class inherit Rules from OUTSIDE the business class hierarchy (e.g., Work- or Data-). Promotes reuse based on FUNCTIONAL suitability.

Resolution order & @baseclass

Pega searches parent classes via pattern inheritance; if unsuccessful, uses the directed inheritance parent for another pattern search — repeating until reaching @baseclass. If still not found after @baseclass, Pega returns an error.
