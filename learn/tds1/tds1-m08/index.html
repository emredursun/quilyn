Why this comes up

The scenario

Applications evolve — new features get added to the system under test after a TestSheet already exists. When a new feature affects existing test data, the TestSheet needs a new Attribute (and its Instances) integrated into the structure that's already in place, without starting over.

Where to add it

Create the new Attribute wherever it logically fits in the existing structure — it can be added right alongside Attributes that already have combinations, even if that means the existing combination set now needs to account for it.

Updating combinations at every level

The core rule

Inspect combinations at every affected level. Fill missing baseline values where appropriate, then complete or propagate uncovered variations according to the chosen method and constraints. The documented Complete Instances command adds uncombined combinations without duplicating existing ones; Propagate Instance(s) adds chosen combinations without applying a combinatorial method.

Inspect missing values and Instance Usage at the affected levels. For explicit propagation, select the source Instance(s), Ctrl-select the higher-level Instances object, and use Propagate Instance(s). Inspect the result; propagation is not a claim that all coverage requirements are satisfied.

Independent worked example: extending shipping choices

The change

Independent Quilyn example, not a verified Academy exercise: assume an unconstrained Linear Expansion design with Ground as the shipping baseline and two previously uncovered alternatives, Next Day Air and Second Day Air. Pickup has N/A shipping. Real business constraints must be modeled rather than inferred from these labels.

Updating the lower (Checkout) level

Fill Ground in the existing checkout baseline and N/A where shipping does not apply. In this example, neither air-shipping alternative is represented yet. Add two checkout scenarios, each varying only the shipping choice while keeping the other fields at their valid StraightThrough baselines.

Updating the TestSheet level

At the TestSheet level, inspect existing rows and select appropriate checkout data. Assume the two new checkout alternatives are not represented there either: this simple Linear Expansion example adds two upper-level baseline variations, one for each checkout alternative. Other methods or Relations can require different combinations; there is no fixed original count of nine rows.

Inspect Requirement coverage and refresh calculations

Inspect the links for new Instances rather than assuming coverage from a previously linked TestSheet. Drag any missing design Instances to their relevant Requirements to create substitutes. After adding executable tests and execution links, replace substitutes as appropriate and use Update Outdated Values when automatic calculation is disabled.

The Academy video and exercise files require access and have not been verified. Practice this documented workflow in your own workspace; independently inspect the resulting combinations, links and calculations.
