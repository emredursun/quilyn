Where TDS1 fits in the testing lifecycle

Independent Quilyn introduction based on Tosca On-Premises 2026.1 documentation. The Academy video requires authentication and was not reviewed; this is not a transcript or verified outline of that course.

Requirements

Define expected functional and non-functional behavior with stakeholders, then organize criteria and prioritize business risk.

TestCase-Design

Plan logical tests and data variation before execution. TestSheets organize Attributes or Steps, Instances hold concrete variations, and Classes support reuse. Templates can instantiate executable TestCases from the design.

Distinct responsibilities

Requirements express expected behavior. A TestSheet structures data and processes; an executable TestCase performs checks. These artifacts are related but are not interchangeable.

Why invest time up front in test design

Planned variation

Select a combination method for the risks and interactions under test. All combinations expands the full defined dataset; Orthogonal covers each value, Pairwise covers value pairs, and Linear expansion varies one non-StraightThrough value at a time around a baseline.

Fewer combinations are not evidence of complete defect coverage. Independent example: testing each discount and shipping option separately can miss a defect that occurs only when two options interact.

Reporting needs recalculation

Link executable tests to their Requirements. After changes, Requirement values need recalculation: AutoCalculateRequirements is off by default in 2026.1. Use Update Outdated Values, or enable automatic calculation and restart Tosca; large repositories can incur delays.
