Where TDS1 fits in the testing lifecycle

Test Design Specialist (TDS1)

This course prepares you to work in the two Tosca sections that sit at the front of the STLC: Requirements (colored yellow in Tosca Commander) and TestCase Design (colored red). Together they cover the analysis and planning phases — figuring out what needs to be tested and how much data variation is needed — before any physical TestCase is built.

Requirements phase

Answers 'what needs to be tested and how risky is it if it breaks?'. Requirements are defined, structured, and risk-weighted so testers know where to focus first, and so progress can be tracked against them later.

TestCase Design phase

Answers 'what data combinations do I need to prove each Requirement works?'. Business behavior and test data are translated into a structured, combinable format — the TestSheet — before a single physical TestCase is built in the TestCase section (which was covered in the Automation Specialist courses).

Why invest time up front in test design

The traditional imbalance

On many projects, only a small fraction of testing time is spent specifying test cases (often done ad-hoc/intuitively), while the vast majority is spent in execution — and that execution effort repeats every regression cycle. Weak upfront design tends to produce redundant test cases that over-cover high-visibility requirements while under-covering others.

Tricentis' approach

Shift more effort into the design phase: define Requirements, weight them by risk, and derive test data combinations systematically (covered across Lessons 1-10). The payoff is fewer but more precise test cases, each with a clear, isolated purpose — which also makes failures faster to diagnose, because a well-designed TestCase only fails for one reason.

Linking TestCase Design back to Requirements (Lesson 7) turns the Requirements section into a live project dashboard — risk coverage, execution state, and outstanding work are all visible from one place.
