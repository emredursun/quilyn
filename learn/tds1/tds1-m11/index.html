About this module

Capstone review

The official course closes with three unguided scenarios where you design a TestSheet from a business description alone, without step-by-step instructions: a discount-calculation feature, a configurable-product feature, and an abstract billing-package feature. Each is meant to force you to apply Lessons 1-10 end to end, without being told which Attribute or method to use. This module walks through one original worked example the same way, then reviews what each official scenario is really testing conceptually.

Worked example: a Loyalty Tier discount

Business context

A webshop is introducing a Loyalty Tier discount at checkout: Guest checkouts (no loyalty account) get no discount, Bronze members get 5% off the subtotal, Silver members get 10% off, and Gold members get 15% off. An expired loyalty account should be rejected with an error at checkout rather than receiving any discount.

Step 1 — Requirement

Under Folder 'Webshop' → RequirementSet 'Checkout', create a Requirement 'Apply loyalty discount'. Since pricing-related bugs have high financial impact but this feature isn't used on every order, it's reasonable to weight it with Complex Weighting — a mid Frequency Class and a higher Damage Class.

Step 2 — Attributes

Create a TestSheet 'Loyalty Discount at Checkout' with the four core Attributes: Administration (No), Precondition (Yes — e.g. an active customer session), Process (Yes — the Loyalty Tier itself), Verification (Result — the expected discount applied).

Step 3 — Instances

Under the Process Attribute's 'Loyalty Tier' Attribute, create Instances: Guest (StraightThrough — the most common, lowest-dependency case), Bronze (Valid), Silver (Valid), Gold (Valid), and Expired Account (Invalid — expected to produce a rejection error, not a discount).

Step 4 — Combinatorial method

With one Attribute driving four meaningfully different behaviors, Linear Expansion is the natural fit here: the Guest StraightThrough becomes the baseline TestCase, and each remaining Instance (Bronze, Silver, Gold, Expired Account) becomes its own TestCase differing only in Loyalty Tier — giving 5 TestCases total, each with an isolated, easy-to-debug focus. All Combinations would be unnecessary here since there's only one Attribute actually varying.

Step 5 — Reuse and linking

If 'Loyalty Tier' is likely to be reused in other TestSheets (e.g. a separate Requirement for loyalty point accrual), it's a good candidate to extract into a Class once that second use case appears — not before. Finally, all 5 generated Instances get dragged onto the 'Apply loyalty discount' Requirement, creating TestCase-Substitute links that make this coverage visible on the Requirements dashboard.
