Building the Requirements structure

Requirement

A criterion the system under test is expected to fulfil — functional (e.g. 'a customer can pay with a Visa card') or non-functional (e.g. system security). Requirements are gathered from workshops with stakeholders, or from existing specs/BA documents.

Structuring principle

Independent design recommendation: organize broad areas and refine only as needed for traceability. A readable hierarchy helps navigation; depth alone does not establish more accurate coverage.

In current documentation, create a folder from a Requirements folder and create a RequirementSet within it. Select Create Requirement on the RequirementSet mini toolbar. Requirement types beyond the default can be configured by administrators.

Basic Weighting

Weight column

New Requirements have weight 1. Set weights with stakeholders to express relative business risk; the Weight column contains those values. Do not confuse direct weights with the 0–10 input scale documented for Frequency class and Damage class.

Top-down entry order

Independent planning technique: agree on broad business areas before detailed criteria so priorities are consistent. This is a suggested workflow, not an enforced Tosca entry order.

Complex Weighting

Why complex weighting exists

A single linear scale often can't distinguish importance clearly enough (is this a 3 or a 4?). Complex Weighting instead asks two separate business questions per Requirement and lets Tosca calculate the Weight for you.

The formula

The 2024.1 column reference documents Weight = 2^Frequency class × 2^Damage class; each class ranges from 0 to 10. For Frequency 3 and Damage 2, the result is 8 × 4 = 32. These are relative risk estimates, not exact monetary predictions.

Independent planning recommendation: discuss frequency and damage estimates with business stakeholders and apply the agreed scale consistently.

Using Requirements as a dashboard

Contribution (%)

The 2024.1 reference describes Contribution (%) as a Requirement’s weighted share of its RequirementSet, with sub-Requirements calculated relative to their parent. Contribution is an importance allocation, not proof that tests passed.

Relative Weight (%)

The reference defines Relative Weight (%) as the Requirement weight divided by the total RequirementSet weight. For a flat set with positive total weight, the percentages sum to 100. Do not treat this as an unconditional rule for every level, filtered view or zero-total-weight structure.

Downstream links

Link TestCases to Requirements directly or through TestCase Links. Reporting distinguishes completed specification, executed tests and pass/fail state. Execution State also depends on result aggregation, which the 2024.1 reference says defaults to First. TestCase Design Coverage is separate and independent of Weight and WorkState.

Keeping Requirements up to date

Current documented update behavior

Tosca On-Premises 2026.1 documents AutoCalculateRequirements as off by default. A linked test change can leave calculated Requirement values outdated; the blue exclamation indicator identifies stale RequirementSets.

Manual refresh

Right-click a RequirementSet and choose Update Outdated Values, or use Update Outdated Values in the Requirements dynamic menu to recalculate all outdated values.

Enable AutoCalculateRequirements under Project → Settings → Commander → General → Advanced, then restart Tosca. Automatic recalculation can cause considerable waits in large repositories.
