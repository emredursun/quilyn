Scanning a Local XML File

XML as a table-like data source

An XML file has a table-like structure and is effectively scanned much like a database. This lesson uses AddressBook.xml, containing pre-populated contacts (Name, Company, Email, Telephone, Address) — representing, for example, an internal HR system's offline employee contact list that needs its add/remove/verify operations tested.

Sending a Request on an XML scan returns an error, and the Response view is always completely blank. Unlike SOAP or REST, an XML scan isn't sending data anywhere — there's no server to respond, so there's nothing to populate a Response with.

Inside the XML Module

No Technical View for XML Modules

Unlike REST/SOAP Modules, an XML Module has no Technical View tab — instead, the XML elements are stored directly within the Module itself.

Resource attribute

Rather than manipulating the XML file directly on disk, Tosca Commander uses the Resource key to load the XML file temporarily into RAM. If a mistake happens during a test run, the original file on disk is never overwritten and no data is lost — the working copy lives only in memory until explicitly saved.

The top-level container element (e.g. "AddressBook") holds every XML element and sub-element. Irrelevant elements (e.g. an unused "Fax" field) can simply be deleted from the Module — but remember to also update/synchronize any TestCase values already pointing at a deleted element.
