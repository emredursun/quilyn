Building a Complete API TestCase

Worked example: add a new coffee shop branch, verify it was added, then delete it — the same three-step pattern (Create → Verify → Delete) introduced in the previous lesson, now fully wired up with real values and run end-to-end.

Official Best Practice: when Modules are updated in Tosca Commander, the TestStep will automatically be updated.

Module ↔ TestStep synchronization

As with UI automation, when a Module is updated in Tosca Commander, its linked TestStep — and by extension the whole TestCase — updates automatically. If you're unsure which Module a TestStep links to, select the TestStep and press Ctrl+J, or right-click it and choose "Jump to Module".

Adding Modules to an API TestCase

Like in UI TestCases, Modules can be added to an API TestCase either by dragging and dropping them from the Modules section, or with the Ctrl+T shortcut — both methods work identically to how you already add Modules in UI automation.

Test Configuration Parameters (TCP) in API TestCases

Just like in UI TestCases, add a Test Configuration Parameter — e.g. "Key" holding the Service Access Key — to every TestStepValue that needs it. This is far less laborious than updating the same literal value in every TestStep individually if the key ever changes, especially in long TestCases.

Buffering the ID from a Create step lets the Constraint ActionMode identify that exact new shop later (to Verify its name/city/country), and the same buffered ID is reused again in the Delete TestStep.

Updating Modules and TestCases from the API Scan

Official Best Practice: when updating Modules, both the Request and the Response need to be selected, in order to update both.
