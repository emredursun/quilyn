Build an independently specified API flow

Independent example: create a disposable resource, buffer its returned identifier, retrieve that resource and assert expected fields, then delete it where permitted. Do not assume every service uses a list Constraint or the same cleanup semantics. A passing run needs all required assertions, not just successful transport.

Create a custom TCP on a supported TestCase/folder or other configuration-bearing object, and reference it in values with {CP[Key]}. Child objects inherit the value; lower-level overrides apply. Do not create a separate TCP on every TestStepValue. Use the appropriate supported data type, including Password where suitable, and follow your project credential-handling policy.

Use TestStep context menu > Jump to Module or Ctrl+Shift+J to inspect the linked Module. Drag a Module onto a TestCase or use Ctrl+T to launch Search and Add TestStep; choose the intended result.

F9 controls show/hide context-sensitive objects, including DoNothing. The View menu hides steps/values with an empty ActionMode; this is not the same as hiding every empty Value, and hiding does not repair missing input.

Refresh selected Modules and inspect affected mappings

Open the affected Module through API Testing > API Scan > Open selected Modules, edit the message and click Update. Review each changed request/response Module; do not assume selecting only one refreshes all related artifacts.

Changed element mappings may require ModuleAttribute Update and Validate. Corresponding message updates do not guarantee every expected value, XPath or business assertion is correct. Inspect affected TestSteps and execute targeted tests.

Independent completion review

Check inputs, credential references, returned identity, assertions, mapping validity and cleanup. A WorkState label is workflow metadata rather than proof of exhaustive validation. Original Academy slides and end-to-end exercise execution have not been verified.
