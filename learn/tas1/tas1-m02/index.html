Model-Based Test Automation (MBTA)

Model-Based Test Automation

A testing technique in which Models capture the technical information and expected behavior of the SUT. Business data is fed into these models to steer and test the system — no coding required.

Advantages of MBTA

Three key reasons to choose MBTA over scripted automation:

  • Save effort — models are created by scanning the SUT, not written by hand
  • Readability — end-to-end tests are easy to read due to descriptive module and step names
  • Reduced maintenance — models are reusable; update once and all referencing TestCases benefit

MBTA is like building with LEGO: you scan your SUT once to create standardized bricks (Modules). Each TestCase is assembled by snapping bricks together. When the SUT changes, you update just the brick — not every model that used it.

What is a Module?

Module

A representation of a SUT section (page, form, or panel) that Tosca can interact with. Contains one or more Controls, each mapping to an individual UI element.

Control

A single UI element within a Module — such as a button, input field, or dropdown. Each Control has identifying properties Tosca uses to locate it on the SUT.

Module Attributes

Properties describing the module itself: its name, the technology it targets (HTML, WPF, SAP GUI), and the Controls it contains.

Steer

When Tosca executes a TestCase, it 'steers' the Controls in the SUT — meaning it interacts with them exactly as a user would: clicking buttons, entering text, selecting from dropdowns. Steering is the act of automated interaction with a Control.

Standard Modules

Standard Modules

Pre-built modules provided by Tricentis for common execution tasks — keyboard input, wait commands, file handling — that operate independently of the SUT.

Tricentis Standard Subset

The package distributed by Tricentis that contains Standard Modules. Import it into any workspace to immediately access utility modules without scanning.

XScan — Scanning the SUT

XScan

Tosca's built-in scanning tool that inspects web application elements through the browser and captures their technical properties to create Modules.

Launching XScan

XScan is launched from Tosca Commander. The standard method taught in AS1: right-click a Module folder in the Modules section and select Scan >> Application. XScan opens alongside the browser ready to inspect the SUT.

Module Naming Convention

Within XScan, rename the Module using the pipe character as a separator: Application | Page. Example: 'WebShop | Log In Page'. This ensures consistent, readable Module names across the workspace.

Wildcard (*) in Technical Properties

In XScan Technical Properties, the Title field accepts the wildcard character *. Setting Title to 'Demo Web Shop*' tells Tosca to match any window whose title begins with 'Demo Web Shop' — ensuring the Module works correctly across multiple SUT pages (e.g., Demo Web Shop, Demo Web Shop. Books).

Identifying Controls: 5 Methods

The 5 XScan Identification Methods

XScan provides 5 ways to identify a control. Properties is the default; the other 4 handle scenarios where properties alone are insufficient:

  • Properties (default) — uses stable HTML attributes (ID, name, class) to directly match the control
  • Parent — uses the parent container element to scope the search; useful when a control's own properties are shared by multiple elements on the page
  • Anchor — uses a stable nearby element as a reference point; ideal for dynamic controls
  • Image — identifies the control by a visual screenshot match of its appearance
  • Index — identifies the control by its ordinal position within its parent container
AspectIdentify by PropertiesIdentify by Anchor
How it worksUses stable HTML attributes (ID, name, class) directlyUses a stable nearby element as a reference point
When to useElement has unique, stable identifiersElement properties change between sessions
Reliability riskBreaks if the stable attribute changesBreaks only if the anchor element changes

Properties = finding a house by its street address (unique, direct). Anchor = finding a house by saying 'the blue building next to the post office' — useful when the address changes but the neighbour stays the same.

Anchor: Shortest Path vs. Coordinate

When using Identify by Anchor, Tosca locates the target control via one of two strategies:

  • Shortest Path — searches each DOM tree level for the target, starting from the anchor, going bottom to top up to the root element. Resolution-independent and robust.
  • Coordinate — finds the target by its exact on-screen coordinates relative to the anchor. Highly resolution-dependent — breaks if screen resolution changes.

The anchor control itself must be uniquely identifiable. If the anchor is not unique, neither the anchor nor its target controls can be reliably located.

ControlGroup

ControlGroup

A named grouping of related Controls within a Module. ControlGroups organize logically related UI elements (e.g., all category navigation links) under one named group, making TestCases easier to build and maintain.

ControlGroups exist inside Modules — they are not a TestCase construct. Their primary benefit is simpler TestCase authoring: reference the group once rather than each Control individually.
