Working in a Multiuser Environment

Multiuser Environment

Multiple testers work against a shared Tosca repository. To prevent conflicts, objects are checked out/locked while one person edits them. A colored bar next to an object shows its lock status.

  • A red bar next to an object = it is locked/checked out (not editable by you right now).
  • You CANNOT make any changes to a locked object.
  • If the locked object is a Module, you can STILL add/reference it in your own TestCases — using it does not require editing it.
  • A red bar does NOT mean 'no one is working on it' — the opposite: it is locked because someone holds it.

Key distinction for the exam: locked (red) = cannot EDIT, but a locked Module can still be USED/referenced in TestCases. Locking blocks modification, not consumption.

Conditional Statements: WHILE, IF, DO

Structure: Condition + Loop

A WHILE/DO statement has two parts you fill in: a Condition and a Loop (Exercise 23).

  • Condition — a Verify-type check that confirms a state (Exists==True, Visible==True, has a value, etc.).
  • Loop — the TestSteps Tosca repeats; it keeps running until the Condition is no longer met OR the max repetitions is reached.
  • Tip: use the Control Flow Diagram to see a visual representation of the statement.
StatementWhen block executesMin executionsUse when
WHILEWhile condition is TRUE0 (may never run)Polling until state changes; condition may already be met
IFIf condition is TRUE (once)0 (may never run)Optional branch — do X only if condition met
DOAlways once, then while condition is TRUE1 (guaranteed)Must execute at least once regardless of condition

WHILE = 'Keep stirring until the sauce thickens.' IF = 'If it's raining, take an umbrella; otherwise, wear sunglasses.' DO = 'Taste the sauce at least once, then taste again if it still needs salt.'

Recovery and CleanUp Scenarios

Scenario typeWhen it firesPurpose
Recovery ScenarioOn a common/unexpected error during a TestCase (e.g., stray pop-up)Recover the SUT so the TestCase can restart from a clean slate and continue
CleanUp ScenarioWhen a TestCase (and all its Recovery Scenarios) FAILSReset the SUT to a clean state so the NEXT TestCase runs unaffected

Key facts (Exercises 24 & 25)

Details that show up on the exam:

  • Recovery & CleanUp Scenarios do NOT work in the ScratchBook — only in the TestCase Section / TestCase / TestStep / TestStepValue level, or in a Reusable TestStepBlock.
  • Both are always contained within a Recovery Scenario Collection.
  • Recovery Scenario has a RetryLevel property (e.g., set to 'TestCase').
  • Recovery settings live in Settings >> TBox >> Recovery (On dialog failure / On exception failure / On verification failure → set to 'Recover').
  • A CleanUp Scenario can be set at the same levels as Recovery and does NOT require a Recovery Scenario to be present.

Exam trap: CleanUp does NOT run 'always after every TestCase (pass or fail)'. It fires when the TestCase FAILS (and any Recovery has also failed), to reset the SUT before the next TestCase. Recovery tries to save the CURRENT TestCase; CleanUp prepares a clean slate for the NEXT one.

Recovery Scenario = a safety net that tries to catch the current test when it stumbles (e.g., closes a stray pop-up) so it can carry on. CleanUp Scenario = the reset crew that, when the test has truly failed, clears the stage so the next test starts fresh — invaluable for overnight/unattended runs.

Dynamic Comparison (XBuffer), Parent Control & Dynamic ID

Dynamic Comparison — XBuffer {XB}

A way to verify a string that contains a DYNAMIC part. {XB} excludes the dynamic portion from the comparison and (optionally) buffers that portion for reuse. Use it for messages with auto-generated numbers, timestamps, etc. that change every run.

  • Syntax: verify 'Order number: {XB[OrderNumber]}' with ActionMode Verify.
  • The static text ('Order number: ') is checked; the dynamic part is excluded from the match.
  • The excluded/dynamic value is stored in the buffer named inside the brackets (here: OrderNumber).
  • You can then reuse {B[OrderNumber]} later for verifications or to steer the app.
  • Tip: use the blue downward arrow in the Value cell to insert correct XBuffer syntax; set ActionMode to Verify when recording XBuffers.

Parent Control (Identify by Parent)

Identifies a UI element relative to its stable parent container. Used when scanning pages with REPEATING elements (e.g., a list of orders) where a child (order number, total, Details button) is not unique on its own but becomes identifiable once its parent DIV is specified.

  • During XScan, select the parent DIV first, then the child controls within it.
  • Deselect unstable properties (e.g., InnerText) and use stable ones (e.g., OuterText = 'Order Number:*').
  • Wildcards (*) handle the varying part of the text.

Dynamic ID

Handles elements whose ID attribute is generated at runtime (e.g., 'btn_7823', 'btn_4910'). Created via XScan using an identification method other than the literal ID — a pattern/partial match or identification by parent.

ExplicitName, TBox Set Buffer, ResultCount & RowCount

ExplicitName

A Configuration Parameter (named 'ExplicitName', Value = True) added to a ModuleAttribute. It lets Tosca steer the generated TestStepValues by INDEX and handle dynamic changes — so you can rename a TestStepValue (e.g., to '#1') and steer the repeating/dynamic control by its position.

  • Added in the Module Attribute's Properties tab as Configuration Parameter ExplicitName = True.
  • Then in the TestCase you can rename the generated TestStepValue (e.g., 'Order Overview' → '#1').
  • Steer by index handles dynamic repeating elements (works together with Parent Control / Dynamic ID).

TBox Set Buffer

A Standard Module that sets/resets a named buffer's value. Use it to initialize a buffer, store a timestamp, or perform a calculation and store the result. Add the Module as a TestStep, rename the TestStepValue '<Buffername>' to your buffer name, enter the value, ActionMode Input.

  • Example: rename '<Buffername>' to 'NumberOfItems', value 3, ActionMode Input.
  • Can hold a MATH result: value {MATH[{B[CartItems]}-1]} to store a calculated number.

ResultCount

Counts the occurrences of a particular value in a table/list, independent of its position. Used in a Verify to assert how many matching items exist. Syntax in the Value cell: ResultCount=={B[NumberOfItems]} with ActionMode Verify.

  • Example: verify a Digital Downloads list has the expected number of items: Item ResultCount=={B[NumberOfItems]} (Verify).
  • Can also buffer the count: ResultCount->CartItems with ActionMode Buffer, to reuse the number elsewhere.

RowCount & ColumnCount

Functions that count the TOTAL number of rows / columns containing data in a table — INCLUDING the header row/column. Used to steer through a whole table or capture its size.

  • Syntax: in the table's value column, enter RowCount==RowNum (RowNum = buffer name), ActionMode Buffer.
  • The result INCLUDES the header — a 4-data-row table buffers RowNum = 5 (4 rows + 1 header).
  • ColumnCount works identically for columns.
  • Common pattern: buffer RowCount, then subtract the header with {MATH[{B[CartItems]}-1]} to get the real data-row count.

RowCount/ColumnCount INCLUDE the header. If you need the number of DATA rows only, subtract 1: {MATH[{B[RowNum]}-1]}. Forgetting the header is a common off-by-one error.

Repetition on Folder Level & ActionMode Constraint

Repetition on Folder Level

Repeats the TestSteps inside a TestStepFolder a specified number of times, set in the FOLDER's Properties (Attribute 'Repetition'). The count can be static or a buffer (dynamic). This is how you repeat TestSteps in a TestCase — an alternative to a WHILE statement.

  • Set on a TestStepFolder → Properties → Attribute 'Repetition'.
  • Value can be a buffer, e.g., {B[ActualCartNumber]}, to repeat a dynamic number of times.
  • Inside the loop, use the variable ${Repetition} (e.g., rename a table's <Row> to ${Repetition}) so each iteration acts on the next row.
  • Example: empty a shopping cart by repeating the 'remove row' steps once per item — without a WHILE statement.

ActionMode Constraint

Limits (constrains) the search within a table/list to identify ONE specific item, regardless of where it sits in the table. You set constraining values on one or more cells; Tosca finds the matching row, then acts on it (e.g., select its Remove checkbox).

  • Set ActionMode Constraint on the cell(s) that uniquely identify the target row.
  • Example (Exercise 31): Product(s)='Music 2' (Constraint) + Price='*10.00*' (Constraint) → finds that exact row.
  • A combination of constraining cell values narrows down to the single intended item.
  • After the row is identified, another cell/action (e.g., Remove checkbox = True, Input) operates on it.

Exam trap: ActionMode Constraint is NOT a 'read-only existence check' and NOT for verifying values. It IDENTIFIES one specific item in a list/table of similar items by constraining on cell values. (Confirmed Knowledge Check answer.)

ActionModePurposeExample
VerifyCompare a control's value to an expected valueSub-Total == 28.00
SelectNavigate/pick a table row/column or dropdown without steeringSelect the Products table, a <Row>, a <Cell>
ConstraintIdentify ONE specific item in a table by constraining cell valuesProduct='Music 2' + Price='*10.00*' → that row
