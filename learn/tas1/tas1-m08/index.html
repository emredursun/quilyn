Multi-user editing and use

Green checkout indicators mean you hold the object; red means another user holds it; white identifies a new object. Inspect checkout details rather than assuming every lock belongs to another person.

A Module held by another user cannot be edited by you, but its existing definition can still be referenced by your editable TestCases. Checkout is an editing coordination mechanism, not a guarantee of test readiness or success.

Conditions and bounded loops

IF evaluates Conditions, then executes THEN when true or optional ELSE when false. It is not a loop. WHILE checks before its Loop and may run zero times; DO runs its Loop before checking and normally runs at least once.

WHILE and DO have MaximumRepetitions, default 30, to bound iteration. A false condition is control-flow information and does not itself fail the overall test. Bound polling and inspect what happens when the maximum is reached.

Independent practice: initialize a numeric buffer, evaluate it below a small limit and increment it in the loop. Use TBox Evaluation Tool for buffer conditions. This is not the verified Academy Exercise 23 procedure.

Recovery and CleanUp

Create Recovery Scenario Collections on TestCases or TestCase folders. Enable the relevant dialog, verification or exception failure handling through TBox Recovery settings, or override those settings with TCPs. ScratchBook does not support Recovery; exercise it through an ExecutionList.

RetryLevel chooses the failure granularity and the point of resumption: TestStepValue, TestStep or TestCase. It does not describe the object where the collection must be created. Successful Recovery retries from that level; repeating a whole case may duplicate setup or side effects.

When Recovery fails, CleanUp attempts to restore the environment for subsequent execution. It is not an always-run teardown for every passing case. Scenarios live in the collection and are tried in order with higher-level fallback.

NonGUI recovery does not support TestStepValue RetryLevel. Exception Recovery inside conditional statements is unsupported with TestStep/TestStepValue RetryLevel. Review these boundaries before designing retries.

Dynamic strings and stable identification

With Verify, Order number: {XB[OrderNumber]} checks the static text while capturing the variable substring in buffer OrderNumber. Read it later with {B[OrderNumber]}; the bracket content is the buffer name, not a fixed expected order ID.

Start with stable, unique properties. If they cannot distinguish a control, select a stable parent before the child and validate uniqueness within that scope. A parent alone does not distinguish three identical child buttons; an additional stable discriminator or justified index is needed.

Changing IDs can use a wildcard for the variable suffix, provided the remaining criteria are unique. Positional indexes can become invalid when the UI changes. ExplicitName permits editing a TestStepValue name; it does not create a stable technical ID in the SUT.

Names, buffers and counts

ExplicitName=True on an XModuleAttribute allows editing its referenced XTestStepValue name; a semicolon-separated value range is another supported form. The meaning of names or # indexes depends on the control type. It is not a universal dynamic-ID repair.

TBox Set Buffer uses a named ModuleAttribute: Input writes the value, Verify checks an existing value. Dynamic expressions can supply values. It does not read the SUT merely because a buffer was named.

ResultCount has two contexts. A general control property counts matching current nodes, for example .ResultCount==5 with Verify. Table ResultCount counts constrained cells, excludes configured headers and needs table Select plus cell Constraint; row/column Verify limits scope. Choose the intended context.

For a table, RowCount and ColumnCount measure table dimensions. Inspect the actual header configuration and returned count before converting it to data-only counts; do not subtract one blindly when the table has no header. Buffer syntax uses a property arrow, for example RowCount->RowNum. Header-relative $ positions differ from absolute # positions.

Repetition and constrained table actions

For a known or dynamically evaluated non-negative count, use Repetition on a TestStepFolder, either in the Details column or Properties. It applies to folders inside a TestCase, not manual tests or parallel execution with AOS. {REPETITION} and {REPETITION[FolderName]} are documented expressions for checking repetition.

When removing rows, positions shift. Repeatedly remove the current first data row after verifying the count/state, or identify each target by a stable business key. Incrementing the row position after deleting earlier rows can skip items.

Constraint restricts the search for the parent row/node using child values. Require unique matching business values or a deliberate index among matches. Then use the correct action on an embedded Remove checkbox/control. Select navigates to nodes, Verify checks values and WaitOn waits within a timeout; they serve different purposes.
