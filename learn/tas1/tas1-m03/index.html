TestCase Structure

TestCase

An ordered sequence of TestSteps that defines a complete test scenario. Stored in the TestCases section; references Modules for its steps.

TestStep

A single action or verification within a TestCase, created by referencing a Module or a specific Control. Each TestStep represents one interaction with the SUT.

TestCaseFolder

A container for organizing TestCases in a hierarchy. Can be nested. Best practice: organize by feature or business process. Inside a TestCase, TestSteps are further grouped using TestStepFolders (e.g., Precondition, Process, Postcondition).

A TestCase is a recipe: each TestStep is one instruction ('add flour', 'stir'). The ingredients (Modules/Controls) come from the pantry (Modules section). You follow the steps in order to produce the dish (test result).

WorkState progression: PLANNED → IN_WORK → COMPLETED. Set COMPLETED when all work is done and the TestCase is ready for a reviewer.

Test Configuration Parameters (TCP)

Test Configuration Parameter (TCP)

A reusable value defined at TestCase or folder level, referenced across multiple TestSteps. Centralizes test data so changes are made in one place.

TCP Syntax (confirmed exam question)

To reference a TCP in a TestStep value field, use exactly: {CP[NameOfTheTCP]}

  • Outer curly braces { } are mandatory
  • CP prefix in square brackets [ ] is mandatory
  • Parameter name goes inside the square brackets

Common wrong formats: CP[Name] (missing braces), {TCP[Name]} (wrong prefix), [CP{Name}] (brackets and braces swapped). Only {CP[NameOfTheTCP]} is valid.

ActionModes

ActionModeDirectionWhat it does
Input→ TO SUTEnters a value into a Control (types text, selects dropdown option)
Verify← FROM SUTReads a Control's value and compares to expected — fails if mismatch
Buffer← FROM SUT (stored)Reads a Control's value and stores it for later reuse in the same TestCase
WaitOn← FROM SUT (waiting)Pauses execution until a Control reaches a specified state or value

ActionModes are verbs: Input = write, Verify = check, Buffer = copy, WaitOn = wait. The same Control can be used with different verbs in different TestSteps.

Populate Your TestCase — TestStepValues

ModuleAttribute

A representation of a Control (button, text field, label, etc.) selected during scanning. When a Module is dragged into a TestCase, each ModuleAttribute becomes a TestStepValue.

TestStepValue

The combination of an ActionMode, a Value, and a DataType for a specific Control inside a TestStep. Tells Tosca exactly what to do with that Control during execution.

DataType

Specifies the type of value being entered. The 5 DataTypes are: String, Date, Numeric, Boolean, Password.

  • String — default; plain text
  • Numeric — use for numbers so that 10 and 10.00 are treated as equal
  • Date — use for date values
  • Boolean — use for True/False values
  • Password — masks the value; use for credentials

Always set DataType to Numeric when comparing or verifying number values (prices, quantities). Without it, '10' and '10.00' may not match — causing false test failures.

F9 key: toggles between showing all TestStepValues and showing only those with an action specified. Useful for large TestSteps.

ScratchBook — Run a Test

ScratchBook

A built-in Tosca capability for trial runs of TestSteps and TestCases before final execution. Results are temporary and overwritten with each new ScratchBook run.

ScratchBook results are NOT saved. Each new run overwrites the previous result. Use ScratchBook for debugging only — final execution goes in ExecutionLists.

Dynamic Values

Dynamic Values

Expressions evaluated at runtime to generate values dynamically — current date, random text, calculated numbers. Written inside curly braces using Tosca's expression language. Syntax: {COMMAND[parameter1][parameter2]...}

Buffer Syntax

To recall a previously buffered value, use: {B[BufferName]}

  • {B[PriceBlueJeans]} — recalls the value stored under that buffer name
  • Buffer name must match exactly (case-sensitive) the name given when the Buffer was set
  • XBuffer for dynamic parts: {XB[BufferName]} — reads and buffers only the dynamic portion of a string

MATH Functions

Perform calculations using static values or Buffer references. Syntax: {MATH[expression]}

  • {MATH[{B[PriceBlueJeans]}*25]} — multiplies buffered price by 25
  • {MATH[{B[SubTotal]}+10.00]} — adds 10.00 to the SubTotal buffer
  • Operators supported: + (add), - (subtract), * (multiply), / (divide)
  • Tip: right-click Value field → 'Translate value' to test a MATH expression before running

Random Values

Generate unique random values at runtime to avoid test data collisions.

  • {RND[7]} — 7-digit random integer (max 18 digits)
  • {RND[100][999]} — random integer between 100 and 999
  • {RANDOMTEXT[10]} — random 10-character string (letters and numbers, max 1024)
  • {RANDOMREGEX["^[A-Z][a-z]+[0-9]{4}$"]} — random string matching a regex pattern

Date / Time Expressions

Structure: {FUNCTION[start][offset][format]}

  • FUNCTION: DATE, TIME, DATETIME, DAY, MONTH, YEAR, MONTHFIRST, MONTHLAST
  • [start]: leave empty [ ] to use today's date as the reference
  • [offset]: d=days, w=weeks, M=months, y=years, h=hours, m=minutes, s=seconds — e.g. [-3y] = 3 years ago, [+4M] = 4 months ahead
  • [format]: MM=2-digit month, yyyy=4-digit year, dd=2-digit day, MMM=3-letter month abbreviation
  • Confirmed exam example: {MONTHLAST[][-3y][MMMyyyy]} = last day of month, 3 years ago, in format Jun2022
  • Exercise 15 example: {DATE[][+4M][MM]} = expiration month +4 months as 2-digit; {DATE[][+3y][yyyy]} = expiration year +3 years as 4-digit

Libraries

Library

A folder in the TestCases section containing reusable TestCase sequences. Other TestCases reference Library entries instead of duplicating steps.

Libraries are stored in the TestCase section — NOT in the Modules section, NOT in Requirements. This is a confirmed exam question: 'In which section are Libraries used? → TestCase.'

Reusable TestStepBlock (RTSB)

An individual TestStep sequence stored inside a Library. Can be dragged from the Library into any TestCase.

Reusable TestStepBlock Reference

When an RTSB is dropped into a TestCase, it appears as a Reference with '_Reference' appended to its name (e.g., 'Precondition_Reference'). It remains linked to the Library — any change in the Library propagates to all TestCases using that reference.

  • Drag RTSB from the Library folder, drop into the TestCase or TestStepFolder.
  • The dropped block is named [OriginalName]_Reference.
  • All TestCases using the same RTSB are updated simultaneously when the Library block changes.
  • Use this when you want a single source of truth (e.g., a shared Login flow).

Resolve the Reference

Replaces a Library reference inside a TestCase with an inline copy of the Library's steps — making the TestCase self-contained with no external dependencies.

  • Right-click the RTSB Reference → 'Resolve Reference'.
  • Icon changes after resolving — the block is no longer linked to the Library.
  • After resolving, changes to the Library NO LONGER affect this TestCase.
  • Can be undone with Ctrl+Z ONLY before saving. After saving, the resolve is permanent.
  • Use when a specific TestCase needs a different version of the standard flow.

Library folders are sorted alphabetically automatically. When dragging RTSBs, drag individual folders (containing TestSteps) — not the top-level parent folder.
