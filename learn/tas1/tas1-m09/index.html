The Big Picture — How Tosca Sections Connect (Mindmap)

The five Tosca Commander sections

Each section owns one job; together they form the automation workflow.

  • Modules — the technical map of the SUT, collected via XScan. To steer a control it must be uniquely identifiable (properties, anchor, parent).
  • TestCases — a sequence of actions (the path through the application) built from Modules.
  • Execution — runs TestCases/folders; organize with ExecutionLists; drag a TestCase onto an ExecutionList to create an ExecutionEntry; add Recovery Scenarios to keep runs going.
  • Requirements — plan test processes and monitor risk coverage (functional & non-functional); TestCases link here.
  • TestCaseDesign — NOT covered in AS1 (centralized test data; see the AS2 course).

Syntax Cheat Sheet — Text Expressions & Random Values

General syntax

All Tosca expressions follow: {COMMAND[Parameter1][Parameter2]...} — curly braces outside, square brackets for each parameter.

ExpressionSyntaxExample / Note
Buffer (recall){B[Name]}{B[Automobile]} — re-enters the saved value
XBuffer{XB[Name]}Reads/buffers the DYNAMIC part of a string. Name may include numbers but must NOT be only numbers
Test Config Parameter{CP[Name]}{CP[Browser]} — reuse a central config value
Random integer (length){RND[n]}{RND[7]} = 7-digit number. Max 18 digits
Random integer (range){RND[min][max]}{RND[-789][123]} — negatives allowed
Random decimal (length){RNDDECIMAL[len][dec]}{RNDDECIMAL[5][2]} = 5-digit, 2 decimals
Random decimal (range){RNDDECIMAL[dec][min][max]}{RNDDECIMAL[4][130][200]}
Random text{RANDOMTEXT[n]}n-char letters+numbers. Max length 1024
Random regex{RANDOMREGEX["pattern"]}{RANDOMREGEX["^[A-Z][a-z]+[0-9]{4}$"]}

Taught in depth in Section 03 (Buffer/MATH/Random), Section 05 (TCP), and Section 08 (XBuffer). This is your one-stop syntax lookup.

Dynamic Date & Time — Quick Reference

Structure

{EXPRESSION[BASEDATE][OFFSET][FORMAT]} — all variables are CASE SENSITIVE.

  • Leave [BASEDATE] empty [] to use today's date.
  • Offset units: d=days, w=weeks, M=months (capital!), y=years, h=hours (1-12), H=hours (0-23), m=minutes, s=seconds.
  • Format codes: %d=1-digit day, dd=2-digit day, %M=1-digit month, MM=2-digit month, MMM=3-letter month, MMMM=full month name, yy=2-digit year, yyyy=4-digit year.
  • Basedate default formats: Date = dd.MM.yyyy, Time = hh:mm tt, DateTime = dd-MM-yyyy hh:mm tt.
ExpressionMeaningExample output
{DATE}Full date30.04.2021
{TIME}Current timehh:mm tt
{DATETIME}Date + time stampdd-MM-yyyy hh:mm tt
{DAY} / {MONTH} / {YEAR}Current day / month / 2-digit year30 / 12 / 15
{MONTHFIRST}First day of the month01.12.2021
{MONTHLAST}Last day of the month31.12.2021
{MONTHLAST[][-3y][MMMyyyy]}Confirmed exam examplee.g. Jun2022

{L..}Localized to system settings (LDATE/LDAY/LMONTH/LYEAR){LDATE} = Monday, December 20, 2021
{N..}Always double figures (NDAY/NMONTH/NYEAR){NDAY} = 30 · {NMONTH} = 12

RowCount & ColumnCount — Quick Reference

RowCount / ColumnCount

Functions that count the TOTAL rows / columns containing data in a table — INCLUDING the header row/column.

  • Syntax in the table's value cell: RowCount==RowNum (RowNum = buffer name), ActionMode Buffer.
  • Result INCLUDES the header: a table with 4 data rows buffers RowNum = 5.
  • ColumnCount works identically for columns.
  • For data rows only, subtract the header: {MATH[{B[RowNum]}-1]}.

Use it to steer a whole table, size a loop/repetition dynamically, or verify an expected count. Taught in Section 08; here as a quick reference.

Resolve the Reference — Quick Reference

Reusable TestStepBlock (RTSB) Reference

When you reuse a Library RTSB in a TestCase, it appears as a Reference and stays LINKED — any change in the Library propagates to every TestCase that uses it.

Resolve the Reference

Unlinks a specific referenced block from the Library so you can customize it in that one TestCase without affecting the others.

  • Right-click the referenced TestStepBlock -> 'Resolve Reference' (the icon changes).
  • After resolving, Library changes NO LONGER affect this block.
  • Revert with Ctrl+Z / Undo ONLY before saving — after saving it is permanent.

Use when one TestCase needs a different flow from the shared Library version. Taught in Section 03; here as a quick reference.

What Makes a Good TestCase — Best-Practice Job Aid

TestCase

A good TestCase is complete, readable, and self-contained.

  • Contains MULTIPLE TestSteps — an entire sequence through the application, rarely just one.
  • Marked with a WorkState: Planned, In Work, or Completed.
  • Once Completed, link it immediately to its Requirement AND its ExecutionList.
  • Contains NO IF statements; use Loops and Conditions only when necessary.

TestStep Folders

Organize TestSteps into clearly named folders.

  • Recommended structure: Precondition, several Process folders, Postcondition.
  • Every TestCase should include a verification.

Modules

Reusable technical building blocks.

  • A single Module creates multiple TestSteps and can be reused any number of times.
  • A Module contains MULTIPLE controls (never just one) — all controls needed to steer one page.
  • Identify controls using the most STABLE methods available.

Point to remember: establish a clear naming convention for every element. Any user should recognize an element from its name alone.
