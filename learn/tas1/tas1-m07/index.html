Business criteria and structure

Functional criteria describe behavior, such as processing a payment; non-functional criteria describe quality, such as a measurable response-time target. Define testable acceptance criteria with stakeholders.

Folders organize RequirementSets; sets contain Requirements. Folders and Requirements may contain further structure, so this is a basic grouping example, not exactly three compulsory levels. TestCase links belong to the corresponding Requirement.

Associate relevant ExecutionLists with the RequirementSet, directly or through its ExecutionList configuration. An ExecutionEntry can also create a TestCase link on a Requirement; associated-list linking depends on AlwaysAdd, AskUser or NeverAdd configuration.

Requirements Management needs its AddIn enabled for editing and a valid license. Linking newly created objects in multi-user workspaces requires check-in. These are separate concerns from WorkState.

Weights and business risk

New Requirements default to weight 1. Teams can enter weights manually, or calculate them with Damage class and Frequency class. The classes use a 0–10 scale; the resulting Weight is not restricted to 1–10.

With both classes, Weight = 2^Damage class × 2^Frequency class. For damage 3 and frequency 4, this yields 128. With one class, use its corresponding power of two. Higher weights increase relative contribution to risk-based metrics.

Relative Weight compares a weight with the total set weight. For parent Requirements, Aggregated Weight can instead sum directly subordinate weights. Weight is a business prioritization input, not evidence that tests passed.

Linking and interpreting coverage

Create a TestCase Link placeholder or drop a TestCase directly onto its Requirement; one case can link to a given Requirement only once. COMPLETED is not required to create the link. It affects the coverage calculation: PLANNED contributes 20%, IN_WORK 50% and COMPLETED 100%.

For explicit execution grouping, create an ExecutionList configuration on the RequirementSet and drop the intended lists into it. Review which configurations are enabled. A link alone does not demonstrate that a compliance criterion passed.

AutoCalculateRequirements defaults to Off. For stale values, use Update Outdated Values on the RequirementSet. Automatic calculation can be enabled in Commander advanced settings and requires restart; assess repository wait times.

Coverage Specified, Coverage Executed and Execution State are distinct metrics. They consider weights and WorkState, rather than simply counting linked tests. Under default Result Aggregation First, use the first Passed/Failed result across associated lists, skipping No Result; Each considers all results. Neither means always use the newest run.

Independent inspection exercise: link an IN_WORK test and inspect its weighted coverage, associate an execution list, refresh values and examine its result. Then compare a COMPLETED state and deliberate aggregation setting. This documentation-based exercise was not executed in Tosca.
