Requirements: Types & Hierarchy

Requirements

Criteria the system under test (SUT) is expected to fulfill. They map business requirements to checks that confirm the application works properly.

  • Functional requirement — a functionality the SUT must carry out (e.g., 'the web shop must be able to process payments').
  • Non-functional requirement — a quality/operational attribute rather than a specific behavior (e.g., security, reliability, performance, maintainability, scalability, usability).
LevelNameRoleWhat links here?
TopRequirementFolderOptional grouping that structures RequirementSets one level upNothing (organizational)
MiddleRequirementSetRepresents an aspect of the app (e.g., 'Webshop Frontend'); organizes RequirementsExecutionLists link HERE
BottomRequirementIndividual, atomic, testable criterionTestCases link HERE

Two different link targets (confirmed by Exercise 22): TestCases link to individual Requirements (bottom level). The ExecutionList is dragged onto the RequirementSet (middle level, e.g., 'Webshop Frontend') — NOT onto an individual Requirement.

Think of a filing cabinet: RequirementFolder = the cabinet, RequirementSet = a drawer, Requirement = an individual document. You attach a TestCase sticky note to a specific document, but you register the whole ExecutionList against the drawer (the Set).

Requirement Weights

Requirement Weight

A calculated risk score (integer 1–10) representing the priority and risk of a Requirement. Derived automatically by Tosca — not manually entered.

  • Input 1: Frequency Class — how often the failure occurs if the requirement is unmet
  • Input 2: Damage Class — the severity of the impact if the requirement fails
  • Formula: exponential function of (Frequency Class, Damage Class)
  • Output: integer from 1 (lowest risk) to 10 (highest risk)

Weight is CALCULATED by Tosca from the two class inputs — it is not a field you type into directly. This is a confirmed AS1 exam question.

Linking TestCases and ExecutionLists to Requirements

Linking TestCases

Drag a COMPLETED TestCase onto an individual Requirement to create a link. This provides traceability: which tests cover which requirements. Link at the Requirement (atomic, bottom) level.

Linking ExecutionLists

Drag an ExecutionList onto a RequirementSet to associate its execution results with that set of requirements — enabling execution/coverage reporting across the whole set.

Update Outdated Values

After linking TestCases and ExecutionLists, right-click the RequirementSet and select 'Update Outdated Values' to refresh the calculated coverage and execution status. Without this, displayed values may be stale.

  • Right-click the RequirementSet (e.g., 'Webshop Frontend') → 'Update Outdated Values'.
  • Recalculates coverage and pulls in the latest execution results from linked ExecutionLists.
  • Run it whenever links change or new results come in.

Test Coverage

Once TestCases are linked, Tosca shows requirement coverage — which requirements have linked tests (covered) and which do not (unverified).
