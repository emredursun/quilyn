Where TDS fits in Tricentis Test Data Management

Test Data Management (TDM)

The umbrella term for Tricentis' holistic data solution, made up of several components: Test Data Service, TDM Studio, qTest, and Flood.

qTest and Flood are separate Tricentis products with their own dedicated training — outside the scope of TDS2.

TestCase Design vs. Test Data Service

Recap: TestCase Design (TDS1)

TestCase Design structures TestCases to cover every variant and pathway of the SUT, producing the combinations needed for comprehensive coverage. Static data values can be added, but this data is non-consumable — it can be reused multiple times and simultaneously by different TestCases.

Test Data Service (TDS2)

TDS acts as a data repository where records can be stored, retrieved, updated, and have their status viewed by multiple people. Unlike TestCase Design's static data, TDS stores consumable/dynamic data that regularly changes — this data can generally only be used once, by one machine, at a time.

Test data, defined

Any information fed into the application under test — usernames, passwords, credit card numbers, customer details, reference data, and more.

Two core challenges TDS solves

Challenge 1 — Acquiring specific test data

Complex database structures often require specific data that isn't available in the SUT or is hard to access. A direct SQL query would normally retrieve it, but suitable SQL statements are often missing, or slow and difficult to write. Existing data (production data, or data created in an earlier test) is another option, but retrieving it manually is time-consuming. TDS solves this either way: it can generate the needed test data on demand, or store and adjust already-available data — both with fast response and run times.

Challenge 2 — Tracking the state of test data

An earlier test frequently changes the data it touched. If inaccurate, old, or already-consumed data gets reused by another TestCase, results become unreliable — a risk that grows sharply when end-to-end TestCases span several days or run on multiple machines.

Worked example — why state matters

Two TestCases logging into the same SAP account to modify personal details can't run at the same time; the second must wait for the first to finish and then use the updated values. A more complex case — creating a bank customer, generating an account number, then processing a payment — needs each dynamic value (customer ID, account number) progressively updated in the TDS repository as it's produced, or a later step (like processing the payment) simply won't have a valid ID to work with.

How TDS keeps data stateful

TDS gives visibility into a multi-tester environment by adjusting each record's Status as it moves through the process, and prevents conflicting use of the same record through lock/unlock features. Data can also be created, retrieved, or updated through API calls, which further increases response time and agility when managing test data.
