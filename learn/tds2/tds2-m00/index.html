Test Data Service in a test-data workflow

Test-data management

A test-data workflow must provide usable inputs, keep necessary state and define how data is reused or retired. This lesson concentrates on Test Data Service, not a verified catalog of Tricentis product offerings.

This is an independent Tosca 2026.1 documentation-based introduction. The Academy video version and its historical product comparisons have not been verified.

TestCase Design vs. Test Data Service

Coverage planning with TestCase-Design

TestCase-Design models test combinations and concrete values through TestSheets, Attributes and Instances. It helps plan coverage and instantiate TestCase templates; it does not make an application input inherently safe for simultaneous use.

Item management with Test Data Service

TDS stores items that tests can select and change. Reuse depends on the test scenario and current data state. Stored items are not inherently single-use: a read can be non-locking, and a selected item can be used again after its lock is released if the scenario permits.

Independent input example

A practice login may use a disposable username and a fake password. A payment workflow may need an already-created practice account. Decide which inputs are valid before running the application actions.

Two core challenges TDS solves

Find suitable data

Prepare or import suitable practice data, then select an item matching the intended preconditions. A create operation stores an item; it is not a guarantee of automatic production-data masking or valid account provisioning in the application.

Track explicit changes

Verify the application result, then explicitly store any new identifier or state required by later tests. A property called Status is not automatically updated merely because an application action or TestCase completed.

Independent account example

Suppose two tests both change a practice account. Separate accounts may permit parallel execution; if one shared account is required, coordinate access and verify its current state. Do not turn this example into a rule that all account tests must run sequentially.

Locking has a defined scope

Find & provide item locks the selected item. Expert ReadOnly retrieves data without acquiring a lock; it does not unlock an existing one. Find releases its lock at execution completion, on failure or a new loop iteration. Locking test-data access does not automatically protect every application-side operation.
