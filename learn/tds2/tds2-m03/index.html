Creating records with a TDS Standard Module

Where the module lives

TDS Standard Modules are found under Standard Modules → Test Data Management → Test Data Service. To register a new record, add a TestStep and insert the module 'Test Data - Create & provide new record', which writes new entries into the TDS repository's table-like structure.

Using the module

Expand the module's Data structure Attribute and fill in every required Attribute and value — this is exactly what gets stored under the TDS type you select. The TestStepValue 'Existing or new TDS type*' lets you pick an existing type or create a brand-new one on the fly.

Alias name

What it's for

Alias name is an optional field that labels a specific record within a dataset. If left blank, the TDS type itself is used as the alias — e.g. the TDS type 'CustomerDetails' becomes the record's alias by default.

When it actually matters

Alias name exists to distinguish between different roles that share the same TDS type. For example, a customer could be either the sender or the recipient in a bank transaction — two roles with different tasks in the SUT that need to be tested separately. Without a distinct alias, both would be grouped under the same TDS type, and a TestCase could fail by testing a sender's flow when a recipient's data was actually needed.

This course doesn't use Alias names, since the scenario only involves one type of user (the customer).

Quick self-check

True or False: (1) If Alias name is left blank, it takes the name of the 'Existing Attribute' — FALSE, it actually takes the name of the TDS type, not any Attribute. (2) Alias name must be used when you have different record types performing different functions in the SUT — TRUE.

Viewing records and understanding the lock

Finding your data

On the Test Data Management page, the landing page shows every configured repository as a tile. Opening one reveals a Types column on the left (types created via Standard Modules appear in blue, each with a small green badge showing its record count). Selecting a type displays all of its records, table-like, on the right.

Once a record is found/retrieved, it is automatically locked — no one else in a distributed team can use it in a TestStep. It only unlocks automatically after the TestCase that retrieved it finishes executing. This is what prevents two testers from colliding on the same record.

Worked example: registering a DemoWebShop customer

Inputs and initial state

First name, last name, and email — already captured as Buffers from the registration TestCase — are fed into 'Create & provide new record' as its inputs. The Status Attribute is set to 'New', which flags freshly registered customers so they can be retrieved later specifically in that state. OrderNumber and OrderStatus are left blank at this point — they get filled in progressively as the customer moves through later steps (purchase, payment, etc).

So far this has run from Scratchbook. In a real project, TestCases like this should run from an Execution List, so results are properly reported and visible to the team.

Generating multiple records at once

Repetitions

To generate several test records in one go, set a Repetitions value on the relevant Execution Entry. From the Ribbon's Context Menu, choose Repetition, enter the desired count in the 'Replace with' field, and select 'Modify All'. A value of 5, for example, produces 5 test records. The same setting can also be changed directly in the Properties pane for that Execution Entry.
