Retrieving test records

TestData - Find & provide record

Retrieves a previously created record via a search query. The 'Existing TDS type*' field defines which dataset to search (e.g. CustomerDetails).

ActionMode Constraint

Restricts the search to records matching a specific condition — e.g. TDS attribute Status = 'New', to find only newly registered customers rather than any customer record.

Because this course's scenario has only one user type (the customer) and no Alias name was set in Lesson 2, Tosca automatically uses the 'Existing TDS type*' value itself to search — it looks in the CustomerDetails dataset for a record with Status = New.

Entering retrieved data: the {TD[...]} expression

Syntax

Once a record is found, its values are fed into the SUT using the {TD[...]} expression, entered directly in a TestStepValue's Value field — the same style of expression used elsewhere in the Automation Specialist courses. The part right after the opening brace is the command to retrieve a test record from the TDS repository; the part in square brackets identifies exactly which value, as TDSType.AttributeName.

Worked example

To log a newly registered customer into the DemoWebShop using their retrieved email address, the Value field would contain: {TD[CustomerDetails.Email]} — retrieve a record from the CustomerDetails type and use its Email attribute.

Updating a test record

TestData - Update record

Used whenever a record's data needs to change — e.g. once a newly registered customer adds an address, their Status should move from New to Active. Updating a record in TDS always works together with a search: you must first find the correct record, then apply the update to it.

Matching the search identity

The TestStepValue 'Existing alias name (record)*' on the Update module must match the value used earlier when the record was searched for — in this example, 'CustomerDetails'. The update itself targets a TDS attribute (Status) and supplies its new value (Active, replacing New).

Once the TestCase runs, the Status change is immediately visible in the TDS repository.

How the repository evolves through the order process

Payment processing — a two-step update

Step 1 (backend): non-UI Standard Modules search for a record with OrderStatus = Pending, then send non-UI requests carrying that OrderID plus the customer's email and password to the backend. Tosca verifies a 200 OK response, confirming the payment succeeded — this moves the status to Processing in the backend system itself, but NOT yet in TDS. Step 2 (repository sync): Tosca searches again for that same Pending-OrderStatus record, verifies the DemoWebShop now shows it as Processing, and only then updates the TDS repository's copy of that record to Processing.

The backend status and the TDS repository status change in two separate steps — don't assume TDS updates itself automatically just because the backend changed.

Moving consumed records to a new TDS type

Why move data at all

Once the full order process (including payment) has run, that customer's data is considered consumed. Moving it into a distinct TDS type keeps the repository stateful — it's immediately clear which records are still 'live' and which have already been used, which is especially valuable for a distributed team.

TestData - Move record to TDS type

Searches for records under the existing TDS type (e.g. CustomerDetails) and relocates them to a new type under a new name (e.g. CustomerDetails_Used). The TestStepValue 'Existing alias name (record)*' takes the CURRENT type's value (CustomerDetails), while 'Existing or new TDS type*' takes the DESTINATION type's value (CustomerDetails_Used).
