Retrieving test records

TestData - Find & provide item

Retrieves a previously created record via a search query. The 'Existing TDS type*' field defines which dataset to search (e.g. CustomerDetails).

ActionMode Constraint

Restricts the search to records matching a specific condition — e.g. TDS attribute Status = 'New', to find only newly registered customers rather than any customer record.

Existing TDS type chooses the search scope. Alias name identifies the retrieved item during the TestCase, not a search condition; if omitted in Find, the type name is used as its default.

Entering retrieved data: the {TDS[...]} expression

Syntax

Use {TDS[ResourceName.PropertyName]} in the Value field after finding or creating the item. ResourceName identifies the item by its alias, followed by the attribute name. Do not substitute the repository name or an arbitrary type name.

Worked example

Independent example: Find an item of type CustomerDetails with alias customer, then use {TDS[customer.Email]} to access its Email attribute. If Find instead omitted the alias, the default would be CustomerDetails, making {TDS[CustomerDetails.Email]} valid for that retrieved resource.

Updating a test record

TestData - Update item

Changes a known item's attributes through its alias. A usual workflow first finds the intended item, then supplies the alias to Update item; an item created earlier can also have an alias. Define changed attributes under Data structure with ActionMode Input.

Matching the search identity

Existing alias name (item) must identify the item already available to the TestCase. For an explicit alias customer, pass customer; only an omitted Find alias defaults to the type name. A synthetic Status change from New to Active is an explicit test-data update.

An application-side change is not itself a TestData Update item operation. Verify the application's expected state and explicitly maintain the repository data when the workflow requires it.

Independent synthetic order workflow

Explicit state maintenance

This is an independent practice example, not a verified Academy payment walkthrough. Keep the application's state assertion separate from the repository update, and handle failures before marking test data consumed. A generic successful HTTP response does not prove a business operation completed.

Do not treat an application response as evidence that TestData - Update item has run.

Moving consumed records to a new TDS type

Why move data at all

Once the full order process (including payment) has run, that customer's data is considered consumed. Moving it into a distinct TDS type keeps the repository stateful — it's immediately clear which records are still 'live' and which have already been used, which is especially valuable for a distributed team.

TestData - Move item to type

Moves a known item identified by Existing alias name (item) into Existing or new TDS type. With alias customer, pass customer and destination CustomerDetails_Used. The alias need not equal the source type. One move targets one known item, not every item in the source type.
