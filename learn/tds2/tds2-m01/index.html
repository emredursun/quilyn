Core TDS terminology

Test Data Service (TDS)

A server-based application with a web-based portal that displays test data in a table-like structure. This web page is called the Test Data Management page, or the Test Data Object Viewer, and can be reached from any browser by typing the right endpoint request.

How Tosca Commander and TDS talk to each other

The connection

Before any of this works, a connection must be established between Tosca Commander and Test Data Service through installation and configuration (covered in Lesson 1). Once set up, TestCases in Tosca are built to specify what should happen to the test data — the common functions being create, find, update, and delete. TDS Standard Modules exist specifically to perform these functions quickly.

The request/response flow

When a TestCase runs, Tosca Commander instructs the SUT what to do, and simultaneously exchanges a series of endpoint requests with TDS — creating, finding, updating, or deleting records as needed. Every change is reflected back in the TDS repository's table-like view.

Worked example: profile → file → upload

A 3-step process — create a user profile, create a file, upload the file — becomes 3 separate TestCases: (1) create a new user account, which shows up as a new entry in the TDS repository; (2) find/retrieve that account's data from TDS, log into the website with it, and create the file — the record is then updated to a new state in TDS; (3) retrieve the newly created file's data and use it to upload the file — the record is updated again to reflect that.

An analogy for the three roles

Tosca works like the project Manager, sending requests for what needs to be done. TDS plays two roles: the Reporter, giving a clear overview of project status, and the Document Controller, storing all the relevant documents (test records) under the right categories (types).

These steps are interlinked and can't be tested independently — you can't upload a file before the user profile and the file itself exist. In a distributed environment, TDS lets you lock data (like a newly created file) for exclusive use in your TestCase, so no one else can grab it mid-flow. Locking is covered in depth in Lesson 2.

This course's scenario: the DemoWebShop order process

We'll also test cancelling an order and deleting its data record. TDS Standard Modules drive every step, and each TestCase's results are reflected in the TDS repository as it runs.

How the repository evolves through the process

1) Adding an address moves a customer's Status from New to Active. 2) Adding items to the cart populates an 'items' column with the count. 3) Purchasing items creates an OrderNumber column and sets OrderStatus to Pending. 4) The payment is processed through non-UI commands, moving the backend status from Pending to Processing. 5) That change is then reflected in the TDS repository's OrderStatus field, Pending → Processing. 6) Once the order is fully completed, its Test Records are moved into a new TDS type called 'Used'.
