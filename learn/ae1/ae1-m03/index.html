Scanning a PDF

The PDF Scan

PDFs have no DOM and no accessible control tree — there is nothing to query for 'the invoice total field'. The PDF Scan solves this by letting you mark regions of the document as controls. Start it by right-clicking a Module folder and selecting Scan, or with the shortcut Ctrl+Shift+P, then choose the PDF file. The scan interface shows the document alongside the controls you are identifying.

Anchor controls: the core concept of this lesson

Why anchors exist

A control's absolute position on a PDF page is not stable. Add a line to an address block or let a table grow by one row and everything below it shifts. Identifying a control by fixed coordinates would break on the next document. An anchor control solves this by locating the target relative to another element instead of by absolute location.

How it works at runtime

At execution, the PDF Engine 3.0 searches the document for the anchor — the text or image you defined — and once it has found it, calculates where the target control must be in relation to it. So the target moves with its anchor, and a shifted layout no longer breaks identification.

The uniqueness condition is the one most often violated in practice. Choosing a column header that repeats on every page, or a label that appears in several table rows, gives the Engine no way to know which occurrence to anchor to.

Anchor accuracy

Exact match by default

By default Tosca looks for an anchor that is an exact match for the text or image you defined. That is the strictest and most predictable setting, and it is what you want whenever the anchor text is genuinely constant.

Lowering accuracy

When exact matching causes identification problems — typically with scanned or image-based PDFs where character recognition is imperfect — a lower level of accuracy can be configured through the OCR settings. This is a deliberate trade: you gain tolerance to recognition noise and lose some certainty about which element was matched.

Treat lowered accuracy as a targeted fix for a specific problematic anchor, not as a default to apply everywhere. A too-forgiving match can silently anchor to the wrong element and produce a test that passes against the wrong region of the document.

Comparing PDF files

PDF 1:1 Compare

The PDF Engine 3.0 compares PDFs through the Module PDF 1:1 Compare, which is part of the Standard subset. It performs a visual comparison between a reference PDF and one or more target PDF files. The TestCase passes if the similarity between the files is above the accuracy you specify — so the threshold is yours to set, rather than requiring pixel-perfect identity.

Where to find it in the workspace: Standard modules → TBox XEngines → Pdf. In the AE1 base subset that folder holds a single Module, named simply '1:1 Compare' — the documentation refers to it as PDF 1:1 Compare, but in the Module tree it appears under the Pdf folder without the prefix. Do not confuse it with TBox Excel 1:1 File Compare, which is the Excel equivalent in a different folder.

Combining compare with exclusions

This is where the scan's exclusion capability pays off. Real generated documents contain fields that change every run — generation timestamps, document IDs, batch numbers. Scanning those regions and excluding them from the comparison lets you compare everything that should be stable while ignoring what is legitimately variable.

For anything the PDF Engine does not cover — checking for broken links, for instance — you work with the Standard subset instead.
