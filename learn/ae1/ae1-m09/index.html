Image-Based Test Automation (IBTA)

Identifying by what it looks like

Every identification method covered so far works on structure — properties, the control tree, the UI Automation interface. Image-based identification abandons structure entirely and identifies a control by one or more screenshots of it. Tosca finds the control by locating that image on screen at execution time.

How to create one

In XScan, select the control you want to identify, then in the Identification methods pane choose ADVANCED IDENTIFICATION → IMAGE. You then supply the screenshot or screenshots that represent the control.

Tricentis' own positioning is explicit: image-based identification is recommended for controls where nothing else works. It is a fallback, not a convenience. Reaching for it early produces automation that breaks on a theme change, a font update, a different screen resolution, or a browser zoom level — none of which would trouble structural identification.

Making image identification as reliable as it can be

Use more than one screenshot

The single most useful technique in this lesson: supply more than one screenshot to identify a control, especially when the control does not always look the same. A button with hover, focused, and default states, or an icon that changes slightly by context, will fail against a single reference image but match reliably against a set covering its variations.

What still breaks it

Multiple screenshots handle variation the control was designed to have. They do not protect against changes to the environment: display scaling, resolution, colour scheme or theme, anti-aliasing differences between machines, or a redesign. This is why image-based controls are also the most machine-sensitive form of automation — a TestCase that passes on the author's laptop can fail on an execution agent with different display settings.

The other Advanced Identification method: Anchor

Identify by anchor

Sitting alongside IMAGE in the same pane is ANCHOR — select the control, then ADVANCED IDENTIFICATION → ANCHOR. Rather than matching appearance, this identifies the target control by its location in relation to another element, the anchor control. It is often the better answer when a control has no stable properties of its own but sits next to something that does.

This consistency is worth noticing: anchors work the same way whether you are scanning a PDF with the PDF Engine or a UI control in XScan. Learn the three rules once and they apply in both places.

Where this sits in the escalation path

Self-healing (Lesson 5) does not appear in this list because it is not an identification method — it is a recovery mechanism that operates when the chosen method fails at runtime. It also does not apply to image-based controls, whose supported-engine list does not include an image matcher.
