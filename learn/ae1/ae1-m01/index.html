What an automation framework is

The problem a framework solves

Every technology exposes its controls differently: a browser has a DOM, a Windows application has native window handles, an Excel workbook has cells and ranges, a mail server speaks a protocol. Without a framework, automating each would mean a different tool, a different scripting model, and a different skill set per technology — and no way to build one TestCase that crosses them.

TBox

The Tosca TBox framework is the .NET-based foundation that all Engines 3.0 are built on, for both GUI and non-GUI tests. It provides one common interface across every supported technology, so the differences between technologies are absorbed by the Engine rather than pushed up into your TestCases. TBox and its Engines 3.0 are part of the standard Tricentis Tosca installation — nothing extra to install for the core engines.

Tricentis cites two concrete benefits of the TBox architecture: higher performance in both creating and executing tests, and one common interface for all supported technologies.

Engines 3.0

What an Engine does

An Engine is the technology-specific layer that knows how to find and manipulate controls in one kind of application. It translates the generic instruction coming from the TestCase — 'set this value', 'verify this value', 'click this' — into whatever that particular technology actually requires.

GUI vs non-GUI engines

GUI engines

Steer something a human could see and click: a browser page, an Excel worksheet, a Windows dialog, a mobile screen. Identification is about locating a visible control.

Non-GUI engines

Steer backend systems with no visual component — the XML and JSON engines, API calls, protocol-level interactions. There is no screen to look at; the Engine works directly against the data or the service.

TBox deliberately supports both categories through the same framework. That is what allows a single TestCase to, for example, submit a web form, then verify the resulting record via an API call, then check that the confirmation PDF was generated correctly.

Modules, XModules, and engine binding

XModules

Engines 3.0 use XModules to steer test objects. An XModule is the Tosca object that represents a piece of the application under test, and it carries the information the Engine needs to find that object again at execution time. XModules can be structured hierarchically and referenced across many TestCases — the same reuse model you already know from web automation.

How the Engine gets chosen

You do not pick an Engine manually per TestStep. The Engine is determined by the Module: when you scan an application, Tosca creates Modules bound to the appropriate Engine for that technology, and every TestStep created from that Module is steered by it. This is why the same TestCase can mix a web TestStep and an Excel TestStep without any special handling — each TestStep inherits its Engine from its Module.

Why the workflow never changes

Because the Engine is hidden behind the Module, the mechanics you learned in AS1/AS2 carry over unchanged: drag a Module onto a TestCase to create a TestStep, fill in TestStepValues, set ActionMode to Input, Verify, Buffer or Select, and run. Learning a new Engine in AE1 is therefore mostly about learning what that technology exposes — which properties exist on an Excel cell, what an Anchor means in a PDF — not about learning a new way to build tests.

Bonus: steering a specific table row

Two ways to reach one row: $ (by value) vs # (by index)

A scanned table gives you a row-level TestStepValue that can be pointed at a specific row two different ways. The # notation targets a row by its ordinal position — the 3rd row, the 12th row — regardless of what data it holds. The $ notation instead targets the row whose cell matches a value you supply, so the TestStep finds 'the row where Order ID = 4021' rather than 'row number 7'. Index-based steering breaks the moment a row is inserted, deleted, or re-sorted; value-based steering survives it, which is why $ is generally the more resilient choice for tables whose row order can change between runs.

HeaderRow

A steering parameter that tells Tosca which row of the scanned table holds the column headers. Once set, later TestStepValues can address a column by its header text instead of a raw column number — 'the Total column' rather than 'column 4' — which keeps the TestCase readable and keeps it working if columns are reordered but not renamed.

Constraint ActionMode

Used to narrow a table TestStep down to one specific row before acting on a different cell in that same row — for example, constrain to the row where the Product column reads 'Laptop', then verify or buffer the Price cell in that row. Constraint is what makes $-style value matching usable across multi-column tables: you locate the row by one column's value and then operate on another.

Row and cell values in a table TestStep also accept REGEX instead of a literal string, so a row can be matched by pattern — a date, an order number with a variable suffix — rather than an exact value that would otherwise have to be hardcoded and would break on the next test run.

Bonus: operating Tosca outside Tosca Commander

TC Shell

TC Shell is the command-line control of Tosca Commander itself — it lets you navigate a Workspace, read or modify a TestStepValue, and run an ExecutionList entirely from the command line, without the Tosca Commander UI ever opening. It has two modes: interactive, where you type commands one at a time and get the same range of functions the GUI offers; and script, where a batch of commands is read from a script data file with no opportunity to intervene — the mode built for running an extensive test portfolio unattended, for instance from a CI pipeline.

Interactive mode: jumptonode and task

You start by copying an object's NodePath from its Properties pane in Tosca Commander (Workspace closed before touching TC Shell). From a command prompt in the Tosca Commander install directory, TCShell.exe -workspace "<path to .tws>" -login "<user>" <password> opens the Workspace; jumptonode "<NodePath>" then moves the shell's focus to that TestStepValue or ExecutionList; and task lists every action available at that point — for a TestStepValue that includes Modify Value, for an ExecutionList it includes Run — selected by number or by name.

Script mode: .tcs and .bat

The same jumptonode / task commands, written into a plain-text .tcs script file instead of typed live, let TC Shell replay a whole sequence — update a TestStepValue, then jump to an ExecutionList and run it — with zero interaction. A short .bat file wrapping TCShell.exe -workspace <path> -login <user> <password> <path to the .tcs file> then turns that sequence into something a build server can double-click or call from a pipeline step.

Tosca REST API: downloading an execution report

Separately from TC Shell, a Tosca Server installation exposes a REST API that can, among other things, print an ExecutionList's report to a file without anyone opening Tosca Commander at all. It requires the Tricentis.Tosca.RestApiService Windows service to be running (disabled by default) and the service's config file to point WorkspaceBasePath at the folder holding the Workspaces it should serve. On the ExecutionEntries object being printed, the PrintOutputFormat property has to be set to ASKUSER first — otherwise the report endpoint has nothing to act on.

The report endpoint follows the shape http(s)://<server>:<port>/rest/ToscaCommander/<workspacename>/object/<id>/task/PrintReport?reportName=<name>&outputFilepath=<target path>, where <id> is the ExecutionList's UniqueId copied from its Properties pane. It is called with Basic Authentication (a Tosca username/password) and a plain GET; a 200 OK response means the file was written to the target path.
