What an automation framework is

The problem a framework solves

Each technology exposes different interfaces. A shared framework supplies common automation building blocks while engines implement technology-specific operations.

TBox

The Tosca TBox framework is the .NET-based foundation that all Engines 3.0 are built on, for both GUI and non-GUI tests. It provides one common interface across every supported technology, so the differences between technologies are absorbed by the Engine rather than pushed up into your TestCases. TBox and its Engines 3.0 are part of the standard Tricentis Tosca installation — nothing extra to install for the core engines.

The original Tosca 16.0 theory names five architecture benefits: performance in authoring/execution, a common technology interface, XScan/Recorder-assisted authoring, shared dynamic-expression behavior and a broader ActionMode range. These are source claims about the framework, not a guarantee of equal supported actions or measured speed for every target.

Engines 3.0

What an Engine does

An Engine is the technology-specific layer that knows how to find and manipulate controls in one kind of application. It translates the generic instruction coming from the TestCase — 'set this value', 'verify this value', 'click this' — into whatever that particular technology actually requires.

The original interactive overview has seventeen Engine information cards across three pages. Its broad technology descriptions are for the course-era overview; they do not certify current driver, platform, protocol, licensing or authentication compatibility. Microsoft UI Automation is the underlying framework; do not confuse its authorship with the Tosca UIA integration.

GUI vs non-GUI engines

GUI engines

Steer something a human could see and click: a browser page, an Excel worksheet, a Windows dialog, a mobile screen. Identification is about locating a visible control.

Non-GUI engines

Steer backend systems with no visual component — the XML and JSON engines, API calls, protocol-level interactions. There is no screen to look at; the Engine works directly against the data or the service.

TBox deliberately supports both categories through the same framework. That is what allows a single TestCase to, for example, submit a web form, then verify the resulting record via an API call, then check that the confirmation PDF was generated correctly.

Modules, XModules, and engine binding

XModules

Engines 3.0 use XModules to steer test objects. An XModule is the Tosca object that represents a piece of the application under test, and it carries the information the Engine needs to find that object again at execution time. XModules can be structured hierarchically and referenced across many TestCases — the same reuse model you already know from web automation.

How the Engine gets chosen

A Module carries engine/interface information used by its TestSteps. Scanned and Standard Modules can represent different technologies; inspect the actual Module configuration.

Why the workflow never changes

Modules, TestSteps and TestStepValues remain familiar building blocks. Available ActionModes depend on InterfaceType and control support; they are not universally identical for every engine.

Original course workspace setup

Course-era single-user training workspace

The original Tosca 16.0 prerequisite exercise creates a single-user workspace named AE1 Exercises using AE1_Base_Subset.tsu as its workspace template. This prepares the supplied training objects; it is not a recommendation to use single-user storage for every production team.

These names and navigation are scoped to the original course installation. Confirm the workspace and Module tree actually exist; reading the instructions or source subset is not a runtime test. The original framework checklist contains one self-assessment objective about exploring the applicable Engines, not a graded test of successful workspace creation.

Bonus: steering a specific table row

Header-relative positions, absolute positions and value constraints

In table addressing, $ identifies positions relative to the configured header, while # identifies absolute positions. Both numeric forms are positional. To find a row by business values, configure cell constraints and resolve any multiple matches before acting on another cell.

HeaderRow

A steering parameter that tells Tosca which row of the scanned table holds the column headers. Once set, later TestStepValues can address a column by its header text instead of a raw column number — 'the Total column' rather than 'column 4' — which keeps the TestCase readable and keeps it working if columns are reordered but not renamed.

Constraint ActionMode

Constraint restricts the search using one or more cell values. Ensure that the resulting row is unique before verifying or buffering another cell; a constraint is not a guarantee of uniqueness.

Row and cell values in a table TestStep also accept REGEX instead of a literal string, so a row can be matched by pattern — a date, an order number with a variable suffix — rather than an exact value that would otherwise have to be hardcoded and would break on the next test run.

Bonus: operating Tosca outside Tosca Commander

TC Shell

TC Shell is the command-line control of Tosca Commander itself — it lets you navigate a Workspace, read or modify a TestStepValue, and run an ExecutionList entirely from the command line, without the Tosca Commander UI ever opening. It has two modes: interactive, where you type commands one at a time and get the same range of functions the GUI offers; and script, where a batch of commands is read from a script data file with no opportunity to intervene — the mode built for running an extensive test portfolio unattended, for instance from a CI pipeline.

Interactive mode: jumptonode and task

Open TC Shell with the workspace path and authentication appropriate to its repository type. Parameters are case-sensitive. JumpToNode uses an object NodePath; task lists operations available for the current object. Inspect the applicable start/command documentation rather than assuming every repository uses -login.

Script mode: .tcs and .bat

Pass a plain-text .tcs command file to start script mode. Supply task inputs in that file; TC Shell processes commands, closes the workspace and exits. A wrapper is optional, not an intrinsic requirement of script mode.

Printing reports through TC Shell

The public 2026.1 reporting workflow requires a report definition with designer configuration and PrintOutputFormat set to NONE. Navigate to the data object, run its Print Report task, and supply the output location/name/type. This does not verify an older REST guide or guarantee a file solely from HTTP status.

The 2023 hands-on guide illustrates particular task menu numbers and a local-repository login. Choose the available task by name/current menu, confirm repository-specific authentication, and use ordinary straight quotes and actual NodePath values. Its training paths and expected results are source examples, not evidence of a fresh run in this environment.
