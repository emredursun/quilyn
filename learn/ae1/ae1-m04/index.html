Why mail automation matters

Mail as part of the business process

Very few end-to-end processes finish inside the application. Register an account and a confirmation email arrives; place an order and an order confirmation follows; reset a password and the whole flow depends on a link that only exists in an inbox. If the test stops at the web page, the part the customer actually receives goes untested.

Mail Engine 3.0

The Tosca Mail Engine 3.0 automates tests against email. Like the other Engines 3.0 it is part of the standard Tricentis Tosca installation, and its Modules belong to the Standard subset — you find them under Standard modules → TBox XEngines → Mail.

Connecting to the mail server

Connect to Mail Server

A dedicated TestStep defines the connection to the mail server — host, protocol, credentials. Note the subtlety: this step defines the connection, but the actual connection is established during the sending or receiving step, not at the moment the Connect step runs. A Connect step that passes is therefore not by itself proof that the server is reachable.

Connect to Exchange Server

A separate Module dedicated to Microsoft Exchange, sitting alongside the generic Connect to Mail Server in the same folder. Where the target mailbox is on Exchange, this is the more direct route than configuring a generic connection.

OAuth 2.0 for Exchange Online / Microsoft 365

Microsoft has been deprecating basic authentication for SMTP and EWS, and Tosca supports OAuth 2.0 as the modern alternative. Tricentis documents a dedicated Connect to Cloud Mail Server Module for this. Hands-on finding: in the AE1 base subset, Connect to Exchange Server itself already exposes an Authentication Type selector (defaulting to 'Direct', i.e. basic username/password) plus App Id and Tenant Id fields — switching Authentication Type away from 'Direct' and supplying an Azure AD app registration's App Id and Tenant Id gives OAuth 2.0 against Exchange Online from that same Module, no separate Connect to Cloud Mail Server step required.

The App Id and Tenant Id come from an Azure AD App Registration with mail permissions, which needs admin consent. In a locked-down corporate tenant a regular employee usually cannot self-provision this — expect to need IT/Azure admin involvement, or to use a personal mailbox instead for a training exercise.

Real-world setup notes: Gmail and corporate mailboxes

Connect to Exchange Server only speaks EWS (Exchange Web Services) — a Microsoft-proprietary protocol. Gmail, and any non-Exchange provider, does not implement EWS at all. Pointing this Module's Exchange Web Services Url at a Gmail account will never authenticate, no matter what credentials are supplied. For Gmail (or any IMAP/SMTP provider), use the generic Connect to Mail Server Module instead.

Gmail: exact server values that work

Connect to Mail Server, configured for RECEIVING: Mail Server = imap.gmail.com, Port = 993, Enable Security = True, Protocol = IMAP. Configured for SENDING (a separate TestStep): Mail Server = smtp.gmail.com, Port = 587, Enable Security = True, Protocol = SMTP.

Give SMTP and IMAP connections DIFFERENT Connection Name values, even against the same mailbox. A Connect to Mail Server step registers its resource under whatever Connection Name you give it, bound to whichever protocol that step configured. If a Send Mail step and a Receive step both reference the same Connection Name, but that name was last configured for the other protocol, you get an error like 'Resource '<name>' does not support sending emails' — the resource exists, it is just registered as the wrong protocol.

Corporate Microsoft 365 tenants almost always block Basic/'Direct' authentication via Conditional Access policies, even with a fully correct password — the request fails with 401 Unauthorized before credentials are meaningfully checked at all. For a training exercise, a personal mailbox (Gmail or a personal Outlook.com account) avoids this entirely, and avoids running third-party automation tooling against a corporate work identity.

Sending mail

Send Mail

The Send Mail Module sends — or replies to — an email message via SMTP. Typical uses in a test are triggering an inbound process (a system that acts on incoming mail), or generating a message the test will later verify was received and correctly handled.

Receiving mail: Simple vs Expert

Receive Mail Simple

Checks whether you received one specific, single email. This is the right choice for the common case: 'after registering, did the confirmation email arrive?' One expected message, one check.

Receive Mail Expert

Checks whether specific emails — plural — were received. Use it when a single message is not the unit of interest: several notifications are expected, or a more elaborate set of criteria has to be evaluated across messages.

Both Simple and Expert support the same protocols: Exchange server, POP3, or IMAP only. The Simple/Expert choice is about how many messages and how much matching complexity you need — not about which mail server you are talking to.
