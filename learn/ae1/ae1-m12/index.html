What the Grand Scenario is for

From isolated lessons to one business process

Each preceding lesson exercised one engine on its own. The Grand Scenario is the capstone that puts them together: a complete Demo Web shop purchase, from logging in through ordering a book and paying on delivery, to downloading the PDF invoice and logging out. It is the exercise that shows why the engines matter — a real process crosses technologies, and the test has to cross them too.

The Modules for this scenario arrive pre-scanned in the base subset, under Modules → Grand Scenario - Demo web shop, grouped as Login, Navigation elements, Products, and Checkout process. You are building TestCases, not scanning the shop from scratch.

Precondition / Process / Post condition

Why the scenario is split into three

The TestCases folder for the Grand Scenario is organised into Precondition, Process, and Post condition. This separation is a test-design discipline, not a Tosca requirement: the Precondition establishes the state the real test needs, the Process is the behaviour actually under test, and the Post condition returns the system to a clean state so the next run starts from the same place.

Note the Post condition does three things, not one: log out, verify the logout worked, and close the browser instance. Leaving the browser open is the classic omission that makes the next run behave unpredictably.

Reuse: the TestStepLibrary

The 'Login to web shop' reusable block

Logging in is needed by the Precondition and would be needed by any other scenario against the same shop. Rather than duplicating those steps, the scenario keeps a TestStepLibrary containing a reusable TestStep block named 'Login to web shop', made up of three steps: Open demo web shop, Click on log in link, and Provide log in details.

Why this matters beyond tidiness

A reusable block is maintained in one place. When the shop changes its login page, one block is updated and every TestCase referencing it is fixed at once — the same centralised-maintenance argument behind Classes in TDS1 and Libraries in the TestCase section. The Precondition TestCase then consists of the reused block plus its own 'Verify successful login' step.

Observe the division of labour: the reusable block performs the actions; the TestCase that uses it owns the verification. Keeping the assertion outside the shared block lets different callers verify different things.

The Process TestCase, step by step

Three TestStep folders

'Order fiction book and pay on delivery' is itself divided into three TestStep folders, which keeps a long flow readable and makes a failure immediately locatable to a phase of the process.

The two techniques that make it work

Buffering the order number

The step 'Verify order and buffer order no' does two jobs at once: it verifies the order was created, and it buffers the order number the shop generated. That number cannot be known in advance — it only exists at runtime — so it is captured into a buffer and then used by the following steps to navigate to the correct order details page. This is the standard Tosca answer to 'the application generated a value and I need it later'.

Crossing into the PDF Engine

'Download PDF Invoice' is where the scenario leaves the browser. The invoice produced by the checkout is a PDF, and verifying it is exactly the PDF Engine work from Lesson 2 — scanning the document, using anchors to locate values that shift with content, and comparing against a reference while excluding the volatile parts such as the order number and date.

This is the moment the course's argument lands. The order number is dynamic, so it must be buffered rather than hard-coded; the invoice is a PDF, so the browser engine alone cannot verify it; and the whole thing is one TestCase because TBox lets engines mix freely. Every lesson in AE1 exists to make this single flow testable.
