What the Grand Scenario is for

From isolated lessons to one business process

The original AE1 Grand Scenario extends a Demo Web Shop fiction-book order into PDF verification, Excel output, file operations and email delivery. The initial base ExecutionList can generate the invoice and log out. In the supplied solution, the complete seven-entry ExecutionList runs login, ordering, PDF checks, Excel output, file movement, mail and finally logout. The course was developed with Tosca 16.0.

The original downloadable package contains both base and solution subsets. Their Grand Scenario folder contains Precondition, Library, Process and Post condition. If an imported subset is not immediately visible, the Academy notes suggest searching under Section. Importing or reading a subset does not execute its tests.

Four extensions to the purchase flow

Business operations and cleanup

Add invoice verification, Excel output, invoice movement and email delivery to the existing purchase ExecutionList. Within the Excel TestCase, the source uses Precondition, Process and Postcondition folders for opening/preparing, writing and saving/closing the workbook. These are training organization choices, not mandatory names for every Tosca test.

Arrange cleanup on relevant failure paths. Sequential TestCases do not themselves guarantee that workbook closure or session cleanup executes after an earlier failure. Cleanup does not undo the order. Validate output files before dependent steps use them.

Supplied login reuse and maintenance

The 'Login to web shop' reusable block

Both supplied subsets contain a TestStepLibrary named Library and its Reusable TestStepBlock Login to web shop. The block contains Open demo web shop, Click on log in link and Provide log in details. The Login to web shop TestCase references this block and then separately verifies successful login.

Why this matters beyond tidiness

References to a Reusable TestStepBlock share centrally maintained steps; changes affect all linked references. A resolved reference becomes an independent copy, so it no longer receives those changes. Updating shared steps still requires validating callers and their assertions.

The supplied login TestCase keeps its success assertion outside the shared block. Other designs may share assertions when appropriate. The observed source structure is a course implementation choice, not a mandatory three-step rule for all reusable blocks.

Copy the order data to Excel

Workbook, worksheet and range are separate references

The exercise creates Order_Details at C:\Tosca_Projects\Order_Details.xlsx using TBox Open Excel Workbook with Create New=True. It creates the Order_Details worksheet, then defines OrderDataRange from A1 to D5. The path and range are training values, not universal defaults.

The source writes specified company/total values and the buffered order number; it does not demonstrate an automatic generic PDF-to-Excel converter. 41.00 is the exercise expectation, not a fixed total for every shop order.

Verify the generated invoice

Scan and verify the order fields

After running the purchase ExecutionList, open its order_orderNumber.pdf output. Under the course’s Grand Scenario Modules folder, create PDF Modules and use PDF Scan to scan Order number, Company from Billing Information and Order total as Text. Save the Module as Order Invoice. In the invoice-verification TestCase, Input the Target PDF path and Verify Company=Demowebshop, Order number={B[orderNumber]} and Order total=41.00.

Crossing into the PDF Engine

Downloading the invoice is not automatic PDF verification. The original exercise uses scanned text assertions; it does not prescribe a reference-file comparison or exclusion area. As an independent extension, use appropriate PDF Modules for selected comparison checks and verify the dynamic identifier separately rather than excluding an important mismatch.

Tosca supports appropriate engine Modules within a business flow, subject to their prerequisites and compatibility. Reuse and buffering do not guarantee that every engine combination or document check works without configuration.

The supplied order TestCase verifies the confirmation line with Order number: {XB[orderNumber]}. This captures the dynamic identifier while verifying the message; subsequent invoice and Excel steps read {B[orderNumber]}. Keep the same buffer name throughout the flow rather than copying an identifier from a previous run.

Move the invoice file

Use the final path consistently

The original exercise adds TBox Move/Rename File. Existing Path points to the actual downloaded invoice; New Path is C:\Tosca_Projects\Invoice.pdf. Both use Input. Later attachment steps must use this new path, not the original download name.

Prepare the destination and check the operation’s result. Moving a file is not invoice-content verification and does not save the Excel workbook.

Send the invoice and workbook

One mail operation, two attachments

The source uses Connect to Exchange Server and Send Mail with the same MailConnection name, then attaches C:\Tosca_Projects\Invoice.pdf and C:\Tosca_Projects\Order_Details.xlsx. It directs the test message to the tester’s own address and adds the four new TestCases to the purchase ExecutionList.

The Tosca 16.0 PDF contains a historical Direct-authentication EWS example with a username/password. Do not assume it works with today’s Microsoft accounts: Exchange Online removed Basic authentication for EWS, and current Outlook.com settings require OAuth2. Confirm supported Tosca/provider authentication and EWS availability before running the mail step; switching to a personal mailbox is not a general fix for an unsupported authentication method.

The source’s final IMAP hint incorrectly describes sending and uses an SMTP hostname. SMTP sends mail; IMAP accesses incoming mail. Current Outlook.com documentation lists smtp-mail.outlook.com:587 with STARTTLS for SMTP, and outlook.office365.com:993 with SSL/TLS for IMAP, with OAuth2. These Outlook.com settings must not be applied indiscriminately to Exchange Online tenants or other providers.

Original purchase flow and Module inventory

Three purchase phases in both subsets

The supplied ordering TestCase has fourteen TestSteps: four navigation steps, seven checkout steps and three order-verification/download steps. The final solution includes four additional output TestCases before logout. These names and grouping are observed training data, not universal Tosca defaults.

Static subset inspection confirms the objects and links, not successful execution against the current shop. Stored source execution logs are not a fresh test run. Revalidate current application controls and test data in a supported installed environment.
