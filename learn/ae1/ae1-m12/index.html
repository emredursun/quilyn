What the Grand Scenario is for

From isolated lessons to one business process

This local worked scenario combines login, book ordering, invoice download and logout to illustrate cross-technology test design. Precondition / Process / Post condition

Why the scenario is split into three

In this local example, Precondition establishes the starting session, Process exercises ordering and Post condition verifies logout and closes the browser. These names are a design choice, not a Tosca-required folder structure. Session cleanup does not delete orders or restore all business data.

Arrange cleanup to run on relevant failure paths as well as success. Three sequential TestCases do not themselves guarantee that logout or close executes after an earlier failure. Closing a browser releases the session; it does not undo the order.

Reuse: the TestStepLibrary

The 'Login to web shop' reusable block

Logging in is needed by the Precondition and would be needed by any other scenario against the same shop. Rather than duplicating those steps, the scenario keeps a TestStepLibrary containing a reusable TestStep block named 'Login to web shop', made up of three steps: Open demo web shop, Click on log in link, and Provide log in details.

Why this matters beyond tidiness

References to a Reusable TestStepBlock share centrally maintained steps; changes affect all linked references. A resolved reference becomes an independent copy, so it no longer receives those changes. Updating shared steps still requires validating callers and their assertions.

This example keeps successful-login verification with the caller. That is a design choice: reusable blocks may also contain verification TestSteps when those assertions are genuinely shared.

The Process TestCase, step by step

Three TestStep folders

This independent flow groups ordering into three folders for readability. A folder label helps locate a phase but does not prove the root cause of a failure or verify the original Academy sequence.

The two techniques that make it work

Buffering the order number

Capture the current order identifier with ActionMode Buffer, or use XBuffer within a verified message to extract its dynamic part. Later steps read {B[OrderID]}. Do not assume the identifier differs on every run; use the value actually produced by the application.

Crossing into the PDF Engine

Downloading the invoice is a browser/file operation, not automatic PDF verification. Verify the file is available, then use PDF Modules for the chosen checks. Content extraction and reference comparison are distinct operations. Configure explicit page/area exclusions only for allowed differences; verify the captured order identifier separately rather than hiding an important mismatch.

Tosca supports appropriate engine Modules within a business flow, subject to their prerequisites and compatibility. Reuse and buffering do not guarantee that every engine combination or document check works without configuration.
