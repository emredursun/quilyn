The problem: widgets that aren't standard controls

When an engine sees the wrong thing

Standard identification works because the engine recognises a control as something it understands — a text box, a checkbox, a table. Complex or third-party UI widgets break that assumption. A custom date picker, a rich grid, or a bespoke component may be built from dozens of nested primitive elements, so the engine sees a pile of divs or panels rather than one meaningful control. You can sometimes still automate it, but the steering is fragile and the Module is unreadable.

Custom controls

A custom control wraps a complex UI widget so that Tosca presents it as one of its standard UI elements. Instead of the tester manipulating the widget's internal structure, the widget is exposed as the control it logically is — and can then be steered with the ordinary ActionModes like any other control. Custom controls are based on special, custom-made DLL files that refine how Tosca detects UI elements.

The key idea: a custom control does not add a new way to build TestCases. It changes what the engine recognises, so the TestCase can stay ordinary. That is precisely why it is preferable to falling back on image recognition.

Where custom controls come from

Not something you author in Tosca Commander

Custom controls are compiled DLLs, not project objects you create through the Tosca UI. Tricentis' own guidance is to contact your Tricentis representative to obtain custom controls — they are provided for known widget libraries rather than built ad hoc by the tester.

Making them available

Once obtained, the DLL has to be put where Tosca will load it, and Tosca has to be restarted for the control to be picked up. The mechanism differs by deployment: in Tosca Cloud an administrator uploads them under Configurations → Uploads → Custom controls, and they are distributed automatically through Launcher and integrated into all test runs. For an on-prem installation — which is what this course covers — the AE1 lesson walks through the placement and activation steps directly; follow the version-specific path shown there rather than assuming a location.

Because custom controls are DLLs loaded by Tosca, they are an installation-level change, not a project-level one. Everyone who executes the affected TestCases needs the same custom control available on their machine or agent — otherwise the TestCases will work for the person who installed it and fail for everyone else.

Using them and where they fit

After installation, nothing special

Once a custom control is installed, you scan the application as usual. The difference is what comes back: the widget now appears as a recognised standard control in the Module rather than as a tangle of low-level elements. From there it is steered exactly like any other control — same TestSteps, same TestStepValues, same ActionModes.

Custom controls sit above image-based controls in that order for a reason: they restore proper structural identification, so the resulting automation survives cosmetic changes like restyling or resolution differences. Image matching does not.
