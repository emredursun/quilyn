The Tricentis Mobile Agent

What TMA does for you

Mobile automation traditionally means assembling a toolchain — Appium, Java components, environment variables, device drivers — before a single test can run. The Tricentis Mobile Agent (TMA) provides simplified setup and configuration of iOS and Android devices so that none of that is your problem: you do not need to install Appium, Java components, or configure environment variables yourself.

Mobile Engine 3.0

The Engine that steers mobile applications, working through the Mobile Agent. As with every Engine 3.0, once Modules exist the TestCase-building workflow is the familiar one — the mobile-specific work is all in the connection and scanning setup.

Local vs Remote connections

Local (TMA)

Connects a device to the workstation running Tricentis Tosca — via USB cable, or to a simulator or emulator running on that same machine. This is the typical setup while developing tests, and what the course exercises use.

Remote (TMA)

A remotely installed Tricentis Mobile Agent connects to a remote device, emulator, or simulator. This is what you use when the device farm lives elsewhere — a shared lab, a CI environment, or cloud-hosted devices.

The choice is a configuration matter, not a different way of writing tests. The same TestCase can run against a locally attached phone or a remote one; only the connection configuration changes.

Preparing an Android device

USB debugging is the step most often missed. Without it the device may charge and appear in Windows, yet remain invisible to the Mobile Agent — the symptom looks like a Tosca problem but is a device configuration one.

Scanning and building the TestCase

Mobile Scan

The Mobile Scan handles native, hybrid, and web applications on mobile. The sequence is: prepare the test environment, start the Mobile Scan and connect to your device, then add the mobile device, emulator, or simulator you want to scan against. From there, scanning produces Modules the same way it does for any other technology.

Configuring the connection with TCPs

The connection to a device, emulator, or simulator is established through test configuration parameters. This is the same TCP mechanism used elsewhere in Tosca — for the TestDataService endpoint, for SelfHealing — so the scoping rules you already know apply.

Open Mobile App must come first

Drag and drop the Open Mobile App Module onto the TestCase — and note the constraint: it must be the first TestStep of the TestCase. Nothing can be steered on the device until the application has been opened through this Module.

This mirrors the Excel lesson's mandatory TBox Open Excel Workbook first step. A recurring pattern across AE1: engines that attach to an external resource require an explicit open step before anything else in the TestCase.

Real-world setup notes: running TMA on a separate machine

The TMAServer TCP value MUST end with a trailing slash: http://<ip>:8585/ — not http://<ip>:8585. Without it, execution fails with the misleading message 'Could not create TMA session: Ensure that the requested device is connected.' The cause is that TMA's REST base path is /api and Tosca appends onto the TMAServer value, so a missing slash produces a broken URL and the request never leaves Tosca.

What makes this trap so confusing: the Mobile Scan wizard's Add connection dialog tolerates the missing slash, so scanning works perfectly while TestCase execution fails. Seeing Scan succeed naturally leads you to rule out the connection — and look everywhere except the one value that is wrong.

Remote TMA must be started with --rest-address

Launching TMA from the tray icon or Start Menu starts it for LOCAL use only. When Tosca and TMA run on different machines, start the agent from the command line with the --rest-address flag: tricentis-mobile-agent start --rest-address <IP>:<port>. On Windows the executable lives under C:\Program Files\Tricentis\Mobile Agent; on macOS inside /Applications/Tricentis Mobile Agent.app.

Diagnosing device-side vs Tosca-side problems

TMA exposes a REST endpoint you can query directly: http://<ip>:<port>/api/devices returns JSON with each device's udid, name, connected, busy and statusReady fields. If that shows connected:true and busy:false, the device side is healthy and the fault is on Tosca's side — which saves you from chasing firewall, proxy, and network theories.

Where is adb? It ships with TMA — on Windows under C:\Program Files\Tricentis\Mobile Agent\app\android-sdk\platform-tools, and with Android Studio under ~/Library/Android/sdk/platform-tools on macOS. You do not need a separate Android SDK install just for adb.

Emulators must run on the same machine as TMA

Tricentis recommends Android Studio for emulators, and the emulator has to run on the machine running TMA. That constraint drives the whole topology: if Tosca Commander runs in a VM but the emulator runs on the host, then TMA belongs on the host alongside the emulator, and Tosca connects to it remotely.

The Android Emulator does not exist for Windows on ARM. Google publishes no ARM64 Windows emulator package, so the SDK Manager never lists it and AVD creation fails with 'Dependant package with key emulator not found'. On an ARM Windows VM the only paths are a physical device, or running the emulator on the host machine with TMA beside it.
