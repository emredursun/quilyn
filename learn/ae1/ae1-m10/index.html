The Tricentis Mobile Agent

What TMA does for you

Mobile automation traditionally means assembling a toolchain — Appium, Java components, environment variables, device drivers — before a single test can run. The Tricentis Mobile Agent (TMA) provides simplified setup and configuration of iOS and Android devices so that none of that is your problem: you do not need to install Appium, Java components, or configure environment variables yourself.

Mobile Engine 3.0

Mobile Engine 3.0 steers supported mobile applications through a configured connection. Modules use the familiar Tosca TestCase workflow, but application type, supported controls, capabilities and device preparation still affect execution.

Local vs Remote connections

Local (TMA)

Local (TMA) uses a locally connected supported device or Android emulator. Select a device explicitly when required by the topology; a single local Android device does not require DeviceName. Check the requirements for the installed Agent version.

Remote (TMA)

Remote (TMA) reaches an Agent on another machine and its supported device, emulator or simulator. Remote TMA is distinct from connecting directly to a cloud provider’s Appium endpoint.

The authoring model stays the same, but moving a test requires validating device/app compatibility, capabilities and connection configuration. TMA 2025.4 requirements restrict iOS hosting to macOS; older Agent/Tosca guides describe broader host support. Use the installed Agent version’s requirements rather than assuming those descriptions apply unchanged.

Preparing an Android device

If Windows recognizes a phone but automation cannot reach it, check USB debugging, authorization, data access and the device driver. Recognition alone does not prove automation readiness; missing debugging is one possible cause, not a proven most-common diagnosis.

Scanning and building the TestCase

Mobile Scan

The Mobile Scan handles native, hybrid, and web applications on mobile. The sequence is: prepare the test environment, start the Mobile Scan and connect to your device, then add the mobile device, emulator, or simulator you want to scan against. From there, scanning produces Modules the same way it does for any other technology.

Configuring the connection with TCPs

The connection to a device, emulator, or simulator is established through test configuration parameters. This is the same TCP mechanism used elsewhere in Tosca — for the TestDataService endpoint, for SelfHealing — so the scoping rules you already know apply.

Open the correct application type

Use Open Mobile App for native/hybrid applications before steering them. The Standard Mobile Module reference documents an exception: Set Desired Capabilities may precede it. Mobile websites instead start with OpenUrl, Browser=ChromeAndroid or SafariiOS, and UseActiveTab left empty.

Opening rules depend on the resource and setup Modules. Do not generalize an unconditional first-step rule across Excel file comparison, mobile web and native applications.

Remote setup and diagnostic boundaries

Use the documented endpoint format

The Tosca mobile configuration guide gives remote addresses as http://<ip_address>:<port_number>/. Keep the documented trailing slash. It does not establish that every missing-slash failure has one exact error or that the Scan wizard always tolerates it.

REST binding is not the Appium port

The TMA 2025.4 CLI binds services to localhost by default. Use --rest-address <IP>:<port> for a reachable web-server binding. --appium-port configures Appium separately; --grpc-address configures gRPC. Match the service endpoint required by Tosca rather than treating these switches as interchangeable.

Diagnose one layer at a time

Check Agent/device availability, the endpoint from the Tosca host, session logs, capabilities and application identifiers. A connected or idle device status alone cannot rule out firewall, routing, permissions or session-creation problems. No undocumented REST response schema is required for this lesson.

Choose supported host hardware

TMA 2025.4 documents bare-metal hosts and requires the Android emulator to run on the same machine as the Agent. It supports Android Studio for Android virtual devices and Xcode for iOS virtual devices. Confirm host architecture, OS and emulator support for your installed versions before setup.

Do not diagnose every APK parsing failure as a v1-signature problem or blindly re-sign the app: changing signing identity can affect updates and behavior. Obtain a compatible test build from its owner and inspect the actual installation error.

Device vendor policies and Android settings vary. The public preparation guide documents USB debugging, phone data access and drivers, not a universal instruction to disable protections or skip every permission-related requirement.
