Two engines for one platform

Why Windows needs two options

Windows applications use different control technologies. UIA and WinX are two available engines, alongside technology-specific engines such as DotNet. Evaluate supported controls and identification before selecting an engine for a large automation suite.

UIA Engine 3.0

UIA Engine 3.0 accesses controls through Microsoft UI Automation. Tricentis recommends it when the corresponding standard engine does not support the controls but their UI Automation interface permits steering; this is not a guarantee that every Windows element is supported.

WinX Engine

WinX steers supported PowerBuilder applications and applications using the Windows UI API. Evaluate its control support and setup requirements rather than treating it as a universal alternative for any UIA identification failure.

UIA depends on the application’s UI Automation exposure. WinX documentation describes Windows UI API and PowerBuilder support. Engine choice, control exposure and supported operations all matter.

Making the choice at scan time

Where the decision happens

Open XScan with Modules → Scan → Application, or Scan → Application from a Module folder. In Select Application, right-click the target application and choose UIA or WinX, then scan and save its controls. This creates technology-specific Modules.

Consequences of the choice

A scanned Module contains engine-specific identification and control information. Selecting a different engine for another scan does not automatically convert existing Modules or TestSteps. Evaluate new Modules and affected test references before migrating.

Tricentis does give UIA selection guidance: use it for controls unsupported by their corresponding standard engine when UI Automation can steer them. For WinX, inspect Windows UI API/PowerBuilder support and scan results. Rescanning is an evaluation step, not a promise that the alternative engine will identify every control.

Working with the scanned controls

Nothing new above the Module

The Module → TestStep → TestStepValue workflow remains familiar. ActionModes and properties still depend on the control and engine; do not assume every control supports Input, Verify, Buffer and Select identically. UIA table cell input uses embedded controls.

Check supported controls and prerequisites before escalating to extensions or image recognition. For disappearing context menus, the documented TBox Context Menu workflow can avoid scanning them. PowerBuilder DataWindow recognition requires enabling the application before scanning.
