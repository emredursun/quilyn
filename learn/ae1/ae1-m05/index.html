Two engines for one platform

Why Windows needs two options

Windows desktop applications are not built on a single technology. Some are WinForms, some WPF, some are decades-old Win32 executables, some are hybrids. No single access mechanism reaches all of them cleanly, so Tosca offers two different ways into a Windows application and lets you pick the one that works for the application in front of you.

UIA Engine 3.0

Based on the Microsoft UI Automation framework — a framework Microsoft developed specifically so that applications built on different technologies could be steered as uniformly as possible. When the UIA Engine steers an application, controls are addressed exclusively through that UI Automation interface in the target application. Beyond application windows, the UIA Engine 3.0 can also test Windows desktop elements and the taskbar.

WinX Engine

WinX is used for Windows UI API tests — it interacts with the application through direct Windows API-level calls rather than through Microsoft's UI Automation abstraction. It is the alternative path for applications that the UIA interface does not expose well.

Note the layering difference: UIA goes through an abstraction Microsoft provides for cross-technology uniformity; WinX goes more directly at the Windows API. That is the essential distinction to remember.

Making the choice at scan time

Where the decision happens

You do not choose the engine on a TestStep or a Module property — you choose it while scanning. After selecting the desktop application you want to scan, right-click the application's tile and pick either UIA or WinX from the context menu. Whichever you choose determines the kind of Modules produced: UIA Modules for UIA tests, WinX Modules for Windows UI API tests.

Consequences of the choice

This is the same Module-binds-the-Engine principle from the TBox theory lesson, applied to Windows. Because the engine is baked into the Modules created by the scan, switching engines later is not a setting you flip — it means rescanning the application with the other option and rebuilding the affected Modules. Worth a moment's evaluation before committing to a large scan.

Tricentis' documentation presents UIA and WinX as equivalent alternatives at scan time and does not prescribe one for specific scenarios — the right choice depends on the application's architecture and how well it exposes its controls. In practice this means: try one, and if controls are not identified reliably, rescan with the other.

Working with the scanned controls

Nothing new above the Module

Once the scan has produced Modules, everything above that level is the workflow you already know: drag a Module onto a TestCase to create a TestStep, fill in TestStepValues, choose an ActionMode of Input, Verify, Buffer or Select. Whether a UIA or WinX Engine is doing the steering underneath is invisible at that level — exactly the uniformity the TBox framework exists to provide.

If a Windows control resists identification by both engines, that is the point at which the later lessons become relevant: Custom Controls (Lesson 6) for extending recognition properly, and Image Based Controls (Lesson 8) as the last-resort fallback.
