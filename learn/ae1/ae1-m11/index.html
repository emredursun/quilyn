Where this module sits

⚠️ This is the OPTIONAL section of the AE1 course. The Final Exam draws no questions from optional sections, so nothing here will be tested. It is worth understanding anyway — Vision AI is where Tosca's control identification is heading, and it directly addresses the weaknesses of the image-based controls covered in Lesson 8.

What Vision AI is

Seeing the UI the way a person does

Conventional scanning reads an application's technical structure — element ids, class names, the control tree. Vision AI instead analyses the application's visual components, using two neural networks: one for finding controls and one for optical character recognition (OCR). It identifies what is on screen much as a human tester would: this looks like a text field, that is a button labelled 'Submit'.

Recognising control types, not just pixels

The crucial detail is that Vision AI detects control types and adjusts its steering mechanism to the classification it has made. Having decided a region is a dropdown, it steers it as a dropdown. This is what separates it from raw appearance matching.

The presence of a dedicated 'Vision AI Self Healing' Module is worth noting against Lesson 5: conventional self-healing covers DotNet, Java, Oracle, UIA, XBrowser and Salesforce, and does not extend to image-based controls. Vision AI brings its own self-healing mechanism for visually identified controls — which is exactly the gap image-based identification leaves open.

Vision AI vs the two methods you already know

Versus property-based scanning

Property-based identification depends on technical attributes staying stable. Vision AI steers by visual components instead, which makes it resilient to UI changes that alter the underlying markup without changing what the user sees — a framework upgrade that renames every generated class, for example.

Versus image-based controls (Lesson 8)

This is the comparison that matters most. Image-based identification matches a screenshot — it knows nothing about what the control is, only what it looked like. Vision AI recognises individual control types and adjusts its behaviour accordingly, which is smarter steering than pixel matching or screenshot comparison. Where Lesson 8's method is a last resort accepting brittleness, Vision AI aims to be a genuine identification strategy.

Tricentis positions Vision AI as producing stable, self-healing Modules for any UI — the self-healing framing is deliberate, contrasting with image-based controls, which self-healing does not cover.

When automatic recognition is not enough

User Identified Controls (UIDCs)

Vision AI does not always classify a control correctly on its own. When standard recognition falls short, controls can be configured manually, or you can create User Identified Controls — controls you define yourself so the AI knows how to treat them.

Anchors, again

UIDCs use anchor points — surrounding elements that guide the AI to locate the target correctly. The same relational idea you met in the PDF Engine lesson and in XScan's Advanced Identification appears here too: when an element is hard to pin down on its own, describe it by what sits around it.

Three lessons, one recurring principle: PDF anchors, XScan anchor identification, and Vision AI anchor points all solve the same problem — identifying something unstable by reference to something stable nearby.

When to reach for it

Note what this list does not say: it is not positioned as a replacement for property-based scanning where that works well. Structural identification remains the default; Vision AI is the answer when structure is unavailable or unstable.
