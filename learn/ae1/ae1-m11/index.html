What Vision AI is

Seeing the UI the way a person does

Conventional scanning reads an application's technical structure — element ids, class names, the control tree. Vision AI instead analyses the application's visual components, using two neural networks: one for finding controls and one for optical character recognition (OCR). It identifies what is on screen much as a human tester would: this looks like a text field, that is a button labelled 'Submit'.

Recognising control types, not just pixels

The crucial detail is that Vision AI detects control types and adjusts its steering mechanism to the classification it has made. Having decided a region is a dropdown, it steers it as a dropdown. This is what separates it from raw appearance matching.

Vision AI recovery requires administrator-enabled cloud image-analysis history, a Recovery Scenario with RetryLevel=TestStepValue, the Vision AI Self Healing Module, OnDialogFailure=Recover and TestStepValueRetries=1. Run from an ExecutionList. Recovery is attempted for missing controls; it does not guarantee that the intended target or later assertions will succeed.

The original Tosca 16.0 handout distinguishes installation from readiness: an appropriate Vision AI account is needed, and the Vision AI Agent must be running with Connected status before scanning or execution. Check the current version/account setup and data policy separately; having Tosca installed alone does not prove Vision AI access or connectivity.

Vision AI vs the two methods you already know

Versus property-based scanning

Vision AI uses visual recognition rather than relying on the target’s DOM identifiers. Changes to technical attributes may therefore leave a visual locator usable, but labels, layout, detection quality and steering support still require validation.

Versus image-based controls (Lesson 8)

Image identifiers match a captured appearance. Vision AI detects control types and uses type-specific steering. Classification can require adjustment; neither method guarantees reliable execution after arbitrary visual changes.

Evaluate Vision AI against the actual interface and supported steering behavior. The introduction documents table-steering limitations and suggests VisionScript for some cases. Marketing descriptions of stable or platform-agnostic automation are not a guarantee that every UI is supported.

When automatic recognition is not enough

User Identified Controls (UIDCs)

When detection is unsuitable, XScan can adjust the ControlType among detected choices, refine labels or create a User Identified Control (UIDC). In Advanced View, define the target region, control type and application category, select anchor controls, save and rescan. UIDC definitions are shared within the company.

Anchors, again

UIDCs use reference controls inside or outside the target region. A single anchor preserves a fixed relative size/position and may fail when sizes vary. Prefer unique text labels and multiple appropriate anchors for variable dimensions; use UidcCategory for the defined application group.

PDF, XScan and Vision AI anchors share a reference idea but have distinct configuration and behavior. PDF-specific rules are not a substitute for UIDC anchor selection.

When to reach for it

These are independent selection considerations, not a universal vendor ranking. Compare identification reliability, supported controls, setup and cloud data requirements. A working structural locator does not automatically justify migration.

Original theory: choosing and validating a visual workflow

Problem areas and candidate use cases

The original Introduction and Use Cases narration separates UI automation from test selection, then groups UI problems into fragility, technical know-how and late automation. Its four candidate use cases are frequent technology changes, difficult custom controls, remote/Citrix interfaces and early UI mockups. These are source recommendations to evaluate, not evidence that any application or future technology will work unchanged.

Mockup to implemented interface

The Workflow narration describes scanning a PDF mockup, selecting controls with ControlType and Label, creating a Module and TestCase, then reusing that example against remote .NET and web implementations. Preparing visual actions against a mockup is not validation of implemented business behavior. Recheck actual controls, window context, data and assertions when the real application becomes available.

Recognition failure is part of the workflow

The customizations narration contrasts an Angular DIV table with structural scanning and refers to the content preview. The UIDC narration then describes a table that was not initially recognized: draw its region, choose two anchors, assign Table and rescan. This is a particular example, not a rule that two anchors always suffice or that every table is supported.

The VisionScript narration describes inserting a script between ordinary TestSteps and checking the actual browser window caption, including spaces and periods, before steering a Continue button. Complete English subtitle texts for all six theory recordings were read; full video visuals and installed executions have not been verified. Caption typos and broad marketing claims are not executable parameter guarantees.

The original seven-item learning checklist covers AI testing, UI problem/use-case analysis, simple TestCase creation/run, customization alternatives, UIDCs, the Run VisionScript Module and script execution. Original optional example: DIV table

From visual scan to cell assertions

The 2023 guide uses obstacle 57445 and an imported AE1 base subset. Select the browser application in XScan, choose Vision AI, scan the visible table and save the resulting Module. In the source example, row $2 / cell $1 is verified against 2.1, while row $1 / cell $2 is buffered as Value 1. These are positional selectors for that example, not guarantees about a changed table.

Inspect the detected table and its content preview before steering. Current XScan exposes additional detection and header parameters; recognition, row/column boundaries and the actual values must be validated. A source screenshot or expected successful ScratchBook result does not demonstrate a fresh execution here.

Original optional example: VisionScript login

Window context and ordered script actions

The guide opens the Demo Web Shop, then uses Run VisionScript to reach the login page and enter account details. Window supplies the caption of the active target window; VisionScript supplies the ordered commands. The source configures Input actions and Password data type for the password-bearing script value. Use an authorized test account and validate the resulting signed-in state, rather than treating a click alone as proof of login.

VisionScript offers a scripted alternative when scanning is difficult; it does not overcome every Vision AI limitation. Labels, window matching, recognition support, account state and cloud prerequisites still matter. The source expected success is not evidence of installed execution, and its example credentials must be replaced rather than copied.
