What Vision AI is

Seeing the UI the way a person does

Conventional scanning reads an application's technical structure — element ids, class names, the control tree. Vision AI instead analyses the application's visual components, using two neural networks: one for finding controls and one for optical character recognition (OCR). It identifies what is on screen much as a human tester would: this looks like a text field, that is a button labelled 'Submit'.

Recognising control types, not just pixels

The crucial detail is that Vision AI detects control types and adjusts its steering mechanism to the classification it has made. Having decided a region is a dropdown, it steers it as a dropdown. This is what separates it from raw appearance matching.

Vision AI recovery requires administrator-enabled cloud image-analysis history, a Recovery Scenario with RetryLevel=TestStepValue, the Vision AI Self Healing Module, OnDialogFailure=Recover and TestStepValueRetries=1. Run from an ExecutionList. Recovery is attempted for missing controls; it does not guarantee that the intended target or later assertions will succeed.

Vision AI vs the two methods you already know

Versus property-based scanning

Vision AI uses visual recognition rather than relying on the target’s DOM identifiers. Changes to technical attributes may therefore leave a visual locator usable, but labels, layout, detection quality and steering support still require validation.

Versus image-based controls (Lesson 8)

Image identifiers match a captured appearance. Vision AI detects control types and uses type-specific steering. Classification can require adjustment; neither method guarantees reliable execution after arbitrary visual changes.

Evaluate Vision AI against the actual interface and supported steering behavior. The introduction documents table-steering limitations and suggests VisionScript for some cases. Marketing descriptions of stable or platform-agnostic automation are not a guarantee that every UI is supported.

When automatic recognition is not enough

User Identified Controls (UIDCs)

When detection is unsuitable, XScan can adjust the ControlType among detected choices, refine labels or create a User Identified Control (UIDC). In Advanced View, define the target region, control type and application category, select anchor controls, save and rescan. UIDC definitions are shared within the company.

Anchors, again

UIDCs use reference controls inside or outside the target region. A single anchor preserves a fixed relative size/position and may fail when sizes vary. Prefer unique text labels and multiple appropriate anchors for variable dimensions; use UidcCategory for the defined application group.

PDF, XScan and Vision AI anchors share a reference idea but have distinct configuration and behavior. PDF-specific rules are not a substitute for UIDC anchor selection.

When to reach for it

These are independent selection considerations, not a universal vendor ranking. Compare identification reliability, supported controls, setup and cloud data requirements. A working structural locator does not automatically justify migration.
