The problem self-healing addresses

Controls change; tests break

An application under active development changes its controls constantly — an id gets renamed, a class is restructured, a button moves into a different container. Nothing about the business behaviour changed, but the automation can no longer find the control and the TestCase fails. Investigating and repairing these false failures is one of the biggest ongoing maintenance costs in test automation.

Self-healing Mode

With Self-healing Mode enabled, a TestCase does not fail just because a control changed. When Tosca cannot find the control during execution, it looks for a similar control in the system under test; if it finds a suitable one, it uses that control instead and execution continues. The result is more stable test runs, less manual repair work, and a record of which controls have actually changed.

Important: when self-healing succeeds, the TestCase passes normally. It is not a warning-level result — execution simply continues on the replacement control.

Turning it on: the SelfHealing TCP

A test configuration parameter, not a checkbox

Self-healing is activated by creating a test configuration parameter named SelfHealing. Because it is a TCP, it inherits the usual scoping rules — set it high in the folder structure to apply broadly, or on a specific TestCase to limit it.

SelfHealingWeightThreshold

An optional companion TCP used with the Weighted mode. It defaults to 0.75 and filters out property combinations that score below that threshold — a way to stop the algorithm from accepting weak matches. Raise it to be stricter about what counts as 'the same control'; lower it to tolerate more change.

Self-Healing Properties

Where the technical data lives

Self-Healing Properties are the technical attributes of a control that give Tosca something to match against when the primary identification fails. They sit on the Self-Healing Properties tab of the ModuleAttribute — one level deeper than the identification you normally work with.

They are created for you

Tosca adds these properties automatically when a Module is created through XScan, Tosca Rescan, Salesforce Scan, or the Tricentis Automation Recording Assistant. You do not have to author them by hand — though you can edit, delete, or add properties manually after scanning if the automatic set is not right.

This is why the scanning tool matters. A Module built by a route that does not populate Self-Healing Properties has nothing for the algorithm to work with, and self-healing will not help it.

Seeing and keeping the results

Spotting a self-healed run

After execution, a self-healing icon appears on the affected ExecutionEntries, and the ExecutionLog's Detail column explains which objects were self-healed. This is how you distinguish 'passed cleanly' from 'passed, but a control had changed' — the pass alone does not tell you.

Apply Self-Healing properties

Healing is per-execution unless you persist it. Right-click the log and select 'Apply Self-Healing properties' from the context menu to write the healed identification back into the Module. Without this step, the same control has to be re-healed on every subsequent run.

Self-healing may negatively impact performance. Every failed identification triggers a search for a similar control, and in Combination mode that means evaluating property combinations. Enabling it project-wide and never applying the healed properties means paying that cost on every run, forever.

Which engines support it

Worth noticing in the context of this course: of the AE1 engines, UIA is on the list — so the Windows desktop automation from Lesson 4 benefits from self-healing. The Excel, PDF and Mail engines are not on it, which is consistent with how they work: they address cells, document regions and mailboxes rather than identifying UI controls that can drift.
