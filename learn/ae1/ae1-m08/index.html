Why file automation belongs in a test

Setup, teardown, and evidence

Most non-trivial TestCases touch the file system somewhere. A test needs an input file placed in a watched folder before it starts; an export must be verified after it runs; yesterday's output has to be cleared so today's run is clean; a generated report needs archiving as evidence. Doing any of that by hand defeats the point of automation, and the Standard subset provides Modules for all of it — no scanning and no engine-specific work required.

These Modules live under TBox Automation Tools in the Standard subset, split across two folders: File Operations and Folder Operations.

Folder Operations

File Copy and Move require an existing target directory. Do not transfer that rule to every folder Module: Copy Folder can create a missing target, and Delete Folder only deletes empty folders unless Recursive is True.

File Operations: creating and reading

TBox Read/Create File

The dual-purpose workhorse: it creates files and writes text content, and it also verifies or buffers text content from an existing file. Encoding is configurable — UTF-8, UTF-16 and ISO-8859-1 are supported, with an optional byte order mark setting. Buffering content out of a file is how you feed data read from disk into later TestSteps.

TBox Append File

Append File adds text and creates the file if absent. Optional encoding and newline settings apply; this does not guarantee that an invalid path, permissions or conflicting file lock can be ignored.

File Operations: moving, copying, deleting

TBox Copy File

Duplicates a file into another directory. The target directory must already exist at run time — this Module will not create it for you, which is why a TBox Create Folder step often precedes it. Tricentis also notes the Module might not work if a security and password management tool is in play.

TBox Move/Rename File

Relocates a file, renames it, or both. As with Copy File, the target directory must pre-exist for a move to succeed.

TBox Delete File

Delete File returns a positive result when no matching file is found. This permits missing-file cleanup but does not prove prior existence or guarantee success for permission, lock or path errors.

A positive missing-file delete result is not an export assertion. Check existence first when required, and still investigate real filesystem errors.

File Operations: verifying and comparing

TBox File Existence

Verifies whether a file exists in a directory. It supports negation with '!' (assert a file is absent), wildcards with '*' (match a pattern rather than an exact name), and the WaitOn ActionMode — which is what you use when a file is produced asynchronously and the test must wait for it to appear rather than checking once and failing.

TBox File Compare

Compares the content of two files and can optionally generate a diff report. Where the second file has additional content, the Module highlights that in green in the report — useful when the question is not merely 'are these identical?' but 'what changed?'.

TBox Image Compare

Verifies image files (BMP, JPG, GIF) with a pixel-accurate comparison — an exact pixel match, not a similarity threshold. Note the contrast with PDF 1:1 Compare from Lesson 2, which passes when similarity exceeds an accuracy you specify. Image Compare is the stricter of the two.

The current File Operations reference includes Zip File and Unzip File. In the supplied original AE1 base subset, its File Operations folder contains eight Modules: Image Compare, File Existence, File Compare, Delete File, Copy File, Read/Create File, Append File and Move/Rename File (all TBox). Zip/Unzip are not in that folder. This is a static package inventory, not proof of installed-version availability or runtime behavior.

Matching actions to Engines: Excel, Database, Browser, and Expressions

Excel UI Engine 3.0

Steers the MS Excel application itself — driving it the way a user would, through its own interface. Use it when the TestCase needs to interact with Excel as an application, not just its data.

Excel Engine 3.0

Excel Engine works with workbook content without driving the visible Excel UI. Choose it for content operations; installed prerequisites still apply and it is not universally faster or more stable than UI steering.

Database Engine 3.0

Database Engine executes database operations through SQL statements. Use its compatible open/operate/close Modules or DB Expert; confirm the supported connection and driver.

HTML modules

Cover browser and document-level actions that sit above individual HTML controls — such as Execute JavaScript, Open a URL, and Close Browser. These act on the browser session itself, not on a specific button or field inside the page.

TBox Evaluation Tool

TBox Evaluation Tool verifies expressions that resolve to TRUE or FALSE. Use ActionMode Verify, quote values intended as strings, and account for supported dynamic expressions and NCalc special-character escaping. A string representation of a date is not automatically a chronological date comparison.

The naming convention is the tell: 'Excel UI Engine' drives the application's interface, plain 'Excel Engine' drives the file directly. The same UI-vs-file distinction shows up across other Engines too.

The original 2023 Evaluation exercise sets two equal text buffers and intends today-versus-yesterday to pass, today-versus-tomorrow to fail, and buffer equality to pass. Its table says Input, but its screenshot and current Module reference say Verify. Use Verify and validate the resolved types/expressions; quoted date strings alone are not proof of chronological ordering. An intentionally false assertion is an expected failure, not a passing overall test.

The XML Engine's Standard Modules

Current location: Standard modules → Engines → XML. The four operations below are examples; the folder also includes validation, signing and XPath evaluation Modules.

Resource vs. file

An XML Resource is Tosca's in-memory working copy — Create XML Resource makes one without any file on disk. Open/Create XML file can either make a brand-new file or load an existing one as a Resource. Save XML file is the step that commits an in-memory Resource's changes back to disk.

Bonus: the JSON Engine — reading a repeating array with one TestCase

JSON structure and identification

Current JSON Module guidance uses XScan. JSON object members are identified by name and treated as unordered pairs; array entries are positional and named item#<position>. Verify the generated structure and data types rather than assuming every export workflow is identical.

ExplicitName enables name editing

The Configuration Param ExplicitName=True permits editing the referenced XTestStepValue name. It does not itself activate wildcard matching or prove that a chosen name selects every JSON array entry.

Counts and repetition are separate concerns

ResultCount describes occurrences of the current node. TestStepFolder Repetition accepts a non-negative integer or dynamic expression, and {REPETITION} identifies the current pass. For variable-length JSON, validate counting and position selection against the actual Module; repetition alone does not guarantee coverage of each array element.

The original 2022 Academy exercise was inspected in full. It uses an API Scan XML/JSON export and an item* ModuleAttribute template, then explicitly counts and indexes the matching nodes. This source prescription is distinct from current XScan guidance and does not prove successful execution for empty, single-entry or changed-schema inputs.

Windows, Buffer, and Process Operations — matching actions to Modules

TBox Dialog

TBox Dialog handles standard Microsoft Windows dialogs without scanning. Customized dialogs must be scanned first. Caption identifies the dialog window, optional Label further narrows it using message text, and Button supplies the text of the button to confirm. JavaScript dialogs have a separate HTML Module, Steer Dialog Box.

Use the actual dialog and button text in the applicable Module. Do not infer that every confirmation popup is an unscanned Windows dialog or that changing letter case is the guaranteed fix for any failed click.

Original optional dialog example

The course adds a temporary shop address before deleting that address, preserving the original account data. Its confirmation example supplies Caption=demowebshop*, Label=Are you sure? and Button=OK. These are source-era target texts, not current-browser compatibility evidence. Independently verify the selected address identity before removal and the resulting account state; successful dialog confirmation alone is not a deletion assertion.

The guide overstates no-scan support for every dialog. The current reference distinguishes standard Windows dialogs from customized dialogs that need scanning; browser JavaScript dialogs have their own HTML Module. Matching uppercase OK in this example does not guarantee that changing case fixes every popup failure.
