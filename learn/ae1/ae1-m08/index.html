Why file automation belongs in a test

Setup, teardown, and evidence

Most non-trivial TestCases touch the file system somewhere. A test needs an input file placed in a watched folder before it starts; an export must be verified after it runs; yesterday's output has to be cleared so today's run is clean; a generated report needs archiving as evidence. Doing any of that by hand defeats the point of automation, and the Standard subset provides Modules for all of it — no scanning and no engine-specific work required.

These Modules live under TBox Automation Tools in the Standard subset, split across two folders: File Operations and Folder Operations.

Folder Operations

TBox Create Folder is frequently the step that makes a later file operation possible — several file Modules require the target directory to already exist at run time.

File Operations: creating and reading

TBox Read/Create File

The dual-purpose workhorse: it creates files and writes text content, and it also verifies or buffers text content from an existing file. Encoding is configurable — UTF-8, UTF-16 and ISO-8859-1 are supported, with an optional byte order mark setting. Buffering content out of a file is how you feed data read from disk into later TestSteps.

TBox Append File

Adds text to an existing file, with optional newline and encoding settings. Note its convenient behaviour: if the file does not exist, Append creates it. That makes it safe to use for accumulating a log across a run without a separate create step.

File Operations: moving, copying, deleting

TBox Copy File

Duplicates a file into another directory. The target directory must already exist at run time — this Module will not create it for you, which is why a TBox Create Folder step often precedes it. Tricentis also notes the Module might not work if a security and password management tool is in play.

TBox Move/Rename File

Relocates a file, renames it, or both. As with Copy File, the target directory must pre-exist for a move to succeed.

TBox Delete File

Removes files from a directory and supports wildcard patterns. Critical behaviour to know: it returns a positive result even if the file does not exist. That makes it ideal as an idempotent cleanup step at the start of a run — but it means a passing Delete step is not evidence the file was ever there.

Because TBox Delete File passes regardless, never use it as an implicit check that a file was produced. If you need to know a file existed, verify it with TBox File Existence before deleting it.

File Operations: verifying and comparing

TBox File Existence

Verifies whether a file exists in a directory. It supports negation with '!' (assert a file is absent), wildcards with '*' (match a pattern rather than an exact name), and the WaitOn ActionMode — which is what you use when a file is produced asynchronously and the test must wait for it to appear rather than checking once and failing.

TBox File Compare

Compares the content of two files and can optionally generate a diff report. Where the second file has additional content, the Module highlights that in green in the report — useful when the question is not merely 'are these identical?' but 'what changed?'.

TBox Image Compare

Verifies image files (BMP, JPG, GIF) with a pixel-accurate comparison — an exact pixel match, not a similarity threshold. Note the contrast with PDF 1:1 Compare from Lesson 2, which passes when similarity exceeds an accuracy you specify. Image Compare is the stricter of the two.

Version note: Tricentis' documentation for newer releases also lists TBox Zip File and TBox Unzip File. Those two are NOT present in the AE1 base subset's File Operations folder — do not expect them in the course workspace.

Matching actions to Engines: Excel, Database, Browser, and Expressions

Excel UI Engine 3.0

Steers the MS Excel application itself — driving it the way a user would, through its own interface. Use it when the TestCase needs to interact with Excel as an application, not just its data.

Excel Engine 3.0

Steers MS Excel files directly — reading and writing cell data without driving the Excel application's UI. Faster and more stable than the UI Engine when you only need the file's data.

Database Engine 3.0

Queries and steers data sets held in one or more databases — the go-to Engine whenever a TestCase needs to read from or write to a database rather than a file or application.

HTML modules

Cover browser and document-level actions that sit above individual HTML controls — such as Execute JavaScript, Open a URL, and Close Browser. These act on the browser session itself, not on a specific button or field inside the page.

TBox Evaluation Tool

Compares numeric, string, and alphanumeric expressions. Found under Standard subset → TBox Automation Tools → Expression Evaluation — distinct from TBox File Compare, which compares file content rather than expressions. Each comparison is entered as an Expression TestStepValue with ActionMode Verify, for example '#{DATE[][][]}'>'#{DATE[][-1d][]}' to check today's date is later than yesterday's, or '{B[Text1]}'='{B[Text2]}' to check two buffered values are equal — one Module handles dates, buffers, and plain numeric or string comparisons alike.

The naming convention is the tell: 'Excel UI Engine' drives the application's interface, plain 'Excel Engine' drives the file directly. The same UI-vs-file distinction shows up across other Engines too.

The XML Engine's Standard Modules

The folder TBox XEngines → XML in the Standard subset contains Modules for the XML Engine 3.0 — no scanning required, same as the other TBox Automation Tools Modules.

Resource vs. file

An XML Resource is Tosca's in-memory working copy — Create XML Resource makes one without any file on disk. Open/Create XML file can either make a brand-new file or load an existing one as a Resource. Save XML file is the step that commits an in-memory Resource's changes back to disk.

Bonus: the JSON Engine — reading a repeating array with one TestCase

Scanning a JSON file

A JSON file is scanned like an API — Module folder → Scan → API → point the file picker at the .json file, then export it as an XML/JSON TestCase. The scan produces a Module whose ModuleAttributes mirror the file's structure, including one attribute per array entry: item#1, item#2, item#3, and so on for however many entries the sample file happened to have.

The problem: the array's length isn't fixed

A Module scanned from one sample file hard-codes exactly the entries that file had. If the real data returns 20 entries instead of 3, a TestCase built directly on item#1 / item#2 / item#3 simply never looks at the other 17. Reading 'however many entries are actually there' needs the Module and the TestCase to both stop assuming a fixed count.

The wildcard attribute: item#1 → item*

On the Module, delete every ModuleAttribute after the first array entry, keeping only item#1, then rename that surviving attribute's Name from item#1 to item* — turning one specific indexed entry into a wildcard that matches any entry in the array, at any index.

ExplicitName = True

A Configuration Parameter added on that same wildcarded attribute. Without it, Tosca's wildcard matching behaves generically; with ExplicitName set to True, the attribute is treated as matching the literal repeating node structure of the source file, which is what makes the wildcarded Module actually bind correctly against the real (variable-length) JSON at run time.

Counting entries, then repeating over them

A first TestStep drags the Module in with ActionMode Buffer on an expression like .ResultCount == someBuffer, capturing how many array entries are present in this run. That count then goes into the Repetition property of a TestStepFolder — set it to {B[someBuffer]} — which turns the folder into a loop that runs once per entry. Inside that repeating folder, the item* attribute is referenced as #{REPETITION}, a token that automatically advances to the next array index on every pass, and each field buffered inside the loop is named with the same token (e.g. firstName_{REPETITION}) so every entry's data lands in its own uniquely named buffer instead of overwriting the last one.

The result is one TestCase that reads a JSON array of any length: it buffers the count, repeats a TestStepFolder that many times, and reads a fresh set of fields on every pass — nothing about it needs to change if next week's file has 3 entries or 300.

Windows, Buffer, and Process Operations — matching actions to Modules

TBox Dialog

Steers a Windows dialog box or browser confirmation popup — an 'Are you sure?' prompt, for instance — without ever scanning it. Because it is a Standard Module rather than something produced by a scan, the same TestStep works across different webpages and applications: set Caption to identify the dialog window (wildcards allowed, e.g. 'demowebshop*'), Label to the dialog's message text, and Button to the button to click, all with ActionMode Input. This is the answer whenever a confirmation popup would otherwise force an extra scan just to handle one button.

The Button TestStepValue is case-sensitive against the button's actual caption — 'OK' has to be typed with a capital O and K exactly as it appears on the button, not 'Ok' or 'ok'. Alternatively, add the exact value to the ValueRange of the Button ModuleAttribute on the TBox Dialog Module itself, so it can be selected rather than retyped.

ActionModule
Open an application or an executable fileTBox Start Program
Buffer the name of the TestCase that uses the ModuleTBox Name To Buffer
Verify or buffer only part of a valueTBox Partial Buffer
Copy text to the Windows clipboard, or verify/buffer text from itTBox Clipboard
Verify existence, or create/copy/delete a folderFolder Operations Modules (TBox Create Folder, Copy Folder, Delete Folder, Folder Existence)

Don't confuse the three Buffer Operations Modules: TBox Set Buffer stores a value you supply yourself, TBox Name To Buffer automatically stores the current TestCase's own name, and TBox Partial Buffer extracts or verifies only part of a larger value.
