Debugging workflows and their boundaries

Use the available evidence to investigate a failure. These tools do not guarantee an exact root cause or turn an application defect into a test defect.

Debugging Helper Panels and JS Code Debugging

Debug Helper panels

Console Log filters messages and can preserve them between runs; Breakpoint Manager locates/removes breakpoints; Scope shows incoming parameters and test/global exports. Future, unexecuted steps have no runtime values to inspect.

JS Code Debugging

For supported browser steps, pause before the step in a local debug run, use Step Into, switch to the AUT, open Chrome DevTools and follow the confirmation prompt. Inspect the code, resume its execution and return to the editor. Supported types include custom action/validation/wait, email/network validation and API action/validation; CLI actions are not listed for this browser workflow.

Debugging Controls: pausing and stepping through a test

Pause

Pause stops at the nearest step boundary in local debug mode. Continue proceeds from the current location; another breakpoint can pause it again.

Step-by-step execution

Start a local run with debugging. Pause or insert a breakpoint, then use the available stepping controls. Step Over executes a step/group; Step Into opens a group before its first step; Step Out executes its remaining steps before leaving.

Breakpoints: manual vs. virtual

Breakpoints pause execution at various stages. Manual breakpoints are explicitly set by the user at a chosen step. Virtual breakpoints are created automatically by the system when debugging controls are used — such as step into, step out, step over, and pause — without the user having to set them by hand.

Breakpoint Manager identifies breakpoint locations, supports navigation and removal, and highlights the current pause.
