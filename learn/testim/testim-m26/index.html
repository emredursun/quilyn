The four Testim debugging tools, at a glance

These four tools form a natural workflow: use Debugging Controls and Helper Panels to isolate exactly where and why a test broke, drop into JS Code Debugging if the culprit is a custom step's code, then use Recording New Steps to fix the test itself once the root cause is clear.

Debugging Helper Panels and JS Code Debugging

Debug Helper panels

Supporting panels available during a debugging session that surface additional context around a step — building on Pause/Continue, breakpoints, and step-by-step execution with a richer inspection surface for diagnosing exactly why a step behaved the way it did.

JS Code Debugging

A dedicated debugging workflow for custom JavaScript steps (custom actions, custom validations, CLI actions) — since these steps run hand-written or AI-generated code rather than a predefined action, they need their own debugging path distinct from the generic step-level breakpoint tools covered above.

Debugging Controls: pausing and stepping through a test

Pause

Pauses test execution at any point in the editor — the run stops at the nearest step when clicked — after which Continue resumes execution from that exact location until the test ends.

Step-by-step execution

To run step-by-step, click the dropdown next to the Play button and select 'Run locally step by step', then use the 'Play Next Step' button to execute one step at a time — letting you inspect state after each individual action rather than watching the whole test run at full speed.

Breakpoints: manual vs. virtual

Breakpoints pause execution at various stages. Manual breakpoints are explicitly set by the user at a chosen step. Virtual breakpoints are created automatically by the system when debugging controls are used — such as step into, step out, step over, and pause — without the user having to set them by hand.

The breakpoint manager panel lists and manages all breakpoints in a test, giving a single place to review where execution will pause before a debugging session starts.
