Debugging tests during runtime

Stop, Pause, Step

Local debug mode supports Pause/Continue, stepping and breakpoints. Pause stops at the nearest step boundary, not an arbitrary instant inside any action. Local playback without debugging does not pause at breakpoints; remote grid execution is not this local debug mode.

Resuming from a breakpoint

Continue/Play resumes a paused run from the current location, unlike Rerun, which restarts. Distinguish manual breakpoints from temporary virtual debug locations rather than promising every breakpoint marker remains unchanged.

Running from a specific step

Play from here starts after the selected arrow. Establish earlier required state, such as authentication and variables; skipping setup can cause failure. This is partial debugging, not full-flow coverage.

This is the same debugging toolkit covered in more depth in the 'Debugging test cases' and 'Streamlining Testing and Debugging' modules — this course frames it specifically as part of the broader 'managing and analyzing results' workflow.

Organizing and filtering with Result labels

Result labels

Free-text labels attached to a run — distinct from the Labels applied to tests in the Test Library. Result labels are commonly used to record things like which application environment was tested, which application version was tested, or which user/system executed the run (examples: 'nightly-scheduler', 'v1.42.34', 'Jenkins', 'Staging').

Adding and filtering by result labels

Add remote-run result labels with CLI --result-label or Scheduler Advanced Options. Each label has a 250-character maximum. Run pages support filtering; test-definition Labels are a separate selection/organization mechanism.

Tagging failed runs with failure types

Tagging a failure

Tag remote-run failures using the documented categories: Bug in app, Environment issue, Invalid test data, Test design or Other. These human-selected cause categories are distinct from engine errors such as Element not found or JavaScript Error.

Why tag failures

Once failures are tagged, the failure-type filter can show only the runs tagged with a specific reason, and the Reports view's donut chart shows the percentage distribution of failure types (each tag's share of total runs, alongside its change vs. the previous period) — turning individual failures into a trend you can act on. Clicking a failure tag jumps straight to the Test Runs screen, pre-filtered to every run tagged with that type.

Tagging does not repair the defect. With a configured tracker connection, the same dialog can link an existing issue or create/publish a new one, so separate manual re-entry is not universally required.
