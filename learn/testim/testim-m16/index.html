Debugging tests during runtime

Stop, Pause, Step

Rather than always running a test start to finish, Testim lets you Pause execution at any point, resume with Play, or run step-by-step to inspect state between actions. Breakpoints (manual, set by you, or virtual, created automatically when using step into/out/over or pause) mark exactly where execution should halt.

Resuming from a breakpoint

After a test pauses at a breakpoint, clicking the Play button ('Run Test') in the action menu resumes the test from that exact step — not from the beginning, and not skipping ahead. The breakpoint itself isn't removed just because execution passed through it.

Running from a specific step

You don't have to start from the very beginning to debug a later part of a test: hovering the arrow between two steps and clicking Play from here starts the run from the step right after that point — useful for quickly re-checking just the part of the test that's actually under investigation.

This is the same debugging toolkit covered in more depth in the 'Debugging test cases' and 'Streamlining Testing and Debugging' modules — this course frames it specifically as part of the broader 'managing and analyzing results' workflow.

Organizing and filtering with Result labels

Result labels

Free-text labels attached to a run — distinct from the Labels applied to tests in the Test Library. Result labels are commonly used to record things like which application environment was tested, which application version was tested, or which user/system executed the run (examples: 'nightly-scheduler', 'v1.42.34', 'Jenkins', 'Staging').

Adding and filtering by result labels

Result labels are added as part of a Scheduler's Advanced Options when setting up a scheduled run. Once runs carry labels, both the Suite Runs / Test Runs pages and the Filter Remote Runs pane let you filter directly by a result label — alongside filtering by execution type (Execution, Label, Plan, Scheduler), branch, or browser.

Tagging failed runs with failure types

Tagging a failure

A failed run can be tagged with a failure-type reason, turning a raw 'failed' status into a categorized one — the same kind of categorization used by the Failure Types report covered in test-results modules (e.g. Element not found, Element not visible, JavaScript Error).

Why tag failures

Once failures are tagged, the failure-type filter can show only the runs tagged with a specific reason, and the Reports view's donut chart shows the percentage distribution of failure types (each tag's share of total runs, alongside its change vs. the previous period) — turning individual failures into a trend you can act on. Clicking a failure tag jumps straight to the Test Runs screen, pre-filtered to every run tagged with that type.

What tagging does NOT do: it doesn't automatically fix the failing test, and it doesn't eliminate the need to manually log a defect in a bug tracker — it's a categorization and analysis aid, not an automated remediation.
