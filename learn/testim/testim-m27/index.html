The TestOps Dashboard: reading project health

TestOps Dashboard

The Dashboard summarizes project activity with plan-dependent panes and selected branch context. It helps prioritize investigation; activity alone does not prove coverage.

Duplication Level pane

Duplication Level estimates redundant sequences that may benefit from shared groups. A lower duplication estimate does not certify overall project health.

Recent Activity pane

Recent Activity links project events. Assigned to me concerns owned tests; the remote pane changes from execution counts to owned-test runs, rather than filtering only actions performed by you.

Together these panes give quick access to prioritize work, identify tests that need updating, review recent changes, and see open pull requests — all without navigating away from a single dashboard view.

Turbo Mode: faster feedback

What Turbo Mode does

Turbo Mode is a professional-plan feature. It ignores step delays and omits successful-run artifacts to reduce overhead. The vendor reports an average speed improvement, not a promised result for every test; browser crashes can prevent failed-run artifacts too.

Enabling Turbo Mode

Enable --turbo-mode for CLI runs or the Scheduler toggle. Execution is extension-based on Chrome or Edge Chromium; this is not a general mode for every browser or mobile device.

Capturing a video for a bug scenario

Prerequisite: the Testim Chrome Extension

The Testim browser extension can capture webpage bugs independently of automated tests. Bug reports may include a screenshot, reproduction video, interaction screenshots and generated reproduction text.

Publishing the capture

Connect the relevant bug tracker before submitting a report. The accessible capture page is incomplete and does not establish that every extension video is stored in an associated test-run result: a standalone webpage capture may have no such run.

Quarantine and CI/CD: what actually happens to a quarantined test

Quarantined tests are skipped in CI/CD, not run

A test marked Quarantine (unstable/flaky, generating errors) does NOT run as part of a normal CI/CD execution — it still appears in the suite run with a quarantine indication, and is recorded in the run's result XML with a 'Skipped' flag, rather than being executed.

Why quarantine this way

This lets a team quarantine a flaky/failing test without removing it from the CI/suite entirely — the test stays visible (so it's not forgotten), doesn't fail the overall build, and can be gradually re-added to real execution once fixed. A CLI override, --run-quarantined-tests, exists for the rare case where you deliberately want quarantined tests to run anyway.
