Keyboard Shortcut steps

Add Keyboard Shortcut step

Sends a specified keyboard shortcut combination (e.g. Ctrl+C) to the AUT during execution — added like other predefined Actions. It's cross-platform by design: a shortcut recorded on Windows (e.g. Ctrl+C) is automatically translated to its Mac equivalent (Cmd+C) at execution time, and vice versa.

Setting the shortcut in Properties

In the step's Properties panel, under the Keyboard Shortcut section, placing the cursor in the Windows field and pressing the keys (all at once) auto-fills the equivalent in the Mac field — or the reverse, starting from the Mac field. Whichever platform the test actually runs on at execution time, Testim uses the corresponding field.

Unsupported combinations

Not every possible key combination is supported. If you use a keyboard shortcut Testim doesn't recognize, it presents an 'unsupported keyboard shortcut' error rather than silently ignoring it, defaulting to something else, or blocking the whole test from running.

Parameters: flexible test step customization

Why parameterize

Parameters let a step or group be customized per use — passing in different information without knowing every value in advance — so the same underlying steps serve multiple scenarios instead of being copy-pasted with small edits each time.

Parameter override rules

When both parameters and test data could supply a value for the same field, parameters take precedence over test data. Within Testim's layered override system specifically, config-file parameters override params-file parameters, and — within the config file — a beforeTest hook's values override a beforeSuite hook's values; params-file parameters, in turn, override the default test data/run data.

Extract Value: capturing data for later steps

Extract Value step

The Extract Mode of an Extract Value step determines the value and format of the contents captured into an extract variable — for example, pulling an order number or a generated OTP code off the page and storing it so a later step can use or validate it. Selecting the mode is done directly in the step's own Properties, not through code, and not through a project-level setting.

This is the same pattern used to grab a verification code from an email/SMS inbox: extract only the stable value you actually need (the code, a link, a subject line) rather than trying to assert on the whole message body.

Wait for Events: synchronizing tests with the application

Waiting for an event, not a fixed time

Testim can wait for a specific event to occur before proceeding to the next step — an element becoming visible, specific text appearing, or a file finishing its download — rather than a plain, guessed time delay. This is the same condition-based-waiting principle covered for basic Wait For steps, applied to a broader set of real application events.

Wait for element visible / not visible

Wait for element visible pauses until a target element appears; Wait for element not visible pauses until an element disappears (e.g. a loading spinner clearing). Both are added the same way as other predefined steps: hover the arrow, open Testim's predefined steps, pick the step, then select the target element.

Changing the element after the fact

If the wrong element was targeted (or the element changed), the fix is the same as for any other step's target element: open the step's Properties and use Reassign to point it at a different element — not deleting and re-recording the step, and not just adjusting the wait duration (which doesn't fix a wrong target).
