Conditions: running steps only when it makes sense

Conditions

Conditions can be applied to a step (run it or not) or to a loop (repeat it or not). If a condition is false, the default behavior is to skip the step immediately or end the loop immediately; if true, the step executes or the loop repeats immediately.

Condition types

Testim supports several condition types, including Element (does an element exist/is it visible), Element text (does an element contain specific text), and Custom (a JavaScript expression you write yourself) — covering everything from simple presence checks to fully custom runtime logic.

Advanced condition settings — retry

By default, a false condition immediately skips the step (or ends the loop). The 'retry' setting changes this: you specify a period in milliseconds during which Testim keeps re-checking the condition before giving up and moving on — useful for conditions tied to asynchronous UI states that need a moment to resolve.

Setting a Custom condition on a step

To attach a Custom (JavaScript) condition to a step or shared step: open the step, click the gear icon to open its Properties, find 'When to run step' (or 'When to run this step'), and select Custom — this opens the field where the JavaScript condition expression is written.

Parameters: variable data instead of hardcoded values

Parameters

A parameter is a variable that can be used to pass information into a test step, letting the same step or group work with different data without needing separate, near-duplicate steps for each scenario.

Parameters on groups

Groups can define their own parameters. If a group is shared across multiple tests, those parameters remain available to every calling test — each test just sets its own values for the parameters rather than duplicating the group's underlying steps.

This is what makes a Shared login group genuinely reusable across many tests with different credentials: the group's steps stay identical, only the parameter values (username/password) differ per caller.

Generating dynamic test data: random values and dates

Generate random value

Found under the predefined steps menu ('M' icon) → Actions → Generate random value. Produces a random string (letters, numbers, or both, via String type), with optional Add Prefix / Add Suffix and a configurable Length — used to avoid hardcoding a value that must be unique or unpredictable on every run, like a test username or email local-part.

Generate date

Also under the predefined steps menu → Actions → Generate date. Produces a date value offset from the current browser time (or UTC), controlled by Time difference and Use UTC, with a configurable Date format (default 'YYYY-MM-DD', or any JS date format).

Finding your way around: search and draft recovery

Search within a test

Typing at least three characters into a test's search field searches across the test's Step description, JS Code, Parameters, Base URL, the URL inside a Navigation Step or an Add API Action step, Test Data, and Condition — a broad sweep across nearly everything a step can contain, not just visible step names. The search is not case sensitive.

Recovering an unsaved test

Changes to a test are auto-saved locally as a draft in the browser's cache every 30 seconds. If the browser closes, you log out, the page reloads, or anything else interrupts editing on the same computer, reopening the test shows a recovery dialog with two choices: Recover opens the draft with the unsaved changes intact; Dismiss discards the draft and opens the test in its last saved state instead. After recovering, it's recommended to click Save — the auto-recovery draft itself isn't meant to be relied on as permanent storage.

Wait For: condition-based waiting instead of fixed delays

Wait For step

Rather than inserting an arbitrary fixed-time delay (which either wastes time or isn't long enough), a Wait For step pauses the test until a specific condition becomes true — for example, an element becoming visible — before continuing to the next step.

This is the same underlying idea as Conditions applied specifically to timing: instead of guessing how long an async operation takes, the test waits exactly as long as needed and no longer.
