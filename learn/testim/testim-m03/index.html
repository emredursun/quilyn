Conditions: running steps only when it makes sense

Conditions

Conditions can be applied to a step (run it or not) or to a loop (repeat it or not). If a condition is false, the default behavior is to skip the step immediately or end the loop immediately; if true, the step executes or the loop repeats immediately.

Condition types

Element conditions use visibility; Element text checks the selected target’s text; Custom permits JavaScript logic. Always Run and Never (skip) are additional execution choices. A condition gates execution, not an assertion that a business outcome occurred.

Advanced condition settings — retry

By default, a false condition immediately skips the step (or ends the loop). The 'retry' setting changes this: you specify a period in milliseconds during which Testim keeps re-checking the condition before giving up and moving on — useful for conditions tied to asynchronous UI states that need a moment to resolve.

Setting a Custom condition on a step

To attach a Custom (JavaScript) condition to a step or shared step: open the step, click the gear icon to open its Properties, find 'When to run step' (or 'When to run this step'), and select Custom — this opens the field where the JavaScript condition expression is written.

Parameters: variable data instead of hardcoded values

Parameters

A parameter is a variable that can be used to pass information into a test step, letting the same step or group work with different data without needing separate, near-duplicate steps for each scenario.

Parameters on groups

Groups can define their own parameters. If a group is shared across multiple tests, those parameters remain available to every calling test — each test just sets its own values for the parameters rather than duplicating the group's underlying steps.

Shared parameter definitions support reuse, with values supplied by each caller. Parameters must be used in supported fields; Variable Name, Description and Date Format are documented exceptions.

Generating dynamic test data: random values and dates

Generate random value

Add Generate random value through predefined Actions. Configure character type, random length and optional prefix/suffix, then reference the stored variable in a later input. Randomness does not guarantee uniqueness; verify collision handling when uniqueness is required.

Generate date

Add Generate date through predefined Actions. Configure the date format (default YYYY-MM-DD), signed offset and browser time or UTC. Match the application’s actual clock, timezone and required calendar semantics.

Finding your way around: search and draft recovery

Search within a test

Within-test search is case-insensitive and requires at least three characters. It searches descriptions, code, parameters, supported URLs, data and conditions, but not every property. Documented exclusions include Sleep duration, Extract variable name and generated-value settings other than descriptions.

Recovering an unsaved test

Testim stores a local recovery draft every 30 seconds. Recover restores the last available cached draft, so edits after that snapshot may be missing; cleared/unavailable cache cannot be treated as durable backup. Dismiss opens the last saved test. Save deliberately after recovery.

Wait For: condition-based waiting instead of fixed delays

Wait For step

Condition-based waits retry until the required state is detected or the step timeout is reached. A condition that never becomes true must not hang indefinitely. Select a timeout and failure handling for the scenario.

Condition-based synchronization can reduce unnecessary fixed delays, but polling and execution overhead mean it is not an exact-duration or no-flakiness guarantee. Sleep remains supported for deliberate fixed pauses.
