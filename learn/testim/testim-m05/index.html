Running multiple tests locally and on a schedule

Run multiple tests locally

From Test List > Tests, selecting several tests and running them takes control of your mouse and runs the selected tests sequentially in your local Chrome browser (local runs are Chrome-only). Because Testim is actively driving the browser, you should not use your mouse or computer while the tests run. Locally-run tests are tracked and viewable afterward under Runs > Executions, tagged 'local-suite'.

Treat browser/session cleanup as a diagnostic check if a local batch stalls. An unclosed browser alone does not establish that the next test must fail; inspect the actual error and lifecycle evidence.

Scheduler

Scheduler runs selected labels, suites or test plans on a schedule, with applicable grid, branch and configuration. It can coexist with CI. Test plans supply their own grid/base URL/configuration, so those overrides are not available in the scheduler. Clone a schedule and review the copied settings.

Incognito mode and the Configuration File

Incognito mode (Testim IO)

Incognito isolates browser cookies, login state and autocomplete from ordinary sessions. Enable the Testim extension in Incognito before local use. It does not reset backend data or guarantee an entirely fresh application/account state.

Configuration File with the CLI

A CLI configuration file supplies execution options, parameters and hooks; it is not automatic encryption. Use supported Secrets Manager references instead of literal credentials. Static JSON params files need the documented JavaScript/module.exports conversion for secret references. Screenshot masking applies only to password-type fields, so review artifacts separately.

Timeouts and retries

Test timeout

CLI --timeout uses milliseconds; Scheduler Test timeout uses seconds. Both document a 10-minute default and three-hour maximum. Do not confuse this test limit with the execution-list status that can temporarily become Timeout after 90 minutes while grid work continues.

Timeout retry

CLI documentation describes timeout-specific retries up to three times and --disable-timeout-retry. Scheduler documentation describes one extra timeout run and its disable toggle. Check the actual execution path/version rather than promising one universal retry count.

Failed-test retries

General failed-test retries use their configured maximum and stop on success. They are separate from timeout retries; passing after retry is evidence to investigate, not proof the original defect or instability is fixed.

Diagnosing a failure and reading the Execution Runs view

Diagnosing why a test failed

For visual symptoms, compare available baseline and result screenshots alongside the failed step, error and environment. Screenshots do not establish every network, credential or backend cause; gather relevant evidence before changing configuration.

Execution Runs view

The execution list shows duration, parallel test concurrency and results. Its graph plots execution count over time, not duration. Execution details include source/version/grid/data evidence; the details’ concurrent-executions count is distinct from the list’s parallel-test count.

The Test Runs view: statistics across past runs

Test Runs / Test statistics

The Test Runs screen shows statistics on past runs — aggregated across all selected tests, and per-test (e.g. how many times a specific test passed/failed and its average test duration) — under the Test statistics section. Filters (status, time, execution/label) narrow what's shown, and clicking a specific run opens it in the Test Editor to drill into per-step screenshots and durations.

Counted runs vs. Local Editor Runs

Test Runs separates Counted Runs from Local Editor Runs. Under the documented test-runs subscription model, local editor runs are exempt; local library/CLI executions and remote grid runs are counted. A remote grid run launched from the editor must not be treated as quota-free solely because the editor triggered it.
