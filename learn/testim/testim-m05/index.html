Running multiple tests locally and on a schedule

Run multiple tests locally

From Test List > Tests, selecting several tests and running them takes control of your mouse and runs the selected tests sequentially in your local Chrome browser (local runs are Chrome-only). Because Testim is actively driving the browser, you should not use your mouse or computer while the tests run. Locally-run tests are tracked and viewable afterward under Runs > Executions, tagged 'local-suite'.

Local runs are sequential and single-browser: each test in the batch expects the browser to be in a clean state before it starts. If the browser from the previous test doesn't close properly, the next test case in the batch is liable to fail to run, since it can't reliably take over an already-open, unexpected browser state.

Scheduler

Lets you schedule tests to run on a predefined schedule (the test must carry a Label or belong to a Test Suite), with options for Where to run (which grid) and Branch. A schedule can be cloned, modified, and saved as a new schedule — reducing the effort and risk of manually recreating a similar configuration. The Scheduler is especially valuable for teams that don't have CI/CD tooling in place: it provides built-in, manually-defined scheduled execution without needing a Jenkins/GitHub Actions/Azure DevOps pipeline to trigger runs.

Incognito mode and the Configuration File

Incognito mode (Testim IO)

Running tests in Incognito mode starts each execution from a fresh browser state — no cookies, no local storage, nothing remembered from a prior run. This is the primary benefit: a clean, predictable starting point every time, rather than saved login states or stored cookies leaking between runs and masking real issues (like whether a login flow genuinely still works).

Configuration File with the CLI

A Configuration File passed to the CLI is the main mechanism for keeping sensitive values (credentials, tokens) out of the test itself. Rather than hardcoding a password into a step, hidden parameters and encrypted credentials can be supplied through the Configuration File (or a JSON Parameters File) at run time — Testim explicitly recommends against exposing sensitive information in plain text or version history, pointing instead to the Configuration File, Hidden Parameters, and the Secrets Manager.

Timeouts and retries

Test timeout

A timeout period (in milliseconds) aborts a test run if it's exceeded. The default is 10 minutes, with a maximum of 3 hours — long enough for legitimately slow flows, but still a hard ceiling against a genuinely hung run.

Timeout retry

By default, when a test fails specifically due to 'test reached timeout', Testim automatically re-executes it — up to 3 times — before marking it failed. This default can be disabled with the --disable-timeout-retry CLI flag when you want a timeout to fail immediately and be investigated rather than retried.

Failed-test retries

Separately, failed-test retries can be configured to re-run any failed test repeatedly until it either passes or the max retry count is reached — a broader mechanism than the timeout-specific retry, aimed at absorbing general flakiness rather than one specific failure cause.

Diagnosing a failure and reading the Execution Runs view

Diagnosing why a test failed

Beyond just an error message, comparing the run's baseline (expected) screenshot against its result (actual) screenshot is one of the most direct ways to see exactly what went wrong visually — a layout shift, an unexpected error banner, a missing element — rather than immediately re-running blind or reading console logs in isolation.

Execution Runs view

The runs graph gives an overview of the number of executions and tests per execution over time, plotting duration on one axis against time, and showing Concurrency (how many executions ran at the same time as a given one). Hovering an entry surfaces further details: Extension Version, Source (local vs. remote), CLI Version, Grid Name, and the Test Data (parameters) used for that run.

The Test Runs view: statistics across past runs

Test Runs / Test statistics

The Test Runs screen shows statistics on past runs — aggregated across all selected tests, and per-test (e.g. how many times a specific test passed/failed and its average test duration) — under the Test statistics section. Filters (status, time, execution/label) narrow what's shown, and clicking a specific run opens it in the Test Editor to drill into per-step screenshots and durations.

Counted runs vs. Local Editor Runs

Remote execution runs — suite runs, plan runs, scheduled runs, and label-triggered runs — are the 'counted' runs shown in the main Test Runs view. Tests run directly from the editor are tracked separately, in their own 'Local Editor Runs' tab, and are explicitly excluded from (not counted toward) the subscription-quota-relevant Test Runs statistics.
