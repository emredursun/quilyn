The target element and its Properties panel

Target element

A step’s target is the selected AUT element, represented by a thumbnail in Properties. Open Show Properties to edit supported settings; available fields depend on the step type.

Opening the Properties panel

Hovering over any step in the test and clicking Show Properties opens the Properties panel on the right-hand side. From there, hovering over the target element thumbnail reveals four options: Highlight, Reassign, Improve, and View locators.

Editing step properties (not just the target element) is also how you rename a step, edit the value a step enters, or adjust timing/behavior settings — all part of what 'editing tests' covers beyond re-recording from scratch.

The four Target Element options

Highlight

Highlight temporarily emphasizes the selected target in the AUT for inspection; it does not replace locators or highlight every element matching a class.

Reassign

Reassign chooses a different target and replaces its locators. Use it when the intended target has genuinely changed.

Improve

Improve updates identification for the existing target after a DOM change, comparing captured and current attributes. Reach the relevant AUT state and verify the resulting target.

View locators

View locators displays weighted target and parent attributes. Resilience is not guaranteed; manual locator edits disable future Auto Improve for those locators, and the documentation recommends consulting support.

Specialized step properties

Expected value

The value Testim checks for when the step runs (used by Validate element text, Validate CSS property, Validate HTML attribute, Wait for element text). It's editable after the step is created, and — importantly — it isn't limited to a literal string: Parameters, regular expressions, and JavaScript expressions can all be used in the Expected value field.

Expected status (checkboxes / radio buttons)

Used by Validate checkbox and Validate radio button to set whether the step expects Checked (the default) or Unchecked. These validations only work on native checkbox/radio input elements — a custom checkbox implementation that doesn't use an underlying native input isn't supported.

Add Prefix / Add Suffix / String type / Length

Generate random value sets character type and random length. Optional prefixes and suffixes can contain quoted strings or existing variables/expressions; they are not restricted to fixed strings.

Date format / Time difference / Use UTC

Generate date uses configurable format tokens (default YYYY-MM-DD), a signed time offset and browser time or UTC. Check the required input format; do not confuse format tokens with an arbitrary JavaScript Date object.

Extract Mode

Extract Mode selects the whole text or number/date/Regex matches. Individual extracted matches remain strings; All matches modes return arrays. Convert deliberately before numeric calculations.

Variable name and Variable scope

Choose a valid JavaScript identifier; dollar signs and underscores are allowed. Generated values default to Test scope; Local limits scope and Suite shares it across suite tests. Consult the individual step’s documentation: the Extract Value page describes Local availability differently from the general Properties table.

Native events (Click step)

Click can use native browser events or synthetic events. The Native events setting is a possible troubleshooting change, not proof that event type caused every click-without-effect failure; inspect target, readiness and outcome.

Pre-step delay (ms)

Pre-step delay postpones the not-visible check. It does not continuously monitor absence or prove the element cannot appear after the check.

Sleep duration

The property of a Sleep step — how long (in ms) the test pauses before the next step. The default is 1 second (1,000 ms), and it's directly editable.

+PARAMS

Supported custom, API and network steps expose PARAMS for HTML and JavaScript inputs. Parameters let callers supply different data to the same logic.

Auto complete

While recording a test, Testim watches for a match against your existing Shared Groups and suggests them as the next steps — a pop-up labeled 'Auto record your steps' appears above the steps counter listing the matching suggestions. Clicking a suggestion has Testim automatically perform and save those steps in the test being recorded, instead of you re-recording a sequence you've already built elsewhere. If the matched group has parameters, you're prompted to name them and supply values before the steps are added. This feature is available on the professional plan.

Replace with a clone / See old revisions

Replace with a clone creates a separately editable copy of a shared step/group. Cloning a group does not automatically detach nested shared steps: they remain shared. Saved changes create revisions; reverting shared content can affect other instances.

Reusable editing: groups and Shared Steps

Groups

Steps can be grouped together, and groups can be nested inside other groups. A group is identified in the test by a folder icon in its upper-left corner.

Shared Steps / Shared Group

Shared groups enable cross-test reuse within a project. Edits to shared definitions affect their references; review affected tests and distinguish instance-specific properties from shared ones.

Groups can take parameters (variables). When a group is shared across multiple tests, those parameters stay available in every test that calls it — each caller just supplies its own values instead of duplicating the underlying steps.

Shared Steps Library

A dedicated library view listing every shared step, group, and folder in the project, with four columns: Name, Date Modified, Kind (shared step / group / folder, plus the underlying step type), and Used by (a clickable count of how many tests reference that item — clicking it navigates to the Test Library filtered to just those tests). The library can be filtered by category: Groups, Actions, Validations, and Wait for.

Labels

A lightweight organizational tool applied to tests in the Test Library, letting you categorize and quickly find tests without moving them between folders. A test can carry multiple labels at once (e.g. 'smoke', 'checkout'), and the library can be filtered or searched by label — useful once a project's test count grows past what folders alone can keep navigable. (Covered in more depth, alongside folders and dependencies, in the 'Advanced test management' module.)
