Recording: the starting point of every test

The AUT browser

Creating a test starts by navigating to the relevant website inside the Application Under Test (AUT) browser window and recording the series of actions you want tested — clicks, text entry, scrolling, navigation. Testim captures each action as a step.

Steps

Each recorded action becomes a step, shown as a box in the test procedure with an icon in its upper-left corner indicating the action type (click, enter text, scroll, etc.). Steps run top-to-bottom in the order they were recorded, and can be reordered, edited, or deleted afterward.

'Codeless' means no scripting is required to produce a working automated test from a recording — but every step remains editable afterward, including adding validations, which is where the later 'editing tests' skills come in.

Smart Locators: why the test doesn't break on every UI change

Smart Locators

When an element is selected during recording, Testim's algorithm analyzes potentially hundreds of attributes associated with that element and assigns weights to them to uniquely identify it. These weighted attributes are the element's Locators. Smart Locators also learn with each test run — if some attributes change, Testim falls back to other still-valid attributes instead of failing outright.

This is the mechanism that lets a test survive normal UI churn (a class name changing, a button being restyled) without needing to be re-recorded every time — it's what makes the tests genuinely maintainable rather than brittle.

Saving a test and viewing results

Saving

A recorded test is saved into the project's Test Library, where it can be organized into folders, labeled, and re-run at any time — locally, from the editor, from the CLI, or on a schedule.

Viewing results

After a run, Testim reports pass/fail per step and per test, and surfaces the reason a step failed (e.g. element not found, element not visible) so you can diagnose without re-watching a full manual re-run.
