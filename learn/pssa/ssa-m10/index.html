Pre- and post-processing in Flow Actions

Choose the right mechanism

Pre-processing runs when a Flow Action is presented or selected; post-processing runs after successful submission. Pre-processing can execute again on revisit, so defaults must not overwrite intentional edits. Prefer a Declare Expression for a value that should remain derived rather than recalculating it on each action.

Worked example: Populate a default meeting only when none was deliberately selected or removed. When the user revisits the form, do not recreate a deleted default.

Pre- and post-processing configuration for Flow Actions

Choose the right mechanism

Configure pre/post Data Transforms, activities or supported automations on the Flow Action's Action tab. Post-processing can save one or more savable Data Pages, with parameters and When conditions. Define persistence timing deliberately; displaying a form is not committing its external data.

Worked example: On successful submission of a supplier form, save D_Supplier with the supplier ID parameter. Skip the save when the form represents an unchanged draft.
