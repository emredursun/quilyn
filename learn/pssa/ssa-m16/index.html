Error handling in connectors

Choose the right mechanism

Distinguish transient failures from persistent configuration or request errors. Temporary unavailability can justify a controlled retry; malformed requests or invalid configuration need correction. Communicate failure early rather than silently returning misleading success.

Worked example: A partner is restarting: notify the user and retry when appropriate. A wrong SOAP message schema keeps failing until its mapping is fixed, so repeated blind retries waste resources.

Error detection configuration

Choose the right mechanism

For Data Page connector loads, inspect errors in the response Data Transform and invoke reusable handling such as a copy of pxErrorHandlingTemplate. The connector error-handler flow covers errors not handled earlier; the default ConnectionProblem flow is not automatically invoked after a response transform has already handled the error.

Worked example: D_Policy detects page messages in its response transform, writes a safe diagnostic record and returns a user-actionable message. A fallback flow is reserved for unhandled failures.

Integration testing and security

Choose the right mechanism

Test success, incorrect data, timeout and authentication failures. Assert mappings on Data Pages and use appropriate credentials, certificates, keystores and approved endpoints. Secure transport does not make all incoming data safe; validate inputs and avoid exposing credentials in logs.

Worked example: Run D_Address with synthetic valid and invalid IDs, then assert mapped fields and failure messages. Configure required certificates in a keystore and keep secrets out of test fixtures.
